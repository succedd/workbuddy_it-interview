服务雪崩是怎么发生的？限流、熔断、隔离、降级该怎么配合才有效？

中级场景题后端架构师架构师SRE站点可靠性工程师服务治理雪崩熔断隔离降级

题目

考察点：雪崩链路、四种手段的分工、常见误用。服务治理的核心场景题。

参考答案

要点：

  • 雪崩的完整链路（讲清「怎么从局部故障变成全站故障」）：

1. 某个下游（DB、第三方、某服务）变慢而不是直接挂掉；

2. 调用它的服务线程/连接被慢调用占满（这是关键——资源耗尽比故障本身更致命）；

3. 该服务无法处理其他请求 → 它的上游也被占满 → 沿调用链向上逐层扩散；

4. 重试与超时叠加（重试放大流量、超时累积）加速崩溃；

5. 最终全站不可用，且恢复后流量洪峰再次压垮刚重启的系统（需慢启动/预热）。

  • 四种手段的分工（必须说清各自解决哪一环）：

- 超时：最基础、最容易被忽略——没有超时，慢调用会永久占用资源。所有跨进程调用必须显式设置超时，且要分层递减（见网关题）。

- 限流：控制「入口流量」，防止超出系统承载能力。作用在最上游（网关）效果最好。它防的是「请求太多」。

- 熔断：控制「对某个下游的调用」。以错误率/慢调用比例为依据，快速失败（不再真的去调用），给下游留出恢复时间。状态机 CLOSED → OPEN → HALF_OPEN：OPEN 期间直接拒绝；到时间后进入 HALF_OPEN，放少量请求试探，成功则回到 CLOSED，失败则继续 OPEN。关键参数是错误率阈值 + 窗口大小 + 最小请求数 + OPEN 持续时间。它防的是「反复去撞已经坏掉的下游」。

- 隔离（舱壁模式 Bulkhead）：控制「资源边界」——给不同下游分配独立的线程池/信号量/连接池，让「一个下游慢」不会耗尽调用方的全部资源。这是最容易被忽略但最有效的手段：把「共享资源」变成「分舱资源」，故障就被限制在一个舱里。

- 降级：给出「可接受的替代结果」——缓存旧数据、默认值、简化功能、异步兜底。它决定用户体验退化到什么程度，是业务决策而非纯技术配置（谁来定降级内容、什么时候触发、怎么恢复，都要提前约定）。

  • 配合关系（一句话总结）：限流在入口拦住过多请求 → 隔离把资源切成舱避免互相拖累 → 熔断在检测到下游客异常时快速失败 → 超时保证单次调用不会永久占资源 → 降级给用户一个可用的替代结果。缺任何一环，其余手段的效果都大打折扣。
  • 常见误用：① 只加熔断不加隔离——熔断阈值没到之前资源已被耗尽；② 熔断阈值太灵敏导致频繁误熔断（应设最小请求数，避免低流量时因 1 个错误就熔断）；③ 降级返回看似正常但错误的数据（比报错更危险，会污染下游决策）；④ 没有监控熔断状态——熔断器打开必须告警，否则「快速失败」会变成悄悄的业务功能缺失；⑤ 熔断后不做预热直接放全量流量，导致二次崩溃。
  • 落地建议：把「超时 + 熔断 + 隔离 + 降级」做成统一的 RPC 客户端配置模板，和注册中心/配置中心联动，避免每个团队各自为政（Sentinel、Resilience4j、Hystrix 都能承载，Hystrix 已停止新特性开发，新项目选 Sentinel 或 Resilience4j）。
