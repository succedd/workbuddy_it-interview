git rebase 和 git merge 有什么区别？各自适合什么场景？

中级简答题软件开发工程师(通用)前端开发工程师后端开发工程师DevOps工程师rebasemerge提交历史GitFlow

题目

团队中有人用 rebase、有人用 merge，请说明二者对提交历史的差异：rebase 是否会改写提交，merge 会产生什么，分别在什么场景下推荐使用。

参考答案

本质区别：

  • git merge：把两条分支的末端合并，生成一个新的合并提交（merge commit），保留完整分支拓扑，不改动已有提交。
  • git rebase：把当前分支的提交“移植”到目标分支顶端，逐个重新生成新的提交对象（新 hash），形成线性历史，不保留原 merge 结构。
merge 后:        rebase 后:
A---B---C  (topic)   A'---B'---C' (topic)
   /       /            /
D---E---F---G (main) D---E---F---G (main)

适用场景：

  • 用 rebase：把本地、尚未推送的 feature 分支变基到最新 main，得到干净线性历史；git rebase -i 还可整理/合并提交（squash）。只 rebase 自己的私有分支。
  • 用 merge：合并已经公开的分支、需要保留“何时合并”记录时（如 GitFlow 的 release/merge 到 main）。

黄金规则：不要对已经推送到共享仓库的提交做 rebase，否则会改写他人基于旧 hash 的历史，造成协作灾难（他人需 git pull --rebase 或强制解决）。

冲突处理差异：rebase 逐提交重放，可能多次解决同一冲突；merge 一般只解决一次。
