# 国内访问性能诊断与优化说明（2026-10-06）

> 起因：用户反馈 `https://itinterview.com.cn/`「打开很慢」。本文记录完整实测数据、
> 根因判定，以及已落地 / 待落地的优化项。**所有数字均为实测，非估算。**

---

## 一、实测基线（2026-10-06 17:00前后）

| 指标 | 实测值 | 判定 |
|---|---|---|
| 首页 TTFB | **1.1s ~ 6.0s**（6 次采样） | ❌ 极慢 |
| 首页总耗时 | 10s ~ 20s | ❌ 极慢 |
| `data/published.json` 原文 | 2,925,653 字节（2.79MB） | ⚠️ 过大 |
| 同上brotli 后 | 780,153 字节 | 压缩本已生效 |
| Cloudflare 边缘节点 | **恒为 `LAX`（洛杉矶）** | ❌ 绕行美西 |
| 客户端 IP / 归属 | `112.193.82.118` / `loc=CN` | 成都电信，确认在国内 |

### 关于压缩：这里有一个曾被误判的事实

初次用 `curl`（**未声明 `Accept-Encoding`**）测得 `content-length: 2898662`，
且响应头里没有 `content-encoding`，一度判定为「Cloudflare 没给 JSON 开压缩」。
**这是错的。** 补上 `Accept-Encoding: br, gzip` 后实测：

```
Content-Type: application/json
Content-Encoding: br          ← 压缩一直生效
vary: accept-encoding
```

站内 `index.html` / `css/*.css` / `js/*.js` / `data/*.json` / `q/*` **全部已走 brotli**。
所以「开启压缩」这条 P0 建议**无需再做**，真正的问题在下面两条。

## 二、根因一：`/data/*` 从未进边缘缓存（⚠️ **修了一半，结论是走不通**）

### 现象

`/data/published.json` 的 `cf-cache-status` **恒为 `DYNAMIC`**。

### 已做的修复（两处，都已上线）

**① `cloudflare/pages/_worker.js` 新增 `applyDataCache()`**
带 `?v=` 的资源→ `no-cache`（发版才能生效）；
不带 `?v=` 的 `/data/*.json` → `public, max-age=3600`。

**② `sw.js` 把 `cache: "reload"` 换成 `cache: "no-cache"`**

| 写法 | 语义 | 是否回源 |
|---|---|---|
| `reload` | 绕过一切缓存 | **一定回源** |
| `no-cache` | 必须校验，但**允许用缓存响应**（走 304） | 命中时**不回源** |

`no-cache` 保留了「每次校验 → 发版立刻生效」，不再连带击穿边缘缓存。
**这一条是真实有效的修复**，值得保留。

### ⚠️ 但边缘缓存这条路最终没走通（上线后实测结论）

线上三轮实测（每一版都部署后连续5~6 次采样）：

| 版本 | Cache-Control | cf-cache-status |
|---|---|---|
| 第 1 版 | `public, max-age=300, s-maxage=3600` | DYNAMIC ×4 |
| 第 2 版 | `public, max-age=3600, must-revalidate` | DYNAMIC ×5 |
| 第 3 版（当前） | `public, max-age=3600` | DYNAMIC ×6 |

**响应头三次都正确下发了（线上 curl 可见），但 `cf-cache-status` 始终是 `DYNAMIC`。**

对照组说明了原因：
- `css/style.css`（**未经 Worker 改写**）→ `MISS → REVALIDATED`，**能进边缘**
- `/data/*.json`（**经Worker 处理**）→ 恒 `DYNAMIC`

### 结论（别再在这上面花时间）

**Cloudflare Pages「高级模式」（`_worker.js`）下，Worker 处理过的响应不落Cloudflare 边缘缓存。**
这是产品层面的行为，不是配置错误，也不是 Cache-Control 写法的问题——
第 3 版已经去掉了 `must-revalidate`、去掉了无效的 `s-maxage`，仍然 DYNAMIC。

要真正让 `/data/*` 进边缘，只有三条路，都超出本仓库代码范围：
1. **去掉 `_worker.js`**（放弃应用层反爬，换边缘缓存）—— 与项目既有安全策略冲突，不建议；
2. **把数据请求改走 Cloudflare Worker**（而非 Pages 静态资源）—— 架构级改动；
3. **在 zone面板配 Cache Rules** 绕开 Worker —— 需 zone 权限，
   且仓库已记录该令牌无 Zone WAF / Zone Settings 权限（见 `tools/ci/zone-security.py` 注释）。

**因此本次真正生效的优化是第三章的分片（传输量降 84%），
而不是边缘缓存。** 首页 TTFB 优化前后实测均为 1.0~6.5s，未见改善——
因为它由跨太平洋网络延迟主导（见第五章），与缓存无关。

## 三、根因二：单文件 2.79MB 太大（已修复：分片）

### 拆分方案

产物由 `tools/split-published.py --write` 生成（幂等）：

| 文件 | 体积（原文） | 体积（brotli） | 何时拉取 |
|---|---|---|---|
| `data/published.json` | 2.79 MB | 780 KB | 权威快照，**保留不动** |
| `data/manifest.json` | **914 KB** | **123 KB** | 首屏（题目元数据，无答案正文） |
| `data/shards/s00..s05.json` | 1.58 MB | 841 KB（6 片，均 137KB） | 按需（答案正文） |

**首屏传输量：780KB → 123KB，降幅 84%。**

### 三条守住的安全线

1. **写路径一行未改。** `data/published.json` 仍随 Pages 正常发布、
   仍是编辑端发布的唯一目标、`guardAgainstShrink` / `absorbRemote` /
   `verify-publish.py` 的语义完全不变。
2. **任一分片缺失 → 整包回退。** 只要有**任何一片**拉不下来，
   `fetchManifestSnapshot()` 直接返回 `null`，退回整包 `published.json`。
   绝不允许「部分题目 `answer` 为空」的快照进 `applyRemote`——
   那是整包替换本机题库，编辑端还会推回云端，等于用空答案覆盖好答案，
   而且**题数没减少，`guardAgainstShrink` 拦不住**。
3. **版本一致性校验。** manifest 的题数必须与 `data/version.json` 的 `count` 相等，
   不等即视为两者未同步发布，弃用 manifest。

### 验证结果

用 Node 复刻前端合并逻辑，与整包**逐题逐字段**比对：

```
分片拉取: s00=OK(269) s01=OK(260) s02=OK(242) s03=OK(268) s04=OK(283) s05=OK(218)
缺失片: 0
拼回题数: 1540 (整包 1540)
忽略键顺序后的实质差异题数: 0        ← 内容完全等价
题目 id 顺序: 完全一致              ← 列表分页 / 「下一题」不受影响
```

### 涉及的权威比对路径**故意仍用整包**

以下三处保持 `fetchRemote()`（整包），因为它们涉及与云端的权威比对或写回：

| 位置 | 函数 | 原因 |
|---|---|---|
| `cloud.js:521` | `absorbRemote` | 编辑端并集吸收，要与本机逐题比对 |
| `cloud.js:~686` | `guardAgainstShrink` | 发布守卫，必须看到云端真实全量题数 |
| `cloud.js:~744` | `exportAll` | 要把云端 `removedQuestions` 一并写回 |

### 答案懒加载

`js/app.js` 的 `pageQuestionDetail()` 增加：
若题目存在但 `answer` 为空，按题号从对应分片补一次正文再渲染，
并写回本机表（同片其他题下次直接命中）。补齐失败则照常渲染，绝不白屏。

## 三·五、首屏瘦身：把「延迟次数」降下来（2026-10-06 追加，线上 `20261006f`）

### 为什么这条才是真解
前两项（分片、以及边缘缓存的尝试）都在优化「单个请求」，但——
**TTFB 1.0~6.5s 是每个请求都要各付一遍的固定成本**。
首屏要等 46 个资源全部到齐，就等于把这段延迟付了 46 次（浏览器并发，但排队与连接建立仍耗时）。

所以真正的杠杆是：**首屏到底要几个资源？**

### 实测首屏构成（优化前）
| 资源 | gzip | 首屏是否真的需要 |
|---|---|---|
| js/app.js | 110 KB | ✅ 需要 |
| **js/docs/devops.js** | **107 KB** | ❌ 只在点进技术教程时用 |
| **js/docs/java.js** | **88 KB** | ❌ 同上 |
| **js/docs/dba.js** | 85 KB | ❌ 同上 |
| **js/docs/security.js** | 85 KB | ❌ 同上 |
| **js/docs/network.js** | 77 KB | ❌ 同上 |
| **js/docs/frontend.js** | 55 KB | ❌ 同上 |
| **js/docs-data.js** | 50 KB | ❌ 同上（且依赖上面 6 个先挂 window） |
| 其余 39 个 | 约 424 KB | 部分需要 |
| **合计** | **981 KB / 46 个** | |

**技术教程这7 个文件占首屏一半以上，却只在用户点进「学 › 技术教程」时才用到。**

### 改动
- 新增 `js/docs-loader.js`（~1KB）：`requestIdleCallback` 空闲时静默预热；
  用户点进教程时若尚未预热完，`await` 同一个 Promise（不重复请求）
- `index.html` 里 7 个阻塞 `<script>` → 1 个 loader
- `docs.js` 三个页面函数加 `ensureDocs()` 守卫，数据未就绪先加载；失败给「重试」入口
- `sw.js`：这 7 个文件从 `APP_SHELL` 移到运行时 cache-first。
  **留在 APP_SHELL 会让 SW 安装阶段一次性下载全部 547KB**，
  等于从另一条路把刚省掉的又花掉；移到运行时后离线可用性不变。

### 结果
**首屏 46 → 38 个资源、981KB → 438KB（-55%）**，少付 8 次跨太平洋延迟。

### 为什么不用 `<script defer>`
defer 仍会在首屏解析阶段**下载**这些文件（只是不阻塞 HTML 解析），下载开销一分不少。
这里要的是「首屏根本不发起这 7 个请求」。

### 两处主动加固（写端到端测试时发现的风险）
1. **单文件加载超时 8s** —— `onload`/`onerror` 都不触发的情况真实存在（网络挂起、SW 卡住）。
   只等这两个事件会让 `await` 永远挂起，用户点进教程页就一直空白，
   连「加载失败可重试」都出不来。
2. **失败静默期 60s** —— 没有它时弱网用户每次进首页都会在空闲回调里重试
   7 个文件 × 8 秒，越慢越失败、越失败越重试，反而拖慢首页。
   静默期内「用户手动点进教程」仍真重试（`load(force)` 与 `warmup()` 分离）。

### 验证
最小 DOM桩三场景端到端：首屏发起 script 数 0 ✅；触发后 7 个文件顺序正确
（6 方向在前、`docs-data` 在后）✅；全部 error 仍尝试完 7 个 ✅；
全部挂起时超时生效、不死锁 ✅。原有 `tools/validate-docs.js` 仍 `ASSEMBLE_OK`（7 方向 / 101 篇）。

### 还能不能再降？
剩下的 438KB 里，`js/app.js`（110KB）是单文件巨石（5383 行 / 374KB），
已评估过拆分（见 README 2026-10-05 的 P2-7）：需引入模块系统并冒 36 处 script 顺序 +
SW 清单 + 闭包断裂风险，且无 E2E 保护，**当时结论是维持现状**。
若要继续降，下一步应从这里入手，但需配套建 E2E 测试再动。

## 四、根因三：Cloudflare 边缘节点恒为 LAX（**产品限制，需用户决策**）

### 实测证据

```
$ curl https://itinterview.com.cn/cdn-cgi/trace
ip=112.193.82.118      ← 成都电信
loc=CN← 确在中国大陆
colo=LAX              ← 但边缘节点在洛杉矶
warp=off
```

6 次 `CF-RAY` 采样**全部**为 `-LAX`。并且
`curl --noproxy '*'`（强制直连、绕过本机代理）**仍然是 `colo=LAX`**，
排除了「是本机代理导致出口在美国」的可能。

DNS 也正常——`itinterview.com.cn` 解析到 Cloudflare 权威 IP
`104.21.61.147` / `172.67.211.117`，未被人为投毒。

### 结论

**这不是配置错误，是 Cloudflare 免费版的固有限制。**
免费版不启用 China Network，大陆访客不会被调度到就近的境内节点，
而是被分配到任意一个境外节点（本次恒为洛杉矶）。
延迟因此多出约 150~200ms 的跨太平洋往返，
且这部分**无法通过 DNS、代码或 Worker 配置绕开**。

### 可选方案（按性价比排序，均需在 Cloudflare 后台或付费侧操作）

| 方案 | 成本 | 预期效果 | 说明 |
|---|---|---|---|
| **A. Argo Smart Routing** | $5/月 + 用量 | 中~高 | 付费版独有的智能路由，可显著改善跨网质量；一键开启 |
| **B. 启用 China Network** | 企业版 | 高 | 真正的境内节点，但**仅企业版**且需 ICP 备案 |
| **C. 换国内 CDN** | 视供应商 | 高 | 把静态资源推到国内节点（又拍云/七牛等），需改 DNS 接入 |
| **D. 维持现状** | 0 | — | 本次的代码侧优化（分片 84% + 边缘缓存）已把「要传的东西」和「回源次数」都降下来了，体感会明显改善，但底层跨太平洋延迟仍在 |

> **本仓库代码侧已无可优化空间。** 上述 A/B/C 均属账号/计费层面的操作，
> 未经用户确认不擅自执行（涉及付费与 DNS 变更）。

### 发版后必须做的事

`tools/split-published.py` 依赖 `data/published.json`。
**每次发版后都要重新生成分片**，否则 manifest 与题库会不一致
（此时 `fetchManifestSnapshot` 的题数校验会拦下，回退整包——功能不坏，但优化失效）：

```bash
python tools/split-published.py --write
```

建议把这一步加进扩充流水线（与 `_publishInner` 写 `published.json` / `version.json` 同一处）。
