什么场景该把 MySQL 换成 TiDB？迁移时热写入热点问题怎么处理？

高级开放讨论题数据库架构师DBA数据库管理员TiDB技术选型热点AUTO_RANDOM迁移

题目

考察点：选型判断标准、热点 Region 原因、AUTO_RANDOM/SHARD_ROW_ID_BITS、迁移路径。

参考答案

要点：

  • 该换的信号：① 单表数据量到亿级、分库分表带来的跨片查询/扩容痛苦（ShardingSphere 改造成本高）；② 写入量持续增长需要在线水平扩容；③ 需要 HTAP（TP 库+实时分析一份数据，TiFlash 列存副本）；④ 多写多活/强一致容灾诉求。不该换：小数据量、重度依赖存储过程/外键、预算敏感（至少 3 副本起步资源要求高）。
  • 热点问题：单调递增主键（自增/时间）导致写入全打在最后一个 Region——写热点。处理：AUTO_RANDOM 主键（打散）、SHARD_ROW_ID_BITS 打散行、业务键加哈希前缀；索引热点用 ADD INDEX ... INVISIBLE 逐步 + Hot Region 调度。
  • 迁移路径：TiDB Lightning 物理全量导入（TB 级快）+ DM（Data Migration）持续同步 Binlog 增量 → 双跑比对 → 切流；SQL 先过兼容扫描，改掉外键/存储过程依赖。
