MyBatis 分页为什么必须用物理分页？PageHelper 的实现原理和潜在坑是什么？

初级简答题Java后端工程师Java开发工程师后端开发工程师MyBatis分页PageHelper拦截器深分页

题目

考察点：逻辑分页 vs 物理分页、拦截器机制、深分页。这是最容易在生产翻车的点之一。

参考答案

要点：

  • 逻辑分页：SqlSession.selectList(query, rowBounds) 或在内存里 List.subList。做法是把全表数据查出来再截取，数据量一大就是 OOM。性能随总量线性恶化，深分页尤其灾难。
  • 物理分页：改写 SQL 加上 LIMIT ?, ?（MySQL）/ OFFSET ... FETCH NEXT（SQL Server）/ ROWNUM（Oracle），把分页交给数据库，只传输需要的那一页。
  • PageHelper 原理：基于 MyBatis 的 Interceptor 插件机制，拦截 Executor#query。调用 PageHelper.startPage(pageNum, pageSize) 时把分页参数放进 ThreadLocal，拦截器在查询前取出参数，由 SqlUtil 按数据库方言拼接出分页 SQL，并额外执行一条 count 查询得到总数，最后把结果包装成 PageInfo。
  • 三个经典坑：① ThreadLocal 未清理——startPage 之后如果没执行查询（或异常），分页参数会残留，污染下一次查询（这是线上事故高发点）；② startPage 必须紧贴目标查询语句，中间插了别的查询就会错位；③ 深分页 LIMIT 1000000, 20 数据库仍要扫描并丢弃前 100 万行，需改用游标（keyset）分页：WHERE id > lastId ORDER BY id LIMIT 20。
  • 加分点：count SQL 可以被自动优化（去除 order by），也可以 PageHelper.startPage(1, 10, false) 关闭 count 查询以省一次开销。
