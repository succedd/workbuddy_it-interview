FastAPI 中同步 def 与 async def 路由混用会出什么问题？什么情况下反而该用同步？

高级故障排查题Python后端工程师Python开发工程师后端架构师FastAPI异步事件循环阻塞线程池

题目

考察点：事件循环阻塞、线程池调度、异步陷阱。这是异步框架最致命的坑。

参考答案

要点：

  • FastAPI 的调度规则：async def 路由直接在事件循环里跑；def（同步）路由被自动丢到 ThreadPool（默认 anyio 的 40 个线程）里跑。所以两者混用本身不会报错。
  • 致命错误：在 async def 里调用阻塞代码。例如 requests.get()、time.sleep()、同步的 pymysql/psycopg2 查询、CPU 密集的 pandas。这些会阻塞整个事件循环，导致所有并发请求一起卡住——表现是「并发数上来后所有请求都变慢，但 CPU 不高」，非常难排查。
  • 正确姿势：① 用异步库（httpx.AsyncClient、asyncpg、motor、SQLAlchemy 2.0 async）；② 万不得已用 await run_in_threadpool(blocking_fn) 或 asyncio.to_thread() 把阻塞调用挪出循环；③ CPU 密集交给 ProcessPoolExecutor 或独立的 Celery/任务队列。
  • 什么时候故意用同步 def：依赖同步驱动、代码复用存量同步逻辑、或该接口本身 QPS 很低。交给线程池反而简单安全——代价是线程数成为并发上限，40 个线程被打满时新请求要排队。
  • 排查手段：asyncio 的慢回调日志（loop.slow_callback_duration）、压测时观察「并发上升 → P99 断崖式上涨」；或用 py-spy dump 直接看事件循环线程栈里卡在哪个同步调用上。
  • 加分点：启动/关闭事件 lifespan 也必须是 async 友好的；同步依赖同样走线程池，这也是「同步依赖里做重活」被诟病的原因。
