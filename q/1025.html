Pydantic 在 FastAPI 里承担什么角色？从 v1 升级到 v2 有哪些必须注意的变化？

中级简答题Python后端工程师Python开发工程师后端开发工程师FastAPIPydantic数据校验v2迁移OpenAPI

题目

考察点：数据校验/序列化、模型驱动开发、v1→v2 迁移。框架选型与升级实操。

参考答案

要点：

  • 角色（三层）：① 请求校验——把 JSON body 反序列化成模型，类型不符自动返回 422 与结构化错误；② 响应序列化——response_model 决定对外暴露哪些字段（可裁掉密码等敏感字段）、并做类型转换；③ 自动文档——Pydantic 的字段定义/Field(description=...) 直接生成 OpenAPI Schema，Swagger 就是这么来的。此外还用于配置管理（pydantic-settings）与内部 DTO。
  • v2 的核心变化：

- 内核重写为 Rust（pydantic-core），校验速度提升数倍，这是最大卖点；

- validator → field_validator、root_validator → model_validator，且默认是 mode='after'，要前置校验得写 mode='before'；

- Config 内部类 → model_config = ConfigDict(...)；

- orm_mode → from_attributes=True（配合 v2 才用 .model_validate(obj) 读 ORM 对象）；

- .dict()/.json() → .model_dump()/.model_dump_json()；parse_obj → model_validate；

- Optional[X] 语义收紧：v1 里 Optional 隐含「非必填」，v2 中类型可空与字段必填是两件事，必填要显式 Field(...)，否则会出现「少了字段不再报错」的隐患；

- pydantic-settings 拆成独立包，BaseSettings 不再在 pydantic 主包。

  • 迁移建议：用官方 bump-pydantic 脚本批量改写，但回归测试必须重跑——最常踩的是 Optional 语义变化和 field_validator 的作用模式差异，这两处会静默改变校验行为。
