Node.js 单进程只能用一个 CPU 核心，Express 服务该怎么用满多核？cluster 有哪些坑？

高级场景题Node.js工程师后端开发工程师后端架构师Expresscluster多核优雅重启Node.js

题目

考察点：多进程模型、cluster 负载均衡、共享状态、优雅重启。Node 生产部署必考。

参考答案

要点：

  • 问题本质：Node 的 JS 执行是单线程的，一个进程只能吃满一个核。8 核机器上单进程 Express 只能用到约 1/8 的算力，且一个致命错误会带走整个服务。
  • cluster 模块：主进程（primary）用 cluster.fork() 派生多个 worker，共享同一个监听端口。默认策略是 Round-Robin（cluster.SCHED_RR，由主进程分发连接），在 Linux 上比交由内核抢占（SCHED_NONE）更均衡，能缓解「连接分布不均导致某些 worker 忙死」。
  • 生产替代方案：pm2 -i max（内部也是 cluster）或直接用容器编排——每容器一进程，由 K8s/HPA 扩副本，这比单机多进程更符合云原生思路（隔离性、滚动更新都更好）。
  • 核心坑：

- 端口冲突：worker 都 listen 同一端口是允许的（cluster 内部做了处理），但在 cluster 外自己再起进程会 EADDRINUSE；

- 内存不共享：多进程意味着内存里的 session/限流计数/cache 各存各的，多副本下会不一致——必须外置到 Redis；

- 定时任务重复执行：每个 worker 都会跑 setInterval，导致任务被执行 N 次，需要分布式锁或把定时任务独立成进程；

- 滚动重启：cluster 支持零停机重启——逐个 worker.disconnect()（先停止接收新连接、等存量请求处理完）再 fork 新的，不能所有 worker 一起杀；

- worker 崩溃不自动重启：必须监听 exit 事件主动 fork，且要防止崩溃风暴（异常启动即崩 → 无限 fork，需加退避与最大重启次数）。

  • 加分点：worker.send()/process.send() 做进程间通信；cluster.isPrimary 区分角色（旧版为 isMaster）。
