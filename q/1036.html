GraphQL 接口怎么防止恶意深度查询和复杂度攻击？有哪些可落地的限流手段？

高级场景题后端开发工程师后端架构师安全开发工程师GraphQL安全复杂度分析深度限制持久化查询

题目

考察点：查询复杂度分析、深度限制、超时与持久化查询。安全类必考。

参考答案

要点：

  • 攻击面为什么比 REST 大：单个 endpoint 的响应体积和计算量不可预估——客户端可以自由组合嵌套、别名、循环查询。典型攻击：① 深度嵌套（user { friends { friends { ... } } }）；② 别名炸弹：同一字段用不同别名重复请求上百次，绕过「字段级」限制；③ 批量爆破：用 alias 在一个请求里尝试多个登录组合，绕过基于请求数的限流；④ 高代价字段（聚合、模糊搜索、大文件导出）被低成本组合调用。
  • 可落地的五道防线：

1. 深度限制（Depth Limit）：如 graphql-depth-limit 限制最大深度 5–10 层，超限直接拒绝；

2. 复杂度分析（Complexity / Cost Analysis）：给字段标权重，乘上列表的 first/last 参数（这才是关键——comments(first: 10000) 要用分页参数放大代价），总成本超阈值拒绝；graphql-cost-analysis、Apollo 的 cost 指令可落地；

3. 强制分页上限：first 之类参数设 max 校验（如 ≤100），并在 schema 层用 connection 模式统一分页；

4. 超时与深度熔断：resolver 级超时 + 整请求超时；对反复超限的 IP/用户熔断；

5. 持久化查询（Persisted Queries）：客户端只允许发送已登记的查询哈希（APQ），从根本上关闭「任意查询」——生产环境的白名单是性价比最高的方案。

  • 额外加固：关闭生产环境 introspection 与 playground（减少信息泄露面）；对写操作（mutation）单独限额；@skip/@include 与 fragment 展开后的实际规模要在展开后再估算复杂度，否则会被 fragment 绕过。
  • 加分点：Apollo Router / GraphQL Mesh 等网关层可以统一挂深度限制与成本分析，避免每个子图重复实现；对 alias 数量单独设上限能直接掐掉别名炸弹。
