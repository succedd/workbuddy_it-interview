GraphQL 真的「不需要版本」吗？Schema 该怎么演进才能不破坏现有客户端？

中级开放讨论题后端架构师后端开发工程师前端架构师GraphQLSchema演进兼容性deprecatedAPI设计

题目

考察点：无版本化理念的边界、schema 演进纪律、破坏性变更识别。设计类题。

参考答案

要点：

  • 理念来源：GraphQL 的设计是「按字段按需获取」，客户端只声明自己要什么字段。所以新增字段不会影响任何老客户端（它不请求就收不到，也不会有多余数据）——加字段天然向后兼容，这是「无版本」这一说法的底气。REST 里加字段也可能影响反序列化严格的客户端，GraphQL 从协议层规避了。
  • 但「无版本」≠ 可以随便改。以下都是破坏性变更（breaking change）：删除字段/类型/枚举值、字段类型变更（如 String → Int）、非空性收紧（String → String!，会让老查询因缺值直接报错）、把字段设为必填参数、参数类型变更、改字段语义但保留名字（最危险，客户端不会报错却拿到错误含义的数据）。
  • 正确演进姿势：

1. 先加后弃（Additive then Deprecate）：新字段加进去、老字段标 @deprecated(reason: "...") 并在文档中给出替代，graphql-inspector / Apollo Studio 的 schema check 会在 CI 里自动拦截破坏性变更；

2. 观察真实使用量再删：靠 Apollo 的 field usage 统计确认「没有任何客户端在请求了」才删，不要靠猜；

3. 需要改变语义时：新建字段名（如 priceV2）而不是复用旧名；

4. 用 @deprecated 的 reason 传达迁移窗口，配合 changelog 通知调用方。

  • 什么时候确实需要版本：① 出现根本性领域模型重构（旧 schema 无法平滑过渡）；② 合规要求物理隔离旧接口。此时更实用的做法是在网关层暴露 /graphql/v2，或用 schema 联合（Apollo Federation）把新旧子图并行一段过渡期。
  • 配套纪律：schema 必须进版本控制并做 CI 校验（schema registry）；客户端尽量用 fragment + codegen 生成类型，这样字段被弃用时编译期就能发现，而不是等线上报错。
