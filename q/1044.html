Core Web Vitals 的三个指标（LCP / INP / CLS）分别衡量什么？各自怎么优化？

中级简答题前端开发工程师前端架构师性能优化Core Web VitalsLCPINPCLS

题目

考察点：真实用户体验指标、优化手段与指标之间的取舍。性能优化从「感觉快」到「可量化」必备。

参考答案

要点：

  • LCP（Largest Contentful Paint，最大内容绘制）：衡量加载性能，指视口内最大元素渲染完成的时间。良好阈值 ≤2.5s。优化手段：

- 资源优先级：首屏关键图用 <link rel="preload">、给 LCP 图片加 fetchpriority="high"，不要对它用 loading="lazy"（会把 LCP 推迟到滚动后，这是最常见的自伤）；

- 减少服务端时间：TTFB 是 LCP 的下界，靠 CDN、缓存、后端优化压下去；

- 消除渲染阻塞：CSS 内联关键部分、JS 用 defer/async、字体用 font-display: swap 并 preconnect 字体域；

- 图片尺寸合适（避免用 4000px 原图当缩略图）、优先 AVIF/WebP。

  • INP（Interaction to Next Paint，交互到下次绘制）：2024 年起取代 FID，衡量整页交互响应性（取交互延迟的高分位）。良好阈值 ≤200ms。优化手段：拆分长任务（scheduler.postTask/setTimeout 切片）、把重计算挪进 Web Worker、避免布局抖动（读写分离，先批量读再批量写）、事件处理用防抖/节流、减少 hydration 与主线程竞争。
  • CLS（Cumulative Layout Shift，累积布局偏移）：衡量视觉稳定性，良好阈值 ≤0.1。优化手段：给图片/视频/iframe/广告位预留尺寸（width/height 或 aspect-ratio）、字体加载不跳变（size-adjust 或匹配 fallback 字体度量）、不要在已有内容上方动态插入（banner、提示条），非得插入就用 transform 从已占位元素里滑出。
  • 指标间的取舍要讲清：懒加载能省带宽但会推迟 LCP；预加载能救 LCP 但与关键资源抢带宽（需排优先级）；把首屏图片转成占位色块能压 CLS 但可能加大 LCP。所以优化顺序是先量化再动手——用 CrUX/PageSpeed 看是哪个指标不达标，别盲目全局优化。
  • 落地方法：PerformanceObserver 采集 LCP/CLS/INP 上报（web-vitals 库最省事），按设备/网络/页面维度分桶看 P75——因为 Chrome 的评分标准就是 P75，平均值会被少数慢样本掩盖真实分布。
