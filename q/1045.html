首屏加载优化中，懒加载、预加载与 HTTP 缓存策略该怎么组合才不互相打架？

高级场景题前端开发工程师前端架构师性能优化懒加载预加载HTTP缓存资源优先级

题目

考察点：资源优先级、缓存语义、指标导向的组合策略。考察是否真的理解优先级机制。

参考答案

要点：

  • 先分清三件事的职责：懒加载决定「什么时候取」；预加载决定「提前取什么、优先级多高」；HTTP 缓存决定「要不要取、取几时的新版本」。三者都作用在「网络层面」，冲突点全在优先级与带宽竞争。
  • 分层组合策略（按视口内外划分）：

- 视口内（关键路径）：关键 CSS 内联、关键图 preload + fetchpriority="high"、字体 preconnect，绝不用 lazy；

- 视口外/进视口才需要：图片 loading="lazy" + decoding="async"，列表/组件用 IntersectionObserver 或 React.lazy + Suspense 按需加载；

- 可预期的下一跳（详情页、下一页）：<link rel="prefetch"> 或 hover/可视区停留时预取——预取要设预算（并发数、总字节），否则会和关键请求抢带宽，把 LCP 拖慢（典型的「优化了跳转速度、牺牲了首屏」）。

  • HTTP 缓存配合（关键）：

- 带 hash 的静态资源（app.abc123.js）：Cache-Control: public, max-age=31536000, immutable，彻底长效缓存，靠文件名变化失效；

- HTML 入口：Cache-Control: no-cache（允许缓存但每次校验，不是不缓存），保证发版即生效；

- 接口数据：短 max-age + stale-while-revalidate 兼顾速度与新鲜度；ETag/Last-Modified 支持 304 省流量。

  • 常见的互相打架：

1. 给 LCP 图加了 loading="lazy" → 直接违反 LCP 优化；

2. prefetch 写太多 → 抢占带宽，首屏反而更慢；

3. HTML 也设了长效强缓存 → 发了新版用户拿到的还是旧 HTML，连带引用的旧 JS（这也解释了为什么「改了代码用户没生效」常见于入口 HTML 缓存配置错误）；

4. 预加载的资源与实际用到的 URL 不一致（带参数/域名不同）→ 预加载白做功且控制台报警告。

  • 验证方式：Chrome DevTools 的 Network 面板按 Priority 排序看真实优先级；Performance 面板看 LCP 元素与资源瀑布图；Coverage 面板看未使用代码比例；线上用 PerformanceObserver 分别上报「懒加载命中时间」与 LCP，确认优化真的转移到了指标上。
