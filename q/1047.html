微前端方案（iframe / qiankun / Module Federation / Web Components）该怎么选？各自的真实代价是什么？

中级开放讨论题前端架构师前端开发工程师技术经理微前端qiankunModuleFederationiframe选型

题目

考察点：方案对比、隔离性 vs 性能 vs 改造成本。架构选型题，最忌只说优点。

参考答案

要点：

  • iframe：

- 优势：天然最强隔离（JS、CSS、路由、全局变量全隔离），改造成本≈0，子应用可任意技术栈；

- 代价：性能与体验差（每个 iframe 独立上下文，白屏、内存占用高）、通信只能靠 postMessage（异步、复杂）、弹窗/遮罩无法跨 iframe（Modal 会被限制在 iframe 内）、SEO 与路由同步困难、登录态与 Cookie 跨域问题。

- 适用：内部系统、老系统集成、安全隔离要求高（如第三方页面），不适合面向 C 端的高体验场景。

  • qiankun（微前端框架，基于 single-spa）：

- 优势：JS 沙箱 + 样式隔离 + 资源预加载开箱可用；子应用接入成本低（导出生命周期函数即可）；生态成熟、国内文档多；

- 代价：沙箱靠 Proxy + 快照模拟，无法 100% 隔离（document 级操作、window 上的原生事件、全局 CSS 变量的污染都可能漏出）；样式隔离在「子应用用全局样式覆盖」场景很容易破功；主子应用版本耦合（框架版本、公共依赖各自打包，体积翻倍）；主子应用共享状态需要额外设计。

- 适用：多个团队维护多个技术栈不同的中后台/管理端。

  • Module Federation（Webpack 5 / Rspack / Vite 插件）：

- 优势：运行时模块共享——公共依赖只加载一份，体积与性能最好，天然支持独立构建独立部署；

- 代价：必须统一构建工具与共享库版本（React 18 与 17 混用会直接崩），强约束技术栈；共享依赖版本冲突、singleton 配置不当会出现「一个页面两个 React 实例」；本地开发调试需要对方环境可用（否则得配 mock）；

- 适用：同技术栈、同框架大版本、追求性能与依赖复用的前端平台化场景。

  • Web Components：标准、无框架依赖、隔离性靠 Shadow DOM 较好，但生态与状态管理成熟度低，与 React 组合需要包装层，实际落地案例少。
  • 选型判断（按优先级）：

1. 为什么要微前端？ 如果是「一个团队几个页面」→ 单体 + 模块化就够了（微前端是组织问题的解药，不是技术问题的万能药）；

2. 技术栈是否统一 → 统一优先 MF；不统一选 qiankun；

3. 隔离要求有多高 → 极高选 iframe；

4. 必须提前设计的三件事：路由归属（谁是主、主子路由如何拼接与回退）、共享状态与鉴权（token 放主应用还是各自维护）、公共依赖与样式规范（设计 token 与全局样式归主应用）。

  • 共同坑：产物体积重复、样式污染、window 全局污染、主子应用版本不一致导致的诡异 bug——没有哪套方案能免掉这四条，差别只在是否需要你手工解决。
