微前端架构下，主子应用的路由与共享状态该怎么设计？token 放哪一层？

高级系统设计题前端架构师前端开发工程师技术经理微前端路由状态管理鉴权架构设计

题目

考察点：路由归属、状态边界、鉴权收敛。落地微前端最容易返工的部分。

参考答案

要点：

  • 路由归属的三种模式：

1. 主应用统一路由（推荐）：主应用持有路由表并决定「哪条前缀激活哪个子应用」。浏览器地址栏由主应用或子应用单侧负责（谁改谁负责，绝不能双方都改，否则出现无限重定向）。激活规则要避免重叠前缀（/user 与 /user-center 会同时命中）。

2. 子应用自治路由（主应用只给前缀）：子应用内部用自己的 router，主应用只负责「进入/离开」。优点是子应用可独立开发调试；代价是 主应用无法感知子应用内部页面（埋点、面包屑、权限拦截都要额外接口）。

3. 浏览器路由 vs 内存路由：微前端里常用 base 前缀 + history 模式；如果子应用嵌在弹窗/Tab 内而非独占地址栏，则用 memory 路由，避免污染地址栏。

  • 路由的三个必解问题：① 子应用内跳转如何不出前缀（路由 base 必须与激活前缀一致，否则刷新 404）；② 跨子应用跳转要通过主应用提供的 navigate API，而不是硬写 location.href；③ 刷新/直达深链必须能正确激活对应子应用（激活规则要能匹配任意深度的子路径）。
  • 共享状态的分层原则：

- 只共享「跨应用且低频」的东西：用户信息、权限、主题、全局配置、当前选中的租户。不共享业务领域状态（订单列表、表单草稿）——那属于子应用自己的边界，共享只会造成耦合。

- 实现方式：① 主应用提供 props/上下文（qiankun 的 initGlobalState、Single-SPA 的 props）——简单直接；② 发布订阅事件总线——解耦但要防「事件满天飞、难以追踪」；③ URL 作为状态载体（查询参数）——最利于分享与刷新还原；④ 统一状态库（pinia/redux）+ 外部存储——跨构建的资源共享成本高，慎用。

  • token / 鉴权该放哪：收敛到主应用。理由：① 子应用各自维护 token 会出现刷新时机不一致、过期处理重复；② 主应用统一在请求层（axios 拦截器）注入 token 与处理 401 跳登录，子应用无需关心；③ 权限校验放在主应用的路由守卫 + 子应用的能力查询接口两层——主应用管「能不能进这个子应用」，子应用管「页面内按钮级权限」。
  • 落地契约（强烈建议写进文档）：主子通信接口（props 结构）、路由前缀表、共享依赖清单与版本、全局样式与设计 token 归属、事件命名规范、以及子应用禁止事项清单（不得改 document.title 之外的全局、不得引全局 CSS、不得自行跳转）。微前端的成败八成在契约，不在框架。
