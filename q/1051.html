Webpack 的 Loader 和 Plugin 有什么区别？写一个自定义 Loader 要注意什么？

中级简答题前端开发工程师前端架构师WebpackLoaderPlugin构建工具源码

题目

考察点：职责边界、执行时机、职责链与异步处理。基础但常被答得含糊。

参考答案

要点：

  • Loader：处理「单个文件模块」的转换。它在模块加载时对源文件做「输入源码 → 输出源码」的纯转换（ts→js、scss→css、图片→URL/base64）。特征：

- 在 module.rules 里按 test 匹配，从右到左 / 从下到上链式执行（use: ['style-loader','css-loader','sass-loader']，实际先 sass → css → style）；

- 必须返回字符串或 Buffer（或用 this.callback(null, content, map)）；

- Loader 是管道的一环，不应有副作用（不写文件、不发请求），也不该关心「什么时候构建完成」。

  • Plugin：干预「整个构建流程」。它注册在 compiler 的钩子（hooks）上——compilation、emit、done、optimizeChunks 等，可以读写产物、拆分 chunk、生成 HTML、注入变量、做资源分析。特征：

- 是一个带 apply(compiler) 方法的类/函数；

- 能访问 Compilation 对象（整个模块图、chunks、assets），拥有全局视野；

- 可以有副作用（compilation.emitAsset 写文件、compiler.hooks.done 里上报统计）。

  • 一句话区分：Loader 是「文件级、转换、链式、无全局视野」；Plugin 是「构建级、监听钩子、可操作产物、有全局视野」。
  • 写自定义 Loader 的注意点：

1. 必须处理异步：用 this.async() 返回 callback，或直接返回 Promise；忘记异步化会让构建结果错乱（尤其涉及读文件、网络）；

2. 必须考虑是否走缓存：this.cacheable(true)（默认 true），有外部依赖时要 this.addDependency(file)，否则改配置文件不会触发重建（经典 bug）；

3. 源码要透传 Source Map：用 this.callback(null, code, map) 传下去，否则调试断点全错位；

4. 取参数用 this.getOptions(schema)（Webpack 5），并 提供 JSON Schema 做校验——参数写错要在构建期报错而不是运行时静默；

5. 别自己拼字符串做语法转换：优先用 babel/swc 等成熟解析器 + AST，正则替换必然在边界情况翻车；

6. this.resourcePath / this.query / loader-utils 是常用上下文；pitch 阶段的 Loader 能「提前返回」从而短路后续 loader（style-loader 的注入就用了这思路）；

7. 用 this.getLogger() 输出日志，别用 console.log（会污染构建输出且可能被并发交错）。

  • 加分点：Webpack 5 的 LoaderContext 支持 getOptions + schema；多个 Loader 串联时成本叠加，能用 rule.include/exclude 缩小范围就别省那行配置（babel-loader 误处理 node_modules 是构建慢的头号原因）。
