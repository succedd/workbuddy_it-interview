Webpack 产物名里的 hash、chunkhash、contenthash 有什么区别？怎么做才能让缓存收益最大化？

中级简答题前端开发工程师前端架构师DevOps工程师Webpackhashcontenthash缓存splitChunks

题目

考察点：三种 hash 的粒度、缓存失效策略、与 CI/CD 的配合。发版缓存问题的核心。

参考答案

要点：

  • 三种 hash 的粒度：

- hash：整个 compilation 级别。项目里任何一个文件变了，所有产物的文件名都变 → 全量缓存失效。对缓存策略基本是反效果。

- chunkhash：按 chunk（入口/异步 chunk）。同一个 chunk 内容变化只影响自己 → 比 hash 好很多。但问题在于：一个 chunk 里包含多个模块（如 JS 里内联了 CSS、或 runtime 包含 chunk 映射表），模块变化会导致整 chunk 重新哈希；更麻烦的是入口 chunk 里常混入 runtime 代码，runtime 里含 chunk 映射表，导致「改了异步 chunk，入口也跟着变」。

- contenthash：按文件内容计算，粒度最细，最稳定。CSS 提取后尤其必要——如果 JS 用了 chunkhash，改一行 JS 会让同一 chunk 里被提取的 CSS 也换名。这是推荐做法。

  • 最佳实践配套：

1. optimization.runtimeChunk: 'single'：把 runtime（模块清单、chunk 映射）单独抽成一个 chunk，避免它变化导致所有入口失效；

2. optimization.splitChunks：把第三方依赖（node_modules）拆成 vendor chunk——依赖不变就不换名，用户长期命中缓存；业务代码单独一份；

3. moduleIds: 'deterministic' / chunkIds: 'deterministic'（Webpack 5 默认）：用稳定的短 ID替代数字 ID，避免「新增一个模块导致后面所有模块 ID 位移、全量重哈希」；

4. CSS 用 MiniCssExtractPlugin 的 [contenthash]；图片/字体同理；

5. HTML 入口不要强缓存（no-cache 或短 max-age），让它引用新文件名；

6. output.filename 与 output.chunkFilename 都要带 contenthash（异步 chunk 容易被漏配）。

  • 验证方式（很重要）：改一行业务代码重新构建，对比产物文件名——理想结果只有「业务 chunk + runtime」发生变化；如果只有 vendor 也变了，说明 moduleIds 不稳定；如果全都变了，说明还在用 hash 或 runtime 混在入口里。
  • 常见误区：① 用 [hash] 以为能省事，实际每次全量失效；② 没有抽出 runtime，导致加一个新页面就全量失效；③ 把 splitChunks 拆得过细（几十个 chunk），请求数增加抵消缓存收益——按「变化频率」分组才是原则：依赖（很少变）/ 业务（常变）/ 运行时（每次构建都可能变）。
