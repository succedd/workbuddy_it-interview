Vite 开发时用原生 ESM，为什么生产构建还要换回 Rollup？

中级简答题前端开发工程师前端架构师ViteRollupesbuild构建TreeShaking

题目

考察点：dev 与 build 的取舍、ESM 的请求风暴、Rollup 的产物质量。理解 Vite 的设计权衡。

参考答案

要点：

  • dev 为什么能用原生 ESM：省掉打包步骤，按需编译——浏览器请求哪个模块才编译哪个，所以冷启动与 HMR 都是毫秒级（不与项目规模成正比，这是相对 Webpack 的最大优势）。配合 esbuild 做 TS/JSX 转换（Go 实现，比 babel 快一到两个数量级）与依赖预构建（把 CJS 依赖转成 ESM，并把 lodash-es 那种「几百个小文件」的包合并成单文件，避免请求风暴）。
  • 为什么生产不能这样交付：

1. 请求数爆炸：一个中型应用有上千个模块，原生 ESM 会发出上千次请求（HTTP/1.1 下更糟；HTTP/2 也扛不住深层依赖瀑布）。生产用户在网络上的往返延迟会把这点优势彻底抹掉；

2. 没有产物优化：原生 ESM 无法做 Tree Shaking、死代码消除、作用域提升（Scope Hoisting）、code splitting、CSS 提取、资源内联与压缩——这些都需要全局的模块图分析，必须打包；

3. CJS/UMD 依赖兼容：很多 npm 包仍是 CJS，浏览器不能直接执行，生产必须靠打包器统一处理；

4. 浏览器差异与缓存粒度：文件粒度的模块缓存虽好，但会让版本管理与失效控制变复杂，打包成少量 chunk 更好控制。

  • 为什么选 Rollup 而不是 esbuild：

- Rollup 的 Tree Shaking 与产物质量是生态标杆——输出更干净、Scope Hoisting 更彻底，长期是库构建的首选；

- esbuild 极快但功能取舍激进：对某些 CJS/特殊语法、装饰器、以及代码分割与 CSS 处理的完善度不如 Rollup 生态，插件生态也薄；

- Vite 的策略是各取所长：dev 用 esbuild 换速度（不被功能细节拖累），build 用 Rollup 换产物质量与插件兼容（这也是为什么 Vite 的插件 API 大量沿用 Rollup 的钩子——插件能在两边复用）。

  • 演进补充：Vite 5/6 引入 Rolldown（Rust 版 Rollup） 的目标就是「用 Rust 的速度提供 Rollup 的产物质量」，逐步统一 dev 与 build 的底层；当前早期版本与 Rollup 的兼容性仍在补齐（部分 Rollup 插件需要适配），生产引入要评估。
  • 回答时要点出本质：dev 的最优目标是「快」（启动/HMR），business 无需打包；build 的最优目标是「小而稳」（体积/兼容/缓存），必须全局分析。 两者目标不同，用同一套策略一定是妥协，Vite 选择分别优化。
