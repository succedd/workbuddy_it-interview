Vite 的 HMR 为什么比 Webpack 更精准？它的实现机制是什么？

中级简答题前端开发工程师前端架构师ViteHMR模块图开发体验ESM

题目

考察点：模块粒度、import.meta.hot、运行时边界。开发体验背后的原理。

参考答案

要点：

  • 根本差异来自模块模式：dev 下 Vite 不打包，模块天然是独立文件、独立 URL，所以「文件 → 模块」是一一对应的，改动哪个文件就能精确知道要更新哪个模块 URL。Webpack 需要重新构建受影响的 chunk，粒度是 chunk 而非模块，边界判断更粗。
  • 完整链路：

1. 文件变更 → Vite 用 chokidar 监听（并要求开发者用原生文件系统事件，容器/NFS 挂载下需退回轮询 usePolling）；

2. 模块图（Module Graph）：Vite 在内存里维护两张图——moduleGraph（模块 ↔ 文件的导入关系）与 transformResult 缓存，能反向查导入者（importers）；

3. 确定边界：从变更模块沿 importers 向上查找最近一个「自接受（self-accepting）」模块——即调用过 import.meta.hot.accept() 的模块；

4. 只失效这一条链：使该模块及其上游被接受边界以下的模块失效（不影响其他分支）；

5. 通过 WebSocket 推送「更新的模块 URL + 时间戳」，浏览器用带时间戳 query 重新请求该模块（/src/foo.vue?t=1699... 打破 HTTP 缓存）并替换；

6. 若无边界，则 hmr.invalidate() → 整页刷新（full-reload）。

  • 为什么更精准：

- 模块级粒度：只失效必要的一条依赖链，不重编译其他模块（Webpack 需重新构建 chunk）；

- explorer 用浏览器原生 ESM：更新即「重新请求一个 URL」，无需运行时打补丁到 chunk；

- 框架插件定义了高质量边界：@vitejs/plugin-vue 让 .vue 文件自接受并做组件级替换（保留 state 的部分在 vue HMR runtime 里处理）；React 走 @vitejs/plugin-react（Babel，支持 Fast Refresh）或 plugin-react-swc。

  • 常用 API：import.meta.hot.accept(cb)（自接受）、accept(['./dep'], cb)（接受依赖）、dispose(cb)（清理副作用，如清除定时器/事件监听，不清理会内存泄漏）、invalidate()（主动升级为整页刷新）、prune(cb)（模块不再被导入时清理）、import.meta.hot.data（跨更新共享数据）。
  • 为什么有时还是整页刷新：改动文件没有任何自接受边界（工具函数、常量、store）；改了 vite.config 或环境变量（需重启）；插件未正确标注边界；或在 optimizeDeps 里的依赖被改（需重新预构建）。
  • 对比补充：Webpack 5 的 HMR 也有模块级 accept 机制，差距主要在于「是否重新打包」与 ESM 原生请求带来的粒度优势，以及 Vite 依赖图反向查找更轻量。
