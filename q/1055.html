Vite 的插件体系和 Webpack 的有什么本质不同？写一个兼容两端的 Vite 插件要注意什么？

高级简答题前端架构师前端开发工程师Vite插件Rollup钩子unplugin

题目

考察点：插件钩子模型、Rollup 兼容层、dev/build 双环境差异。进阶必备。

参考答案

要点：

  • 本质不同：

- Webpack 插件面向构建流程，作用于 compiler/compilation 钩子（emit、optimizeChunks），能操作产物与模块图，但没有「按文件转换」这一层（那是 Loader 的职责）。插件与 Loader 是两套机制，需要分别实现。

- Vite 插件是「Rollup 插件 + Vite 扩展」，一套机制同时承担 Loader 与 Plugin 的角色：靠 transform(code, id) 做文件转换（等价 Loader），靠 buildStart/generateBundle 等钩子做构建干预（等价 Plugin）。这是最核心的区别：Vite 用一个钩子模型统一了 Webpack 的两层概念。

  • Vite 插件独有（Rollup 没有）的钩子（都以 vite 前缀命名，用来区分环境）：

- config / configResolved：修改或读取最终配置；

- configureServer：拿到 dev server 实例，可加中间件（写 mock 接口、代理）；

- transformIndexHtml：改 HTML（Webpack 里要靠 html-webpack-plugin，Vite 内建）；

- handleHotUpdate：自定义 HMR 行为（如 .md 文件变化时更新多个模块）；

- load / resolveId / transform：与 Rollup 同名，但 Vite 在 dev 与 build 都会调用。

  • 关键约束：同一个插件要跑在 dev（ESM 直出、无打包）与 build（Rollup）两个环境，所以要特别注意：

1. 用 apply: 'serve' | 'build' 明确作用环境，否则 dev-only 的钩子在 build 时报错；

2. enforce: 'pre' | 'post' 控制插件顺序（比 transform 的默认中间位置更需要显式声明）

3. 不要假设「文件一定被合并/打包」：dev 下模块各自独立、URL 带 ?t= 查询串，id 里可能带 query，必须剥离 ? 后再判断扩展名——这是 Vite 插件的头号坑；

4. dev 下不要返回 CJS 代码（浏览器不能执行），要返回 ESM；

5. 虚拟模块（virtual module）：约定 id 加 \0 前缀并在 resolveId 里处理，load 里返回内容——两环境行为要保持一致；

6. HMR 要显式声明：只有 handleHotUpdate 或框架插件会做，普通 transform 插件改了文件会退化为整页刷新；

7. 构建产物用 generateBundle/writeBundle，不要用 Node 的文件读写去改 dist（Vite 的产物在内存中流转）。

  • 加分点：插件可以 export default 函数（接收 options）或数组（一个插件包拆成多个插件，configResolved 里做状态共享）；跨环境共享配置用 configResolved 里记录的 config.command === 'serve' 判断；想同时支持 Webpack 与 Vite 时，建议写两套薄适配层（各自调同一个核心实现），而不是硬造统一抽象——生态里 unplugin 就是为此而生，它把「Vite/Webpack/Rollup/esbuild」四端的适配封装好了，新插件优先基于 unplugin 起步可以省掉 80% 的适配工作。
