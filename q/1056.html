Next.js 的 SSR / SSG / ISR / CSR 四种渲染模式怎么选？判断依据是什么？

中级简答题前端开发工程师Web全栈工程师前端架构师Next.jsSSRSSGISR渲染模式

题目

考察点：渲染模式与数据特性匹配、性能与新鲜度取舍。App Router 时代的核心选择。

参考答案

要点：

  • 四种模式速览（App Router 语义）：

- SSG / 静态（默认）：构建时渲染，产物是静态 HTML，最快、最省。适用于内容不变或低频变化的页面（文档、博客、营销页、商品详情在多数场景也可）。

- ISR（增量静态再生）：静态 + 定时/按需更新。export const revalidate = 60 表示「最多 60 秒后过期，下次请求触发后台重建，先返回旧内容（stale-while-revalidate）」。这是电商列表类页面性价比最高的选择。

- SSR（服务端渲染）：每个请求都即时渲染。适合强个性化或实时性要求高的页面——用户中心、订单详情、依赖登录态与实时库存/价格；用 cookies()/headers() 访问请求数据会自动让路由进入动态渲染。

- CSR（客户端渲染）：组件标 'use client'，数据在浏览器里取。适合交互密集、依赖浏览器 API、无需 SEO 的部分——仪表盘图表、编辑器、实时通知、用户输入后的二次查询。

  • 判断依据（按顺序问四个问题）：

1. 需要 SEO / 首屏内容可见吗？ 不需要 → 可以 CSR（最省服务端成本）；需要 → 往下。

2. 内容对每个用户不同吗？ 相同 → SSG/ISR；不同 → SSR。

3. 内容新鲜度要求多高？ 分钟级容错 → ISR；秒级/强一致 → SSR。

4. 页面内是不是有混合需求？ 现代答案是混合：外层 SSG/ISR 的静态骨架 + 内部一个小范围 'use client' 组件做动态部分（Streaming + Suspense 让静态部分先出、动态部分后补）。不要为一个小区域把整页降级为 SSR。

  • 实践要点与坑：

- ISR 的「陈旧窗口」：revalidate 期间用户会看到旧数据，业务能接受才用；需要「发布即生效」用 On-Demand Revalidation（revalidatePath/revalidateTag）配合后台钩子主动失效；

- 动态渲染的传染性：一个组件用了 cookies()、no-store 的 fetch 或 dynamic = 'force-dynamic'，会让整个路由变为动态，静态化收益全丢——排查性能问题时先查这条；

- export const dynamic/revalidate 是路由段配置，粒度是页面/布局级，不是组件级；

- SSR ≠ 更好的性能：TTFB 取决于服务端渲染耗时，服务端数据请求慢会让首字节更慢，有时不如静态 + 客户端补数据（需按实测决定）；

- 自托管时注意：ISR 依赖持久化的缓存存储与共享文件系统，多实例部署必须有共享缓存（Redis/S3），否则各实例数据不一致。
