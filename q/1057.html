Next.js App Router 的缓存有哪几层？为什么「改了数据页面没变」？怎么正确失效？

高级故障排查题前端开发工程师Web全栈工程师前端架构师Next.js缓存revalidateTagDataCacheAppRouter

题目

考察点：四层缓存、缓存交互、失效手段。Next.js 最容易被吐槽、也最容易出事故的部分。

参考答案

要点：

  • 四层缓存（同时存在，任一层没失效都会看到旧数据）：

1. Request Memoization：同一次渲染中相同 URL + options 的 fetch 只发一次（靠 React 的缓存，仅请求内有效）；

2. Data Cache：跨请求持久的 fetch 结果缓存（服务端，持久化到 .next/cache 或自托管时的存储）。这是「改了数据库页面没变」的最常见元凶。

3. Full Route Cache：构建时把整个路由的 RSC Payload + HTML 缓存为静态产物（SSG/ISR 的落地形式）；

4. Router Cache（客户端）：浏览器内存里缓存已访问路由的 RSC Payload，让前进/后退与预取瞬间完成（默认有效期：动态路由约 30 秒、静态约 5 分钟，session 级）。

  • 为什么「改了数据页面没变」（按层排查）：

- Data Cache 命中：fetch 默认缓存（stale 语义），或用了 cache: 'force-cache'；

- Full Route Cache 命中：路由被判定为静态，构建产物没有重新生成；

- Router Cache 命中：服务端已经更新，但浏览器还在用内存里的旧 Payload（刷新一次就好，但用户不会刷新）；

- 部署环境缓存：CDN 边缘缓存（s-maxage/Vercel 的 Data Cache 在边缘）或反向代理缓存了 HTML。

  • 失效手段（对症下药）：

- 精确控制 fetch：{ cache: 'no-store' }（不缓存，永远最新）、{ next: { revalidate: 60 } }（定时过期）、{ next: { tags: ['posts'] } }（打标签）；

- On-Demand Revalidation：写操作后主动失效——revalidatePath('/posts') 或 revalidateTag('posts')（推荐 tag，语义与数据关联而非路径关联，避免改一处要清多个路径）；本质上是在服务端调用后清除 Data Cache + Full Route Cache 并让 Router Cache 失效；

- 路由段配置：export const dynamic = 'force-dynamic'（整段动态）、export const revalidate = 0（不静态化）、export const fetchCache = 'default-no-store'；

- 客户端 Router Cache：调用 router.refresh() 强制拉取最新 RSC Payload（注意它只刷新数据不重置客户端 state，这正是它的价值）；或用 revalidatePath 在 Server Action 里让框架自动处理；

- 确认哪层在起作用：给响应加 x-nextjs-cache: HIT/MISS/STALE 观察头（Vercel 提供），或临时把 no-store 打开验证是否立刻更新——先定位层，再选失效手段，否则容易「全开 no-store」把性能彻底扔掉。

  • 工程建议：给数据获取统一封装（getPosts() 内部声明 tags），让「数据标签」成为约定，写操作后统一 revalidateTag；避免在页面里散落 no-store；监控缓存命中率与 TTFB，静态化是 Next 的主要收益来源，别因为图省事全面动态化。
