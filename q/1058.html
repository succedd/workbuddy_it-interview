Next.js 的中间件（Middleware）运行在哪？为什么不能在中间件里做重业务逻辑？

中级简答题前端开发工程师Web全栈工程师前端架构师Next.js中间件EdgeRuntime鉴权matcher

题目

考察点：Edge Runtime 限制、执行时机、鉴权收口。理解运行时的边界。

参考答案

要点：

  • 运行位置与时机：Middleware 跑在 Edge Runtime（Vercel 边缘节点或自托管的轻量运行时），在请求到达路由渲染之前执行，每个匹配的请求都会跑（包括静态资源与预取请求，需用 matcher 收窄）。这是「请求进入应用的第一道关卡」。
  • Edge Runtime 的限制（为什么不能做重活）：

1. 没有完整 Node.js API：没有 fs、net、child_process，不能读写本地文件、不能开 TCP 连接——很多 Node 库直接不能用（数据库驱动、某些 SDK、图片处理库）；

2. 执行时间与内存受限（各平台有上限，通常执行时间窗口很窄），超时直接被终止；

3. 每次请求都可能冷启动/无状态，不能持有连接池，也不要用内存做缓存（多节点不共享）；

4. 运行在网络边缘的多点：直连主数据库会有跨区域高延迟（数据库在单区域，边缘节点遍布全球），并且连接数会被放大（每个边缘节点各开连接）；正确做法是走边缘可用的存储（KV、边缘数据库）、调用自己的 API，或只做无副作用判断。

  • 中间件适合做的事：重定向 / 改写（rewrite）、国际化语言路由、A/B 分流与灰度、基于 Cookie 的轻量鉴权（只校验 token 是否有效/是否过期，不查库）、安全响应头、Bot 与地域拦截、给响应打 trace id。
  • 不该在中间件做的事：访问数据库、调用慢的服务接口、做复杂业务计算、读写文件、大 payload 处理（请求体解析）。因为这些会放大到每个请求并落在延迟最敏感的位置。
  • 鉴权的正确分层（高频追问）：

- 中间件：粗粒度——无 token 直接跳登录页，token 格式/签名校验（用 jose 这类兼容 Web Crypto 的库做 JWT 验证，不能依赖 Node 的 jsonwebtoken 的部分能力）；

- 服务端组件 / Route Handler / API 层：细粒度——查库确认用户状态与权限（这里才允许访问数据库/调用服务）；

- 关键：中间件不能作为唯一鉴权防线，因为它的判断依据（Cookie）可被伪造或过期，真正的数据访问权限必须在数据层再校验一次（纵深防御）。

  • 其他要点：middleware.ts 必须在项目根（或 src/ 下）；用 matcher 配置精确匹配（支持正则）排除静态资源，否则每个图片请求都跑一遍中间件；request.cookies 只读，要改 Cookie 得在响应上设置（NextResponse.next() 后 response.headers）；rewrite 用于「URL 不变但内容不同」（多租户、灰度），redirect 会改地址栏——混用会导致无意的地址跳转。
