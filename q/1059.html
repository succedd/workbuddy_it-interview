浏览器事件循环中宏任务与微任务的执行顺序是怎样的？Node.js 的有什么不同？

中级简答题前端开发工程师HTML/CSS/JS工程师前端架构师浏览器事件循环微任务EventLoopNode.js

题目

考察点：任务队列、渲染时机、Node 的阶段模型。异步基础题里的高分题。

参考答案

要点：

  • 浏览器的一次事件循环：从宏任务（task）队列取一个任务执行 → 该任务产生的所有微任务（microtask）在本轮内全部清空（queueMicrotask、Promise.then、MutationObserver）→ 可能需要渲染更新（样式/布局/绘制，通常对齐屏幕刷新率 60fps≈16.6ms）→ 进入下一轮。
  • 两条铁律：① 每个宏任务之间会清空微任务队列；② 微任务执行期间新产生的微任务会在同一轮继续执行（所以「微任务里递归 Promise」会饿死渲染，页面卡死）。
  • 执行顺序实例：
console.log('1')
setTimeout(() => console.log('2'))          // 宏任务
Promise.resolve().then(() => console.log('3')) // 微任务
console.log('4')
// 输出：1 4 3 2
  • setTimeout(fn, 0) 为什么不是「立即执行」：它至少要等下一个宏任务轮次，且浏览器有 4ms 的最小钳制（嵌套调用超过 5 层时）；requestAnimationFrame 在渲染前执行，适合动画；requestIdleCallback 在空闲时执行，适合低优先级任务。
  • Node.js 的不同（阶段模型）：事件循环分为 timers → pending callbacks → idle/prepare → poll → check（setImmediate）→ close callbacks，每个阶段之间（以及每个阶段内部）会清空微任务队列。要点：

- process.nextTick 优先级高于 Promise 微任务——它有自己的 nextTick 队列，且总在微任务之前清空（滥用会饿死 IO）；

- setImmediate 与 setTimeout(0) 的顺序不确定：在主模块（同步代码）里，两者顺序取决于进程启动耗时（通常不确定）；但在 I/O 回调里，setImmediate 总是先于 setTimeout（因为 IO 回调后先到 check 阶段，再到 timers 阶段）；

- Node 11+ 起两者都对齐到浏览器的「宏任务间清微任务」语义，早期版本的差异（微任务何时清空）已修正。

  • 实践结论：想「尽快执行但仍让出渲染」→ 微任务（Promise/queueMicrotask）；想「下一帧前执行」→ rAF；想把长任务切片避免阻塞 INP → 用 setTimeout/scheduler.postTask/MessageChannel 主动让出；别用 setTimeout 做「同步后的立即刷新」，DOM 更新在微任务里就能被读到（await nextTick() / Vue 的 nextTick 就是基于微任务）。
  • 渲染相关：微任务清空后才可能渲染，所以「改 DOM 后立刻读取布局」会强制同步布局（reflow）；Flush 频率取决于是否被 JS 长任务占满——这也是长任务拖慢 INP 的底层原因。
