浏览器的强缓存与协商缓存怎么判断？Cookie、localStorage、sessionStorage、IndexedDB 该怎么选？

初级简答题前端开发工程师HTML/CSS/JS工程师安全开发工程师浏览器HTTP缓存CookielocalStorageIndexedDB

题目

考察点：缓存头语义、存储容量与生命周期、安全属性。基础工程题。

参考答案

要点：

  • 强缓存（不发请求，直接用本地副本）：

- Cache-Control: max-age=31536000 —— 优先级最高，现代标准；

- Cache-Control: no-cache —— 可以缓存，但每次必须向服务端校验（注意：它的意思是「先校验」而不是「不缓存」，这是最常被误解的头）；

- Cache-Control: no-store —— 完全不缓存（敏感数据用这个）；

- immutable —— 在 max-age 内连刷新都不重新校验（适合带 hash 的静态资源）；

- Expires（HTTP/1.0，绝对时间，受客户端时钟影响）—— 已基本被 max-age 取代；

- public/private —— 是否允许共享缓存（CDN/代理）缓存，带用户信息的响应必须 private，否则会被 CDN 缓存给别人（严重的越权事故）。

  • 协商缓存（发请求带校验字段，服务端决定 304 或 200）：

- Last-Modified + If-Modified-Since：秒级精度（一秒内多次修改识别不到），且「文件内容未变但修改时间变了」会误判为已更新；

- ETag + If-None-Match：内容哈希/版本标识，精度更高，优先级高于 Last-Modified；弱 ETag（W/）表示语义等价而非字节相同；

- 配合策略：强缓存设长 max-age + 文件名带 hash（内容变即换 URL）；接口类用短 max-age + ETag 校验；HTML 用 no-cache 保证发版即时生效。

  • 四种存储的对比与选型：

| | Cookie | localStorage | sessionStorage | IndexedDB |

|---|---|---|---|---|

| 容量 | ~4KB | 5–10MB | 5–10MB | 通常数百 MB 起 |

| 生命周期 | 可设过期时间 | 永久（除非清除） | 标签页关闭即清 | 永久（按需删） |

| 随请求发送 | 是（自动带上，浪费带宽） | 否 | 否 | 否 |

| 线程 | 同步 | 同步（会阻塞主线程） | 同步 | 异步 |

| 数据结构 | 字符串 | 字符串 | 字符串 | 结构化对象/二进制/索引查询 |

  • 选型建议：

- 登录凭证：优先 HttpOnly + Secure + SameSite 的 Cookie——HttpOnly 让 JS 读不到，能有效抵御 XSS 窃取 token；若必须放 localStorage，则要做好 XSS 防护并用短期 token + 刷新机制（这是「localStorage vs Cookie 存 token」这道题的核心权衡）；

- 表单草稿/临时状态：sessionStorage（关标签即清，不污染下次会话）；

- 用户偏好/主题/离线数据：localStorage（注意同步 API，大 JSON 序列化会阻塞主线程）；

- 大量结构化数据、离线队列、文件缓存：IndexedDB（本项目题库就存在 IndexedDB 里）；

- 跨标签同步：localStorage 的 storage 事件或 BroadcastChannel（sessionStorage 不跨标签）。

  • 安全与细节：SameSite=Lax（默认）能防大部分 CSRF；Secure 只在 HTTPS 发送；不要在 Cookie 里存大量数据（每个请求都带，且域名下 Cookie 数量/大小有限制）；document.cookie 无法读取 HttpOnly 项（这正是它的价值）。
