在网关层怎么实现鉴权与灰度发布？按用户/请求头分流要注意什么？

高级简答题后端架构师架构师后端开发工程师API网关鉴权灰度发布JWT灰度路由

题目

考察点：统一鉴权收口、灰度策略、路由匹配规则。网关的核心业务能力。

参考答案

要点：

  • 鉴权为什么要放网关：网关是所有流量的唯一入口，在这里统一校验能避免「每个微服务各写一遍鉴权逻辑」——安全规则收敛到一处，改一次全局生效，也减少业务服务的重复开销。
  • 网关鉴权的分层职责：

- 网关做（粗粒度）：① 身份认证——校验 JWT 签名/有效期，或校验 Session/API Key；② 路由级权限——这个 token 能否访问 /admin/；③ 限流与黑白名单；④ 把解析出的用户信息（userId、租户、角色）通过请求头下发**（如 X-User-Id）；

- 业务服务做（细粒度）：数据级权限（这条订单是不是他的）、业务规则校验。网关不查业务库，否则它就成了新的瓶颈与耦合点。

  • 安全红线（务必强调）：① 网关下发的身份头必须在入口处「剥离后再重写」——如果直接信任客户端传来的 X-User-Id，攻击者伪造该头就能冒充任意用户，这是网关架构最常见、最严重的越权漏洞；② 不要把网关当作唯一防线，服务间调用也要有内部鉴权（mTLS / 内网签名），防止绕过网关直连；③ 不要在网关缓存带用户信息的响应（见缓存头 private 一节）。
  • 灰度发布的实现（按匹配能力递进）：

1. 按请求头：X-Gray: true 走新版本（最简单，适合内部验证）；

2. 按用户 ID / 租户哈希：hash(userId) % 100 < 10 让 10% 用户进入新版本——关键是哈希要稳定（同一用户始终落在同一组，否则体验会「跳来跳去」）；

3. 按比例流量：网关层加权路由（权重 10/90），实现简单但同一会话可能来回切换，只适合无状态接口；

4. 按来源/设备/地域：App 版本号、地域、渠道，适合「先放一个能立刻回滚的小流量池」；

5. 进阶：影子流量（暗发布）——把真实流量复制一份给新版本，只观察不问结果，用于验证性能与正确性，零用户风险。

  • 必须配套的机制：

- 随时可回滚——灰度权重必须支持配置中心热更新（秒级生效），回滚预案要先演练；

- 新旧版本共存期的兼容性——同一个下游可能同时收到两个版本的请求，接口字段要向后兼容（新增字段而非改语义），数据库变更要走先加后删的两阶段；

- 监控分流是否正确——按版本打标签上报指标（错误率、延迟），否则灰度等于盲测；

- 注意匹配优先级：灰度规则必须先于默认路由匹配，且规则之间不能有歧义覆盖（如「按 header 灰度」被「按权重」覆盖）；

- 金丝雀与全量的边界：明确「什么条件才能推进到 100%」——通常要求新版本错误率、P99 延迟在观察窗口内不劣化。
