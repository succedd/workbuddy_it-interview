常见的负载均衡策略有哪些？一致性哈希解决了什么问题，又带来什么副作用？

中级简答题后端架构师架构师后端开发工程师服务治理负载均衡一致性哈希虚拟节点会话保持

题目

考察点：LB 算法、会话保持、哈希倾斜与虚拟节点。中间件与分布式基础。

参考答案

要点：

  • 常见策略与适用场景：

- 轮询（Round Robin）：均匀分发，前提是后端实例性能相近；

- 加权轮询：按机器规格配权重，异构集群的标配；

- 随机：实现最简，规模大时统计上接近均匀；

- 最少连接数（Least Connections）：按当前活跃连接分发，能自动避开慢实例，适合请求耗时差异大的场景；

- 最短响应时间（Least Response Time）：按实测延迟动态调整，对长尾最敏感；

- IP Hash / 用户 Hash：把同一客户端固定到同一实例，实现会话保持（session stickiness）；

- 一致性哈希：见下。

  • 一致性哈希要解决的问题：普通取模（hash(key) % N）在扩缩容时会导致几乎所有 key 重新映射——缓存场景下等于全量缓存失效（缓存雪崩式回源）。一致性哈希把哈希空间组织成一个环，节点与 key 都映射到环上，key 归属顺时针方向第一个节点。增删一个节点只影响相邻区间的 key（平均只迁移 1/N 的数据），大幅减少抖动。
  • 副作用与解法（关键）：

- 哈希倾斜 / 数据不均：节点少时，节点在环上的分布可能极不均匀，导致部分节点承担大部分流量；

- 解法：虚拟节点（Virtual Nodes）——每个物理节点在环上映射几百个虚拟位置，把分布拉均匀。同时虚拟节点带来权重控制能力（性能强的机器分配更多虚拟节点）；

- 节点摘除时的抖动：某节点故障，其全部 key 会压到下一个节点上（瞬间流量翻倍，可能压垮）——需要副本（按顺时针取前 N 个健康节点）或负载上限缓解。

  • 必须区分两种场景：

- 无状态服务：不需要会话保持，用轮询/最少连接即可。强行做哈希反而破坏均衡（热点用户会把某实例打爆）；

- 有状态场景（缓存分片、分库分表、任务分片、WebSocket 长连接）：一致性哈希价值最大。分库分表的哈希分片就是同一个原理。

  • 会话保持的替代方案（更好的做法）：把 session 外置到 Redis——服务变成无状态，就不需要哈希绑定了。「用负载均衡做会话保持」往往是「该外置状态却偷懒」的信号，代价是扩容受限、故障时用户掉线、热点不均。
  • 另需注意：健康检查（主动探测 + 被动摘除）、摘除后的连接处理（优雅下线：先停止接新连接、等待存量请求结束，否则用户会看到 5xx）、四层 vs 七层 LB（LVS 四层性能高、不解析内容；Nginx/Envoy 七层可做路由与灰度）。
