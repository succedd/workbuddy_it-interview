gRPC 的四种流式模式分别适合什么场景？流式相比普通 RPC 复杂在哪里？

中级简答题后端开发工程师Go后端工程师后端架构师gRPC流式Streaming背压HTTP2

题目

考察点：四种调用模式、流控与背压、连接生命周期。理解 gRPC 的表达能力边界。

参考答案

要点：

  • 四种模式（都由 Protobuf 的 stream 关键字声明）：

1. Unary（一元）：一请求一响应，等价于普通 RPC。绝大多数业务接口用这个——简单、幂等好设计、易做重试与缓存；

2. Server Streaming（服务端流）：一请求、多响应。适合大结果集分块下发（导出大数据、日志拉取）、实时推送（行情、通知、订阅）、流式生成（LLM 逐 token 返回）；

3. Client Streaming（客户端流）：多请求、一响应。适合批量上传/聚合（分片上传文件、传感器批量上报、批量写入）——相比「多次 Unary」省掉了每次的头部开销与往返；

4. Bidirectional Streaming（双向流）：双向独立。适合实时双向交互（IM 聊天、协同编辑、语音识别边发边收、游戏状态同步）。注意：双向流是「全双工」，两侧可独立发送，不是「一问一答」。

  • 流式比 Unary 复杂在哪（重点答这一块）：

- 背压（Backpressure）：如果生产者比消费者快，数据会在内存里堆积——HTTP/2 有流控窗口机制，但应用层必须显式配合（如 gRPC 的 isReady() 判断可写、或按需 request(n) 拉取），否则内存泄漏型 OOM。这是流式接口最常见的线上问题；

- 连接生命周期：长连接意味着要处理重连、断线续传、心跳保活；连接断开时未完成的流会出错，业务必须能从中断点恢复（记录 offset/cursor）；

- 错误语义变化：Unary 一次调用对应一个明确结果；流式里错误可能在流中途发生（已收到部分数据再报错），客户端要定义「部分成功的处理规则」；

- 负载均衡失效：长连接一旦建立就粘在某个后端实例上，后续所有流数据都走这一条——发布/扩缩容时无法平滑迁移（需主动断开重建），而不像 Unary 可以每次重新选实例；

- 超时与重试困难：流式请求的耗时不可预估，不能用固定的短超时；重试会导致数据重复（需要幂等/去重）；

- 可观测性变差：一次业务概念上的「会话」在监控里表现为一个超长 span，延迟指标失去意义，需要自定义「每消息延迟」指标；

- 代理与网关兼容性：部分 HTTP 代理、LB 会缓冲或在一段时间无数据后切断长连接流（如 Nginx 需关 proxy_buffering、调 grpc_read_timeout），生产上必须验证每一跳的配置。

  • 选型建议：能用 Unary 就用 Unary（90% 场景）；需要「服务端持续推送」优先考虑 Server Streaming（比 WebSocket 更规范、有 Protobuf 类型）；双向流只在真的双向实时交互时用，并提前设计好背压、断线恢复、死连接检测；纯前端（浏览器）对接时注意 gRPC-Web 不支持客户端流与双向流（浏览器无法完全控制 HTTP/2 帧），此时用 WebSocket 或 SSE 更合适。
