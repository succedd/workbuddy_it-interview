gRPC 的超时、重试与负载均衡该怎么配？为什么默认的 RPC 重试很危险？

高级简答题后端开发工程师Go后端工程师后端架构师gRPC重试Deadline负载均衡幂等

题目

考察点：deadline 传播、重试语义、客户端 LB。生产配置题。

参考答案

要点：

  • 超时用 Deadline 而非 Timeout：gRPC 的 deadline 是绝对时间点，并且会随调用链传下去——服务 A 调 B 再调 C 时，C 收到的 deadline 是 A 定的那个时刻。好处是整条链路的剩余预算被正确共享：B 不会在 A 已经超时的情况下继续等 C。必须显式设置 deadline（默认无超时 = 可能永久挂住线程/连接）。
  • 配置原则：外层 deadline > 内层，且每一跳都要减去自身处理耗时（框架自动处理传播，但服务内部要检查 ctx.Done()/context.isActive() 并及时退出，否则「上游已放弃，下游还在算」——白白消耗资源）。
  • 重试为什么危险：

- 默认不开启（这是 gRPC 的保守设计，但很多团队手工打开后不设约束），一旦开启：放大流量（下游过载时重试 2 次即 3 倍压力）、可能重复执行副作用（非幂等接口重复扣款/重复下单）；

- 正确配置四要素：① 只对幂等/安全方法重试（GET、幂等 PUT，或业务上带幂等键）；② 限制次数与预算——maxAttempts 建议 ≤3，并设置 maxAttempts 与总超时联动（重试必须在上游 deadline 内完成，gRPC 的 retry policy 支持 retryableStatusCodes + 退避参数）；③ 退避 + 抖动（initialBackoff/maxBackoff/backoffMultiplier，必须带 jitter 避免惊群）；④ 限定可重试的状态码——只重试 UNAVAILABLE（瞬时不可用）、RESOURCE_EXHAUSTED，绝不重试 INVALID_ARGUMENT/PERMISSION_DENIED（重试也一定失败，纯浪费）；

- 叠加风险：如果客户端 + 服务端 + SDK 三层都配了重试，实际放大倍数是乘积（2×2×2 = 8 倍）。只在最靠近故障点的一层重试；

- 配合熔断：熔断打开时应直接快速失败，不要继续重试。

  • 负载均衡：

- gRPC 的连接是长连接（HTTP/2），若像普通 HTTP 那样「连到 LB，由 LB 分发连接」，会出现一个连接把所有请求都发到同一台后端的问题（连接级均衡 ≠ 请求级均衡）；

- 正确姿势：客户端侧负载均衡（Client-side LB）——客户端通过服务发现拿到全部后端地址，自己按策略（round_robin/pick_first/least_request）为每个后端建子连接并轮询发请求；gRPC 提供 grpc.Dial 的 resolver + balancer 机制，也可用 xDS（配合 Istio/Envoy）做集中式 LB；

- 若必须用代理（如 Nginx/Envoy 做 L7 代理），需要代理支持 HTTP/2 且按请求分发（Envoy 可以，普通 TCP 四层 LB 不行）。

  • 加分点：健康检查用 gRPC Health Checking Protocol（标准 grpc.health.v1.Health）；连接要设 keepalive（检测半开连接），但要与 LB 的空闲超时协调（keepalive 间隔太长会被 LB 断，太短会浪费）；请求要带 metadata 传 trace id 与业务标识（等价于 HTTP header）。
