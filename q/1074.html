Spring Cloud 的断路器从 Hystrix 演进到 Sentinel / Resilience4j，该怎么选？

中级简答题Java后端工程师Java开发工程师后端架构师SpringCloudHystrixSentinelResilience4j熔断

题目

考察点：组件演进脉络、模型差异（线程池隔离 vs 信号量）、选型依据。Java 微服务高频题。

参考答案

要点：

  • 演进脉络：Hystrix（Netflix，2011）→ 停止新特性开发（2018）→ 官方推荐 Resilience4j（社区）/ Sentinel（阿里）。Spring Cloud Netflix 系列（Hystrix/Ribbon/Zuul/Eureka）在 Spring Cloud 2020.x 起被整体移除，迁移是硬性的（不是可选项）。
  • Hystrix 的核心设计与问题：

- 线程池隔离：为每个下游依赖分配独立线程池，一个依赖慢只耗尽自己的池——隔离性最强；

- 代价：线程切换开销大（每请求至少一次上下文切换），线程数固定导致容器化环境下配置僵化（实例多时线程总量爆炸），且无法传递 ThreadLocal（分布式追踪、RequestContext 需要特殊处理）；

- 另外有 SEMAPHORE（信号量）模式：不切线程，开销小但隔离性弱（适合本地缓存这类极快调用）。

  • Resilience4j：为 Java 8 + 函数式设计，用装饰器组合（CircuitBreaker、RateLimiter、Retry、Bulkhead、TimeLimiter、Cache）。默认信号量式隔离（不开新线程池），轻量、易测试；模块化，可只引需要的部分（不像 Hystrix 是个大包）；与 Spring Boot 2/3、Micrometer 集成好。适合追求轻量、纯 Spring 生态的项目。
  • Sentinel：阿里的流量治理组件，定位比断路器更广：流控（QPS/线程数/热点参数）、熔断降级、系统自适应保护、授权规则。特点：

- 控制台动态改规则（实时生效，不需要重启或改配置）；

- 热点参数限流（如「同一商品 ID 限 10 QPS」）是它的特色能力；

- 系统自适应保护（按 LOAD/RT/线程数自动限流）在大促/突发流量下很实用（不用手工算阈值）；

- 生态适配广（Spring Cloud Alibaba、Dubbo、网关）。适合需要完整流量治理 + 国内生态支持的项目。

  • 选型判断：

- 只用 Spring Cloud 官方栈、需求就是「熔断 + 限流 + 重试」→ Resilience4j（无额外控制台依赖，最轻）；

- 需要动态规则、热点限流、系统保护、多语言（Java/Go/C++） 或有 Spring Cloud Alibaba / Dubbo 背景 → Sentinel；

- 存量还在用 Hystrix → 尽快迁移（不再维护，Spring Cloud 新版已不兼容），迁移主要是把 @HystrixCommand 换成 @CircuitBreaker（Resilience4j）或 @SentinelResource。

  • 通用最佳实践（与选型无关）：

- 熔断参数要设最小请求数（否则低流量时 1 个错误就熔断）；

- 阈值按「错误率 + 慢调用比例」双维度比只看错误率更贴近真实故障（慢也是故障）；

- 熔断器状态必须上报监控并告警（打开 = 业务功能在退化，不能沉默）；

- 降级方法要有业务意义（返回兜底数据而不是 null），且降级逻辑本身不能依赖被熔断的下游（否则降级也失败）；

- 半开状态放行量要小（试探流量大 = 二次打击）；

- 熔断要与重试协调：熔断打开时不应重试。

  • 加分点：断路器只是兜底，真正的稳定性要靠「合理的超时 + 隔离 + 限流 + 容量规划」；把「熔断降级」当成稳定性的全部，是把兜底当成了主防线。
