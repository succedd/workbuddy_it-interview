Prometheus 采用拉模型（Pull），那什么时候该用 Pushgateway？为什么说临时任务也不该轻易用？

中级简答题DevOps工程师SRE站点可靠性工程师系统运维工程师PrometheusPushgatewayPull批处理监控设计

题目

考察点：Pull 与 Push 的取舍、Pushgateway 的真实副作用。常被「为省事」误用的地方。

参考答案

要点：

  • 为什么 Prometheus 默认用 Pull（拉）：

1. 便于判断目标存活——up == 0 就是一个天然的、免费的存活指标（Push 模型里「没收到数据」既可能是服务挂了，也可能是任务还没跑）；

2. 服务端可控——采集频率、超时、重试都在服务端，便于限流与保护，也避免大量客户端同时推送造成尖峰；

3. 配置即清单：目标列表在 Prometheus 侧（static_configs 或服务发现），调试时可以直接用浏览器的 /metrics 页面验证（curl 就能看），排障成本低；

4. 无需在业务侧维护推送逻辑与目标地址（但需要暴露 HTTP 端点）。

  • Pushgateway 的定位：给无法被拉取的目标做一个中间缓存——最典型的是批处理任务/定时任务（CronJob）：跑几秒就退出，Prometheus 来不及在窗口内抓到它。任务把指标 push 到 Pushgateway，Prometheus 再从 Pushgateway 拉取。

注意：Pushgateway 不改变模型——Prometheus 依然是拉，Pushgateway 只是个「替身目标」。

  • 为什么不该轻易用（副作用清单）：

1. 指标会永久驻留：Pushgateway 会保留最后一次推送的值，如果任务不再运行（被删掉、失败退出），指标会一直存在且看着「正常」——形成「僵尸指标」，会严重误导告警与容量判断；

2. 多实例聚合即错误：Pushgateway 按 job/instance 分组保存，多个实例推同名指标会互相覆盖，或产生难以理解的多组值（要手动在推送时加实例标签，且清理需额外接口）；

3. 计数器语义被破坏：任务每次重启都从 0 开始，Push 上去的 Counter 不是单调递增，rate() 的结果会混乱；

4. 失去 up 的存活语义：无法区分「任务正常但没数据」与「任务挂了」（这正是 Pull 的核心优势，被绕过了）；

5. 单点与状态风险：Pushgateway 本身是无状态设计的有状态组件（保存了数据），需要持久化、需要高可用，又多了个要运维的东西。

  • 正确的替代方案（优先顺序）：

- ① 让任务「变长命」：把短任务改成常驻进程 + 定时触发（或加一个 always-on 的 sidecar 暴露指标），从而可被拉取——这是最干净的方案；

- ② Push 到「支持 Push 的时序库」：VictoriaMetrics、Mimir、Thanos 的接收端或直接写 remote_write，语义比 Pushgateway 更清晰（不驻留、可设计 TTL）；

- ③ 用 prometheus-pushgateway 但加重度约束：推送时显式带 instance/run_id 标签、任务结束时主动 DELETE 自己的分组（DELETE /metrics/job/<job>）、为「最后成功时间」设独立 Gauge 并据此告警（这样任务不再运行能被发现）——这是把副作用管起来的补丁，而不是推荐做法；

- ④ 对于「事件式」数据，用 日志 + Loki 或 Push 到支持 TTL 的存储比时序指标更合适（如「本次任务处理了 N 条」本质是事件而非时序）。

  • 判断准则（一句话）：能被拉取的一律拉取；只有「生命周期短于采集周期」且「无法改造成常驻」的目标，才考虑 Pushgateway，且必须为它设计「不再运行」的告警。
