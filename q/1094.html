CLB 的健康检查是怎么工作的？为什么配置了「间隔 5 秒、阈值 3 次」，后端故障后要过约十几秒流量才切走？

中级简答题公有云售后技术支持系统运维工程师云计算工程师CLB健康检查时间窗TCPHTTP

题目

考察点：健康检查的探测协议（TCP SYN / HTTP 状态码）、健康检查时间窗的计算、检测灵敏度与误判的权衡。承接上一题的四层/七层区分，进入 CLB 可用性的核心机制。

参考答案

探测机制（按监听器协议）：

  • TCP 健康检查：CLB 向「后端内网 IP + 健康检查端口」发 SYN 包，收到 SYN+ACK 即判定健康，随后发 RST 中断连接；超时未收到则判定失败；
  • HTTP 健康检查：CLB 向「IP + 端口 + 检查路径」发 HTTP 请求，在响应超时时间内收到与配置匹配的 HTTP 状态码即判定健康；也可用 HEAD 方法降低后端开销；
  • 另有 UDP 的 Ping/自定义探测、以及默认开启的被动健康检查（转发失败累计 3 次即屏蔽该后端 10 秒）。

为什么切换不是「秒切」——健康检查时间窗：为避免抖动误判，只有连续多次失败才切换状态：

  • 四层失败时间窗 = 检查间隔 ×（不健康阈值 − 1）。默认间隔 5s、不健康阈值 3 次时，失败时间窗 = 5 × (3−1) = 10 秒；
  • 七层失败时间窗 = 响应超时 × 不健康阈值 + 检查间隔 ×（不健康阈值 − 1）。默认参数下 = 2×3 + 5×(3−1) = 16 秒；
  • 恢复侧同理：连续健康阈值次数成功才重新纳管流量（新绑定后端还有「探测中」状态，此间不转发流量）。

运维要点：

  • 健康检查探测源 IP 是 CLB 的 VIP 或 100.64.0.0/10 网段（七层请求 UA 为 clb-healthcheck），后端安全组/iptables 必须放行，否则永远异常；
  • 探测建议指向静态页面，避免动态接口慢响应导致误判；阈值调小切换更快但更容易抖动误判，反之亦然——这是灵敏度与稳定性的权衡。
