【场景题·高级】某服务的方法 A（无 @Transactional）内部调用同类的方法 B（有 @Transactional），B 里的数据库操作抛异常后事务没有回滚；另一个 @Async 方法被同类调用后也变成了同步执行。请定位根因、解释原理，并给出修复方案。

高级场景题Java后端工程师Java开发工程师后端架构师SpringAOP自调用事务失效@Async代理

题目

考察点：代理机制的自我调用（self-invocation）盲区、@Transactional/@Async 失效的经典场景、三种修复方案的推荐度排序。追问链 AOP 环节的高频生产事故。

参考答案

根因定位：两个现象是同一个根因——自调用绕过了代理。Spring 事务和 @Async 都是基于代理的 AOP 实现：调用方持有的是代理对象，代理在方法前后织入事务/异步逻辑；但目标对象内部的 this 引用是原始对象而不是代理，A 里调 this.B() 直接打在原始对象上，切面逻辑根本没有执行机会。官方文档明确说明：self invocation via this will bypass the advice。

原理展开（为什么代理救不了 this）：代理增强发生在「外部调用先经过代理」这一层；一旦调用已经进入目标对象内部，后续 this 调用就是普通 Java 方法调用（相当于字节码层面的直接调用），与 Spring 无关。

修复方案（按推荐度）：

  • 首选：避免自调用（重构拆分）——把 B 拆到另一个 Bean，通过注入相互调用，让调用重新走代理；官方称为 best approach，代价是需要少量重构；
  • 次选：注入自身引用（self injection）——把自身 Bean 注入给自己（或用 ObjectProvider 拿代理），通过自引用调 B，让调用走代理；注意可能触发循环依赖，Spring 允许这类自注入；
  • 兜底：AopContext.currentProxy()——((XxxService) AopContext.currentProxy()).B()，需要开启 exposeProxy；官方明确「highly discouraged」——代码与 Spring AOP 强耦合，仅作最后手段。

举一反三（同类失效场景清单）：同类 this 调用、方法非 public（CGLIB/JDK 代理都无法拦截 private）、异常被 catch 吞掉不抛出、final 方法无法被 CGLIB 覆盖——排查「注解不生效」类工单时优先对照这张清单。
