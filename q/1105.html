【故障排查题·高级】应用启动直接失败，日志报 BeanCurrentlyInCreationException，提示依赖形成循环。团队已知 Spring 有三级缓存能解决循环依赖，为什么这次没救回来？请解释机制边界、给出排查路径与解决方案。

高级故障排查题Java后端工程师Java开发工程师后端架构师Spring循环依赖构造器注入BeanCurrentlyInCreationException三级缓存

题目

考察点：循环依赖的解决边界（构造器注入/prototype 无法用三级缓存解决）、BeanCurrentlyInCreationException 的成因、依赖图梳理与重构方案。追问链收尾：从「三级缓存是什么」深入到「什么时候三级缓存也无能为力」。

参考答案

机制边界（为什么这次救不回来）：

  • 三级缓存解决循环依赖的前提是「先实例化、后注入」：A 实例化（构造器已执行完）后可以先把早期引用暴露出去，让 B 先拿半成品 A 用，A 稍后再补完初始化；
  • 构造器注入打破了这个前提：A 还没构造出来就依赖 B，B 又要在构造器里拿到 A——「先有鸡还是先有蛋」无法暴露任何早期引用，Spring 官方文档明确： predominantly constructor injection 可能造成不可解决的循环依赖，运行期检测到后直接抛 BeanCurrentlyInCreationException；
  • 另一边界：prototype 作用域的循环依赖也无法解决——原型 Bean 不进单例缓存，Spring 不缓存它的中间状态，直接报错；
  • 相关参数：Spring Boot 2.6+ 默认禁止循环引用（spring.main.allow-circular-references=false），很多「升级后突然启动失败」的工单源于此。

排查路径：

  • 从异常栈提取循环链（A → B → A），结合 @Autowired/构造器注解画出依赖图，确认是构造器注入、字段注入还是 setter 注入；
  • 确认涉及的 Bean 作用域（是否混入 prototype）；
  • 检查是否为近期升级 Spring Boot 引入的默认行为变化。

解决方案（按优先级）：

  • 首选：重构消灭循环——循环依赖几乎总是设计问题（职责耦合），提取公共逻辑到第三个 Bean，或用事件/回调解耦；
  • 次选：把其中一方的构造器注入改为 setter/字段注入（官方文档给出的可行方案——虽不推荐但可让三级缓存接管）；
  • 应急：在依赖点加 @Lazy——注入的是延迟代理，首次使用才真正解析，绕开启动期循环；
  • 反模式：随手打开 allow-circular-references 只是把问题藏起来，不解决耦合本身。
