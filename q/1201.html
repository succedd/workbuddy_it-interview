故障排查题：线上监控突然告警——数据库 CPU 飙升、连接数打满、响应变慢。你如何快速判断这是缓存穿透、击穿还是雪崩？各自的『止血』手段是什么？

高级故障排查题Java后端工程师后端开发工程师Redis缓存异常故障排查应急止血

题目

考察点：把三种缓存异常的『表象差异』映射到排查动作，以及对应的应急止血手段。要求能结合监控指标（缓存命中率、DB QPS、请求 key 特征）定位，而不是盲目重启。

参考答案

要点：

  • 第一步：看请求 key 特征与监控。① 若大量请求是『格式合法但根本不存在的 id』、缓存命中率骤降且 DB QPS 主要由这类查询构成 → 穿透；② 若是『某个/少数热点 key』在某一瞬间并发 miss、DB 单点被打 → 击穿；③ 若『大量 key 同时失效』或 Redis 本身不可达、应用大面积缓存 miss → 雪崩。
  • 穿透止血：在入口封禁恶意 IP / 限流；对不存在 key 缓存空值（短 TTL）；若已接布隆过滤器则确认其是否生效、是否需要重建。临时可加 WAF/网关层拦截异常流量。
  • 击穿止血：对热点 key 加分布式锁（只让一个线程回源），抢不到锁的线程返回旧值或快速降级；极端热点 key 临时改为不过期 + 后台刷新。
  • 雪崩止血：先熔断/限流保护数据库，避免被冲垮；Redis 宕机则切到高可用从节点；若是大量 key 同时过期，给存量 key 的 TTL 补随机扰动、或对热点数据提前预热。
  • 通用：止血后必须补『缓存预热 + 随机 TTL + 多级缓存（本地 Caffeine + Redis）』做长期防御，并盯紧命中率、DB 实际查库 QPS、P99 延迟等核心指标。

核心：先靠监控和请求特征定性（穿透=不存在的 key、击穿=单热点、雪崩=大面积失效/宕机），再对症下药止血，最后补架构防御。
