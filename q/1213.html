【故障排查】Spring Cloud Gateway 网关突然出现大量 HTTP 503，用户侧大面积不可用。请给出系统化定位思路，区分是注册中心、下游服务还是网关自身的问题。

高级故障排查题Java后端工程师技术经理后端架构师网关SpringCloudGateway503故障排查全链路追踪

题目

追问链第 4 问：网关是统一入口，503 是「上游不可用」信号，但要锁定真正责任人。

参考答案

要点：

  • 第一步：界定 503 含义与范围。Gateway 的 503 通常来自后端路由失败（no available instance）或转发超时/连接拒绝。先确认是全量接口还是特定服务 503：全量→网关或注册中心层面的共性问题；特定→某个下游服务故障。同时看是否伴随 504（超时）还是纯 503（无可用实例）。
  • 第二步：查注册中心。登录 Nacos/Eureka 控制台，看目标服务实例列表是否为空、健康状态、最后心跳时间。若实例数骤降或为 0，说明是注册中心侧问题（实例被误剔除、健康探测失败、或注册中心自身不可用导致列表未刷新）；同时检查网关本地缓存的服务列表是否过期。
  • 第三步：查下游服务。若注册中心实例正常，直接拨测下游 Pod 的 readiness/health 与业务端口，确认进程是否存活、线程池/连接池是否打满、GC 是否长时间 Stop-The-World。下游自身故障（OOM、慢 SQL、依赖雪崩）会让网关拿不到健康响应而 503/504。
  • 第四步：查网关自身。看 Gateway 路由配置/断言是否变更、连接池（reactor-netty）是否耗尽、是否超时配置过短触发熔断、网关节点 CPU/内存/文件句柄是否瓶颈。结合全链路追踪（SkyWalking/Jaeger）定位耗时落在哪一段。
  • 止血与根治：临时对故障服务熔断降级/返回兜底；长期加实例健康检查、限流、舱壁隔离，避免单点拖垮网关。
