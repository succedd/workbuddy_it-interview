【系统设计】如果从零搭建一套微服务基础设施，你会如何为「注册中心、网关、配置中心」选型和组合？给出关键权衡。

高级系统设计题Java后端工程师技术经理后端架构师云架构师技术选型微服务NacosGatewayApollo高可用

题目

追问链第 6 问（收口）：把前面几问串起来，做一个整体技术选型决策。

参考答案

要点：

  • 注册中心选型权衡：① Nacos（推荐 Spring Cloud Alibaba 体系）——同时支持 CP+AP 模式切换、自带配置中心、国内生态好、可视化强，中小团队一站式；② Eureka——纯 AP、自我保护适合对一致性要求不高的内网，但已停更；③ Consul——基于 Raft 强一致 + 多数据中心 + 健康检查强大，但运维偏重；④ etcd/ZooKeeper——CP 强一致，适合 Kubernetes 生态（K8s 本身用 etcd 做服务发现）。建议：K8s 环境优先用 Service+etcd；非 K8s 的 Spring 体系优先 Nacos。
  • 网关选型：① Spring Cloud Gateway（WebFlux 响应式、Predicate+Filter 链、与 Spring 生态无缝，适合 Java 团队）；② Kong（基于 Nginx+Lua，性能好、插件丰富、与语言无关）；③ APISIX（云原生、etcd 存储、动态路由强）。网关要承载鉴权、限流、灰度、日志、跨域等横切关注点，选型看团队栈与性能诉求。
  • 配置中心选型：Nacos（与注册中心合一，省运维）、Apollo（携程开源，灰度发布、权限、审计极强，适合配置治理要求高的团队）、或 K8s ConfigMap+Operator。建议：配置治理复杂度高选 Apollo，求简选 Nacos。
  • 组合与落地原则：① 技术栈统一优先（Spring 体系用 Nacos+Gateway，减少心智负担）；② 高可用——三个组件都要集群部署+多副本+持久化，注册/配置中心数据不能丢；③ 渐进式——先用注册发现+网关打通，再上配置中心与全链路监控，避免一次性铺太大翻车；④ 始终保留「降级开关」，任一组件故障时业务可走兜底。
