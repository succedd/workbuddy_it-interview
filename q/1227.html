【故障排查】生产 Redis 出现「脑裂」（网络分区导致原主与新主并存、双写）或主从延迟过大，你如何定位根因并防御？

题目

追问链第 5 问：高可用架构自身的典型故障。

参考答案

要点：

  • 脑裂根因与危害：网络分区时，哨兵把原主判为下线并提升新主，但原主其实还活着（客户端仍在写它），形成「双主」，分区恢复后原主降级为从、丢弃自身写入，造成分区期间的数据丢失。这是异步复制 + 自动切换的固有风险。
  • 定位手段：① 监控 master_link_status/master_sync_in_progress 看主从连接与同步状态；② 用 INFO replication 对比各节点 offset 是否持续拉大；③ 业务侧核对「双主期间写入冲突」导致的脏数据；④ 网络层排查分区（丢包、交换机故障）。
  • 防御配置：① min-replicas-to-write N + min-replicas-max-lag M——主节点在「健康副本数 < N 或副本延迟 > M」时拒绝写入，从源头遏制脑裂丢数；② 合理设置 quorum 与 down-after-milliseconds，避免过于敏感误切；③ 关键链路配合 WAIT 多副本确认；④ 网络层面做冗余（双网卡/独立心跳）。
  • 事后止血：发现脑裂后比对原主与新主数据差异，必要时以新主为准做数据修复，并复盘网络。
