【系统设计】Redis 主从+哨兵 与 Redis Cluster 两种高可用方案该如何选型？Cluster 的槽路由（MOVED/ASK 重定向）、gossip 与槽迁移（resharding）又是如何工作的？

高级系统设计题Java后端工程师系统运维工程师后端架构师RedisCluster哨兵槽路由resharding技术选型

题目

追问链第 6 问（收口）：把主从、哨兵、集群串起来做架构决策。

参考答案

要点：

  • 主从+哨兵适用场景：数据量单节点内存可承载（通常十几到几十 GB）、需要自动故障转移但不需横向分片的场景。哨兵负责高可用，读写分离靠客户端/Proxy。优点是架构简单、运维心智负担低；缺点是不能突破单机内存上限、写仍是单点。
  • Redis Cluster 适用场景：数据量超过单节点容量、需要自动分片与横向扩展的场景。Cluster 把数据按 16384 个槽（slot）分布到多个主节点，每个主可挂从做高可用。优点是无中心、可扩缩容；缺点是客户端需支持 cluster 协议、多 key 事务/Lua 受限（需在同一槽，用 hash tag 约束）、运维更复杂。
  • Cluster 路由机制：客户端计算 CRC16(key) % 16384 定位槽与对应节点；若请求打到错误节点，返回 MOVED 重定向（槽已迁移到新节点，客户端应更新本地槽映射）；ASK 重定向用于迁移进行中（仅本次请求转发，不更新映射）。节点间用 gossip 协议互相交换集群状态。
  • resharding（槽迁移）：用 redis-cli --cluster reshard 把槽从源节点迁到目标节点，迁移期间逐 key 用 MIGRATE 原子移动，配合 ASK 保证不中断服务。注意大 key 迁移会阻塞，需分批/避开峰值。
  • 选型权衡总结：中小规模、重可用轻扩展→哨兵；大规模、需分片扩展→Cluster；两者都需配合持久化与监控，且都要防脑裂与保证副本健康。
