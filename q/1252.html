Kafka 生产者调用 send() 之后就算发送成功了吗？如何用回调、retries、delivery.timeout.ms 处理发送失败？

初级简答题Java后端工程师后端开发工程师Kafka生产者重试发送可靠性

题目

考察点：生产者异步发送语义、重试参数配合与失败兜底。

参考答案

send() 是异步的，不能默认成功

KafkaProducer.send() 把消息放进缓冲区后立即返回一个 Future，此时消息可能因为网络问题或 Broker 不可用而根本没送达。

两种拿到结果的方式

  • 同步：kafkaTemplate.send(topic, o).get() 阻塞等结果，用 SendResult.getRecordMetadata() != null 判断成败。实现简单但把异步变同步，吞吐明显下降，只适合关键单条消息。
  • 回调（推荐）：future.addCallback(result -> 记录 topic/partition, ex -> 记录失败原因并告警)。成功记元数据，失败打日志并交给补偿任务或本地消息表兜底。

重试参数怎么配

  • retries（新版由 delivery.timeout.ms 统一约束）：遇到可重试异常（网络抖动、Leader 切换）时自动重发。默认 3 次偏少，生产上通常调大；但要注意重试可能造成同一分区内消息重复写入。
  • 重试间隔（retry.backoff.ms）必须设置：间隔太小，一次网络波动就把 3 次重试瞬间用完，重试毫无意义；间隔太大又会拉长故障期间的发送延迟。
  • delivery.timeout.ms：从 send 到最终成功的总超时上限，必须 ≥ linger.ms + request.timeout.ms，超过后回调抛 TimeoutException，交由业务补偿。
  • linger.ms 与 batch.size：linger 太小批次攒不起来，吞吐上不去；调大则增加延迟，可靠性优先时不要把 linger 设得过大。

结论

可靠性不是靠单个参数：acks=all + min.insync.replicas > 1 保证不丢，retries + 退避保证可恢复，回调 + 告警/本地消息表保证「确实没发出去」的消息能被发现，再叠加幂等生产者避免重试引入重复。只写一句 kafkaTemplate.send(...) 就认为发送成功，是生产事故的常见起点。
