GraphRAG 解决什么问题？为什么说 Chunk 是信息孤岛、向量相似度不擅长多跳推理？什么场景下不应该上 GraphRAG？

高级开放讨论题RAG工程师AI应用开发工程师GraphRAG知识图谱多跳推理社区摘要

题目

考察点：对向量 RAG 能力边界的理解，以及图结构增强方案的选型判断力。

参考答案

要点：GraphRAG（Graph-based Retrieval-Augmented Generation）是一类把图结构用于检索增强的方案：把文档中的实体、关系和结构化上下文显式建模，查询时沿图关系收集证据，再交给大模型生成答案。传统向量 RAG 检索的是 Chunk（文本片段），GraphRAG 检索的是节点、边、路径、社区摘要。类比一下：向量 RAG 像在图书馆按语义找几页相似内容；GraphRAG 像先整理出人物关系图、事件时间线和主题目录，再沿关系线索找证据。

向量 RAG 的三类局限

  1. Chunk 是信息孤岛。切块把长文档变成可检索单元，同时拆开了跨章节的事实。以一个系统为例：定义、负责人、依赖的数据库、事故记录可能出现在不同章节，进入索引后不再共享明确的业务标识。相似度可以把相关段落排到前面，却不表示这些段落已被识别为同一系统的上下游证据——语义接近与关系完整是两件事。
  2. 向量相似度不擅长多跳推理。例如“A 系统的负责人最近参与过哪些和支付链路相关的故障复盘”，需要沿 系统 -> 负责人 -> 复盘 -> 链路 完成四次受约束的跳转。“A 系统说明”和“支付故障复盘”都可能被召回，但 Top-K 本身不会告诉检索器该沿哪条路径补齐证据。
  3. 全局性问题很难靠 Top-K 回答。“这批客户投诉主要集中在哪几类问题”“过去一年知识库里反复出现的架构风险是什么”，这类问题要求对语料做聚合与主题归纳。召回片段太少看不到整体模式，太多则 Token 成本和噪声一起爆炸；扩大 Top-K、加 rerank 仍以片段排序为中心，关系链或全局主题缺少显式表示时，问题不会随候选数增多而消失。

核心概念：知识图谱（节点/边/属性）、实体（最小业务对象，抽取质量直接决定上限，建议用 JSON Schema 强约束格式、Few-shot 覆盖正反例、限制最大实体数、强制带 source_text_span 便于溯源）、关系（把“依赖/影响/导致”显式化，是处理多跳问题的关键）、社区发现（用 Leiden/Louvain 等划分层级社区并生成摘要）、全局检索 vs 局部检索（Local Search 从已知实体向邻居扩展；Global Search 用社区摘要做 Map-Reduce 归纳主题；DRIFT Search 在实体邻居之外加入社区摘要）。

什么场景不该上 GraphRAG

  • 数据量小、问题简单：几十篇文档的规则问答，向量 RAG 加混合检索和 rerank 往往更划算。
  • 文档质量太差：源文档主语缺失、版本混乱、术语不统一、表格解析错误严重时，抽出来的图谱也很脏。向量 RAG 的错误通常是“找错几段文本”，GraphRAG 的错误可能是“整张关系网方向错了”。
  • 实时性要求极高：实体抽取、社区发现、摘要生成都会推高更新成本。
  • 团队缺少图建模和评测能力：没人负责实体是否值得建模、关系类型怎么设计、实体如何消歧时，GraphRAG 很容易变成昂贵但不可控的黑盒。

判断顺序：相关文本没进入候选集 → 先排查解析、切分和召回；候选文本已齐全但系统无法按业务关系连起来 → 再验证 GraphRAG。落地建议走“向量 RAG 基线 → 收集关系型失败案例 → 轻量图谱 → 社区发现与全局检索 → 按需 Hybrid 路由”。
