MCP（Model Context Protocol）解决什么问题？它和 Function Calling、普通 HTTP API 的区别是什么？Tools、Resources、Prompts 三类原语分别做什么？

中级简答题AI Agent开发工程师AI应用开发工程师MCP工具接入JSON-RPCFunction Calling

题目

考察点：工具接入层的协议认知，以及 Function Calling、MCP、Agent 的职责边界。

参考答案

要点：MCP（Model Context Protocol，模型上下文协议）是 MCP Client 与 MCP Server 之间的通信协议，解决的是外部工具和数据源的接入问题，常被类比成 AI 领域的“USB-C 接口”。

它要解决的痛点：同一个 Git 工具接到 Claude Desktop、Cursor 和自建 Agent 时，往往要各写一层适配；工具参数、鉴权方式或版本一变，接入它的多个客户端都得跟着改。MCP 把协议适配集中在 Server 一侧，支持该协议的 Host 通过 Client 发现并调用能力，Agent 只需理解用户问题、选择工具并组织结果。

角色划分

  • Host：用户使用的 AI 应用，如 Claude Desktop、Cursor、VS Code 的 AI 插件或自建 Agent 平台；
  • Client：位于 Host 内部，负责与 Server 交换协议消息，一个 Host 可以连接多个 Server，通常每个 Server 对应一个 Client；
  • Server：开发者主要编写的部分，向 Host 暴露文件读取、SQL 查询、GitHub Issue 查询、内部工单等能力；
  • 数据源：本地文件、数据库、内部平台、第三方 API，它们不属于 MCP 的协议角色。

三类标准原语

| 原语类型 | 作用 | 例子 |

| --- | --- | --- |

| Tools | LLM 主动调用的函数，会主动执行逻辑、可能改变外部状态 | 查询数据库、发送邮件、执行代码 |

| Resources | Agent 按需读取的只读上下文 | 本地文件、数据库记录、日志流、数据库 Schema |

| Prompts | 可复用的提示词模板 | 代码审查模板、故障报告模板 |

Tools 通常由模型选择并调用；Resources 和 Prompts 的展示与选择方式还可以由 Host、用户界面或应用逻辑决定。大多数 Server 可以先只提供 Tools，需要只读上下文或可复用任务入口时再考虑另外两类。

和 Function Calling、HTTP API 的区别

  • Function Calling（Anthropic 称为 Tool Use）是模型生成的调用意图，例如 {"name":"read_file","arguments":{"path":"/repo/README.md"}}。模型不执行任何函数，只完成“自然语言意图 → 结构化参数”的映射。
  • MCP 负责把这个意图接到外部系统：工具从哪个 Server 发现、请求如何传输、结果如何返回，底层使用 JSON-RPC 2.0（偏方法调用如 tools/call、resources/read，而 REST 更偏资源）。Server 对外暴露工具时内部仍用 JSON Schema 描述参数——JSON Schema 是数据格式，MCP 是通信协议层。
  • 普通 HTTP API 是后端确定性接口，本身不理解自然语言，中间通常需要工具执行层做映射：模型工具调用 query_order → 服务端校验参数 → 调用 GET /api/orders/{orderId}。
  • 三者关系可以概括为：Function Calling 产生命令，MCP 传递命令并连接工具，Agent 决定这条链路何时继续、何时结束。

传输方式怎么选

本地工具、本地文件、个人使用优先 stdio（Host 将它作为子进程启动，通过 stdin/stdout 交换消息；注意 stdout 是 JSON-RPC 消息通道，一行 print() 就可能破坏消息格式导致 Host 解析失败，调试日志必须写 stderr 或文件）。团队服务、远程 API、多用户访问优先 Streamable HTTP（可沿用普通 HTTP 的鉴权、负载均衡和网关运维方式）。无论哪种传输方式，涉及写操作和敏感数据时都要额外做鉴权、限流和审计。
