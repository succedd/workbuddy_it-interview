Prompt Engineering 和 Context Engineering 有什么区别？Context Engineering 具体管哪些东西？为什么「把资料放进窗口」和「模型用好资料」是两回事？

中级简答题Prompt工程师AI应用开发工程师上下文工程Prompt工程Context Rot按需加载

题目

考察点：从提示词写法升级到上下文供给的工程视角，以及上下文失效的归因能力。

参考答案

要点：两者不在同一层。

  • Prompt Engineering 处理指令本身怎么写——措辞、顺序、格式、语气，以及任务边界和约束条件。
  • Context Engineering 决定这一轮调用实际带入哪些信息，用什么结构放、什么时候放进、什么时候撤掉。Tobi Lutke 的概括是：给 LLM 补齐解决任务所需的上下文——缺少订单状态、权限边界或旧链路约束时，模型没有足够依据作出可靠判断。

打个比方：Prompt Engineering 是“告诉厨师这道菜怎么做”，Context Engineering 更像给厨师准备厨房。更工程化的类比是：它就是 LLM 的内存管理——窗口是有限内存，要决定装什么、换出什么，思路和操作系统页面置换一样。

它具体管哪些东西

  • System Prompt：API 消息里的高优先级指令。注意 .cursor/rules、AGENTS.md 是宿主读取的规则来源，和 API 角色意义上的 System Prompt 不同。
  • User Prompt：用户输入的业务数据和指令。
  • Memory：分短期（Session 内滑动窗口）和长期。长期记忆不一定就是向量库——文件、KV、关系库、图数据库都可以，关键是记录什么、何时写入、怎么更新和遗忘、召回后怎么进入当前上下文。
  • RAG & Tools：RAG 可以看成 Context Engineering 的一种具体实现，回答“检索什么、怎么检索、结果怎么放进上下文”；Tools 负责挂载工具描述、参数格式和调用结果。
  • JSON Schema / Function Calling 的参数结构和返回约束也会限制当前调用，属于上下文的一部分。
  • Token 管理手段：摘要压缩、历史剔除、Context Caching。

为什么“放进去了”还是答错

窗口变大解决不了筛选问题。Context Rot 说的是输入变长、噪声增多后模型对关键证据的利用不再稳定；Lost in the Middle 则是模型对首尾更敏感、中间容易看漏。典型场景：历史需求、接口文档、会议记录一起进窗口，而“老用户登录链路仍依赖旧版 token 校验”只有一行，模型可能读了全部资料却没把它当作方案前提。结论是：长上下文会增加筛选难度和推理成本，但退化程度取决于模型、上下文结构和任务类型——能放进去和能用好是两回事。

运行时怎么加载

  • 预检索：调用 LLM 前按 Embedding 相似度取回片段一次性放进 Prompt。只能依据调用前已知的目标排序，Agent 调用工具后发现的新线索不会出现。适合 FAQ、固定知识库问答、稳定文档审阅。
  • Just-in-Time 按需加载：先保留文件路径、数据库查询或 Web 链接等轻量引用，需要内容时再用工具读取。Claude Code 分析大型代码库就是先按目录结构、文件名收窄范围，再用 head、tail、grep 逐步读取；Anthropic 把这种分层获取称为 Progressive Disclosure。代价是调用次数和延迟增加，并依赖 glob、grep、tree 等导航能力。
  • 混合策略：实际项目更常见——确定性高的静态知识预检索，运行中动态发现的信息按需拉取（如 CLAUDE.md 预加载、具体文件内容运行时探索）。

怎么评估有没有变好：不能只靠体感。先选 20~50 条真实任务轨迹做小评测集，盯住五类指标——任务成功率、工具质量（错选/漏调/参数错误/危险操作拦截率）、上下文成本（输入输出 Token、缓存命中率、压缩后信息保留比例）、延迟指标（首 Token 延迟、p95/p99）、结果质量（幻觉率、证据引用准确率、关键字段遗漏率），并且每次只改一个变量。
