一个需要读代码、跑测试、改文件、写报告的 Agent 跑到第 30 轮时上下文接近窗口上限，开始出现「忘记初始约束」「重复做过的事」。请给出上下文治理方案。

题目

考察点：长任务上下文持久化手段的取舍，以及 Token 预算与信息保真的平衡。

参考答案

要点：三种手段分别解决不同层面的问题，实际项目里通常组合使用。

1. Compaction：窗口快满时压缩历史

连续多轮任务会把早期判断、工具结果和当前目标同时留在消息历史里，接近窗口上限时把历史压缩成摘要，再以摘要和新消息继续执行，从而实现跨窗口衔接。Anthropic 介绍过 Claude Code 的一种实现思路：摘要保留架构决策、未解决 Bug 和关键实现细节，冗余工具结果被移除，压缩后的上下文再配合最近访问的文件恢复任务状态。

难点在取舍——保留太多压缩没意义，保留太少关键上下文又丢了。比较实际的做法是拿复杂 Agent 轨迹反复调压缩 Prompt，先保证重要信息别漏，再逐步删掉冗余内容；这不是一次能写准的。

还有一个更轻量的手段：清理工具结果。工具调用过了、结果也消化了，就没必要保留完整原始输出。Anthropic 的 context editing / tool-result clearing 能在保留 tool_use 记录的同时清理旧的 tool_result，触发阈值需按业务负载测试。

2. Structured Note-taking：让 Agent 记笔记

让 Agent 把关键进展写到外部文件里（比如 NOTES.md、to-do list），上下文重置之后再读取这些笔记继续工作，和人类工程师写技术备忘是同一个道理。Claude 玩 Pokémon 的例子很典型：在数千轮游戏步骤里，它自己维护了数值追踪（“过去 1234 步我在 1 号道路训练皮卡丘，已升 8 级，距离目标还差 2 级”），还自发建立了地图、成就清单和战斗策略笔记；上下文重置之后这些笔记还能被重新读取，所以才能跨好几个小时持续推进。Anthropic 也在 Sonnet 4.5 推出 Memory Tool 公测，用文件系统持久化建立跨会话知识库。

3. Sub-agent：别让一个 Agent 扛所有状态

检索或代码阅读交给独立上下文中的 Sub-agent，主 Agent 只接收证据汇总。子 Agent 即使完成数万 Token 的探索，返回摘要通常只有 1000 到 2000 Token，详细搜索过程不会长期占用主窗口。是否使用取决于任务能否拆分、子任务依赖关系，以及汇总时是否会丢失关键证据。

怎么选

| 技术 | 适用场景 |

| --- | --- |

| Compaction | 需要持续对话的长流程，重点是保持上下文连贯 |

| Note-taking | 迭代式开发、有清晰里程碑、多步推进的任务 |

| Sub-agents | 复杂研究、需要并行探索、最终要汇总结果的任务 |

配套的 Token 预算约束

单次调用内按优先级排序：静态规则（System Prompt）→ 当前目标 → 证据（RAG 片段）→ 记忆 → 工具结果 → 历史摘要，最后按模型 Token 限额截断或裁剪。预算不够时按顺序减少 RAG Top-K、合并重复片段、摘要或截断长字段，一轮塞不下的任务再拆成分批或两阶段生成——而不是继续把窗口塞满。

工具结果不要一股脑塞：要提前设计是保留原文、写入摘要还是后续轮次清理，否则解析和回放阶段会留下大量难以处理的结果。

最后两条工程原则：高信噪比比信息量更重要；长任务要主动清理过期状态。另外从可回放的基线开始——先记录每一轮的上下文组成（静态规则、目标、证据、记忆、工具结果、历史摘要各占多少），否则失败样本只留下一个分数，没有证据可查。
