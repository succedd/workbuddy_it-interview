什么是接口幂等？分布式系统里保证幂等有哪些常见方案，如何选型？

中级简答题后端开发工程师Java后端工程师幂等唯一索引去重表状态机

题目

考察点：幂等的定义、触发来源与工程化落地手段。

参考答案

要点：

1. 什么是幂等

幂等（idempotency）源自数学：一个操作执行一次和执行多次，对服务端资源产生的效果相同。接口语义上指多次相同请求对资源的影响与执行一次一致，资金类接口通常还要求返回稳定的业务结果。注意区分：去重是防止重复执行，幂等是允许重复请求到达但保证结果一致，两者常配合使用。

2. 重复请求从哪来

网络波动、用户重复点击、客户端/网关超时重试、消息重复投递；响应越慢，重复请求概率越高。前端按钮置灰只能降低概率，真正的幂等边界必须在服务端。

3. 常见方案对比

| 方案 | 原理 | 适用场景 | 注意点 |

| --- | --- | --- | --- |

| 唯一请求 ID / 业务唯一键 | 请求携带幂等号，服务端识别重复 | 通用 | 幂等号本身要保证唯一 |

| 数据库唯一索引 | 重复插入抛异常 | 插入/创建类 | 只覆盖插入，不能承载全部逻辑 |

| 去重表 | 请求信息入表，唯一索引标识唯一性 | 支付回调等 | 去重表插入要与业务操作在同一个本地事务里，否则会出现「去重记录已写、业务未完成」 |

| 乐观锁（版本号） | update ... where id=? and version=? | 更新类 | 冲突频繁会不断失败重试；资金类不建议盲目自动重试 |

| 悲观锁 / SELECT ... FOR UPDATE | 数据库排他锁串行化 | 低并发临界区 | 必须命中索引，否则可能近似锁全表；注意死锁 |

| 分布式锁 | 跨 JVM 串行化同一资源操作 | 需保护临界区 | 性能与可靠性需评估 |

| 状态机 | 状态流转控制，已处理状态不再处理 | 订单、支付 | 防止重复执行与状态回退 |

4. 选型优先级

1）能用业务唯一键解决的，优先用业务唯一键；2）能用数据库唯一索引兜底的，不要只依赖缓存；3）涉及状态流转的，用状态机防止重复执行和状态回退；4）需要保护同一业务资源临界区时，再考虑分布式锁；5）高风险资金场景要多层兜底，不要押宝单一机制。

实践中更常见的是组合方案：业务唯一键 / 幂等号负责识别重复请求，唯一索引或去重表负责兜底，状态机防止状态回退，分布式锁只在需要串行化同一业务资源时使用。
