分库分表的垂直拆分与水平拆分分别解决什么问题？分片键应该怎么选？

初级简答题数据库架构师后端开发工程师分库分表分片键哈希分片水平拆分

题目

考察点：拆分维度、分片算法与分片键选择。

参考答案

要点：

1. 先明确分库分表不是第一步

读写分离解决的是读并发，不解决存储问题；分库分表主要解决存储与容量问题。决定前要先确认：慢 SQL、索引、分页、缓存、读写分离是否已优化；单表数据量、单库容量、连接数、写入 QPS 是否真的接近瓶颈；核心查询能否被一个稳定的分片键覆盖。常见触发条件是单表数据量到千万级、备份时间越来越长。

2. 四个概念

| 维度 | 含义 | 例子 |

| --- | --- | --- |

| 垂直分库 | 按业务把单一库拆到不同数据库 | 用户表/订单表/商品表 → 用户库/订单库/商品库 |

| 水平分库 | 同一张表按规则拆到不同库 | 订单表按买家 ID 拆到 2 个库 |

| 垂直分表 | 按列拆分，把宽表拆成多张表 | 用户信息表拆出扩展信息表 |

| 水平分表 | 按行拆分，解决单表行数过大 | 用户表拆成 user_0、user_1… |

3. 常见分片算法

  • 哈希分片：适合随机读写、分布均匀，但对动态伸缩不友好（hash(key) % 32 扩到 % 64 会导致大量数据重新映射），也不适合范围查询。
  • 范围分片：按区间（时间、ID 段）分配，适合范围查询，但容易产生热点。
  • 一致性哈希分片：缓解动态伸缩问题，更适合 KV/缓存场景。
  • 衍生策略：映射表路由（灵活但需额外维护路由数据）、地域路由。

4. 分片键怎么选

四个特性：共性（覆盖绝大多数查询）、离散性（均匀分布，避免倾斜与热点）、稳定性（值不变，避免数据迁移）、扩展性（支持动态增减分片）。四者难以同时满足，需要权衡。

  • 订单系统应优先照顾用户订单列表这类高频范围查询，而不是只按 order_id 分片，否则同一用户订单会散落到多个分片，分页排序都要跨分片。
  • 可把路由信息写进业务 ID（订单 ID 中保留一段 buyer_route），或维护 order_id → buyer_route 路由表。
  • 不要直接取用户 ID 后几位当路由键：Snowflake、自增段等生成器低位不一定均匀，通常要先哈希再取模。
