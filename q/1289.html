【场景】主从读写分离后，用户刚下单就查不到自己的订单，怎么解决？

中级场景题数据库架构师后端开发工程师读写分离主从延迟read-your-writes半同步复制

题目

考察点：复制延迟与 read-your-writes 一致性设计。

参考答案

要点：

1. 现象本质：主从同步延迟

读写分离把写请求交给主库、读请求分摊到只读副本，核心收益是提升读扩展能力。但 MySQL 默认是异步复制，写主库后同步到从库需要时间，这段从库落后的时间就是主从同步延迟；下单后立刻查询走了从库，就会出现「自己刚写的数据自己读不到」。

2. 主从复制链路（便于定位）

1）主库把数据变化写入 binlog；2）从库 I/O receiver 线程接收 binlog 事件写入 relay log；3）从库 applier 线程读取 relay log 并应用。对应三个时间点：T1 主库写完 binlog、T2 从库 I/O 线程收到并写入 relay log、T3 从库 applier 应用完成。T2−T1 反映网络与接收效率，T3−T2 反映回放速度。

3. 解法

  • 强制读主库：对极少数必须强一致的场景通过 Hint 强制路由到主库（ShardingSphere 5.x 用 HintManager + setWriteRouteOnly()，4.x 为 setMasterRouteOnly()）。严禁大范围使用：读写分离本意是给主库减负，大量读回退主库会在秒杀/大促时压垮主库。
  • 按会话/链路做 read-your-writes 路由：同一业务事务里先写后读，后续读继续走主库；可按用户会话、请求链路或业务标记短时间读主库。
  • 等待从库追上指定位点：使用 GTID 时，写成功后取本次事务 GTID，在从库调用 WAIT_FOR_EXECUTED_GTID_SET(gtid_set, timeout)；SOURCE_POS_WAIT() 可等待副本读到并应用到指定 binlog 位置。代价是增加读延迟与实现复杂度。

4. 两个常见误区

  • 半同步复制解决的是数据安全性（主库返回前等至少一个从库收到事务事件），不等于从库已完成应用，不能保证写后立刻读从库一定读到最新值。
  • 从库不是免费的读能力：复杂报表、全表扫描、大分页、慢 SQL 打到从库会抢占资源、影响 applier 执行，反过来加重延迟，因此仍要治理慢 SQL、索引与报表流量。
