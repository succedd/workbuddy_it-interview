MyBatis 用 for 循环单条 insert 插入十万条数据非常慢，如何优化？

中级简答题Java后端工程师后端开发工程师MyBatis批量插入ExecutorTypeforeach

题目

考察点：批量写入的两种手段与 ExecutorType 的取舍。

参考答案

要点：

1. 为什么慢

for 循环里每条 insert 都是一次独立 SQL 发送加一次提交，十万条就是十万次网络往返与 SQL 解析开销，耗时主要花在网络 I/O 与往返次数上。

2. 手段一：SQL 层面合并（<foreach> 批量插入）

把 N 条数据拼成一条多值 insert ... values (...),(...)，用 <foreach separator=","> 生成多组占位符，把 N 次往返压成 1 次。

  • 用 #{} 而不是 ${}，让 MyBatis 生成 PreparedStatement 占位符，避免 SQL 注入和重复解析开销。
  • 一次拼的行数受 max_allowed_packet 与 SQL 长度上限约束，通常按 500～1000 条分批提交，而不是一次拼十万行。

3. 手段二：会话层面用 BATCH 执行器

MyBatis 的 ExecutorType 有三种：SIMPLE（默认，每次新建 PreparedStatement）、REUSE（复用 PreparedStatement）、BATCH（把 update 语句攒起来，遇到 SELECT 或显式 flush/commit 才发送，对应 JDBC 的 addBatch()/executeBatch()）。

用 openSession(ExecutorType.BATCH) 拿到会话后循环 insert，最后必须 commit() 才落库。注意：

  • BATCH 模式下不显式 commit 就不会写入，这是最常见的坑。
  • BATCH 模式下 insert 返回的受影响行数不可靠；需要主键时要配合 selectKey 或改用 <foreach>。

4. 选型建议

  • 十万级批量导入：优先 <foreach> 分批（每批 500～1000）+ MySQL 驱动 rewriteBatchedStatements=true，吞吐最高。
  • 混合读写、需要逐条反馈：用 ExecutorType.BATCH。
  • 无论哪种都要分批提交、避免超长事务（否则加剧主从延迟、放大锁范围）。
