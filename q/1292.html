【故障排查】分库分表后某类查询突然变慢，日志里出现大量「全分片广播」，怎么定位？

高级故障排查题数据库架构师后端架构师分库分表读扩散分片键数据倾斜

题目

考察点：非分片键查询、读扩散与分片热点的排查思路。

参考答案

要点：

1. 现象特征

「全分片广播」意味着中间件无法从 SQL 解析出分片键，只能把语句发到所有分片再合并结果。典型表现是：单条 SQL 耗时随分片数线性增长，数据库连接数与 CPU 升高，慢查询集中在同一类接口上。

2. 三步定位

第一步：确认分片键是否出现在查询条件里。 最常见原因是查询条件只含非分片键字段（如按 buyer_id 分片却用 order_id 点查）。此时看路由到的分片数：应为 1、实际为 N，就是读扩散。注意 ShardingSphere 的 binding table 有前提——同一组表使用相同分片规则且 SQL 关联条件带分片键，否则仍会跨分片路由。

第二步：确认是不是「必需跨分片」的查询形态。 即使带了分片键，group by、order by、跨分片分页仍需要多分片汇总排序；查第 1000 页时每个分片都要返回前 N 页候选再合并截取，分片越多放大倍数越高。这不是配置错误，而是查询形态与分片模型不匹配。

第三步：排查分片热点与数据倾斜。 若某些分片明显更忙，说明分片键离散性不足：取用户 ID 低位取模、连续自增键、时间递增键、大租户都会形成热点。先看分片级监控的 QPS 与数据量分布是否均匀。

3. 对应解决手段

| 场景 | 方案 |

| --- | --- |

| 非分片键高频点查 | 维护 order_id → buyer_route 路由表，或把路由信息写进业务 ID 的固定位置 |

| 后台按条件检索 | 冗余索引表 / 读模型，或交给 Elasticsearch、宽表，避免打核心链路 |

| 跨分片聚合与深分页 | 大结果集外置到搜索引擎/离线报表；核心链路限制分页深度或改用游标分页 |

| 数据倾斜/热点 | 换离散性更好的分片键，或对大租户单独拆分；避免用低位不均匀的 ID 直接取模 |

| 分片规则 | 固定逻辑分片（bucket）+ 映射，扩容只迁 bucket 而非改业务取模规则 |

4. 长期治理

上线前按主要查询路径设计分片键（共性、离散性、稳定性、扩展性需权衡）；业务天然有多条高频查询路径时，应通过冗余读模型或搜索系统分流；并建立分片级监控，保留能快速确认「某条 SQL 路由到几个分片」的手段。
