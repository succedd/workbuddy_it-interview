场景题：列表滚动时的入场动画在低端机上卡顿掉帧。为什么把动画从 left/top 改成 transform/opacity 就顺了？请据此给出优化清单。

高级场景题前端开发工程师UI/UX设计师CSS动画性能transformwill-change合成

题目

考察点：把「渲染瀑布」理论落到 CSS 动画优化上的能力。

参考答案

关键在渲染瀑布。MDN 把浏览器把属性变化画到屏幕上的过程称为「渲染瀑布」，依次是：Recalculate Style → Layout → Paint → Composition（合成）。整条链路必须在一帧内跑完；追求 60fps 意味着每帧只有 16.7ms 用来执行脚本、重算样式、布局与绘制。

不同属性的代价不同（MDN 分类）：

  • 影响几何或位置的属性（left、margin-left、width、font-size…）触发 样式重算 + Layout（重排）+ Paint，最贵；
  • 不影响几何、也不独立成层的属性（color）只需 样式重算 + Paint；
  • 在独立图层中渲染的属性（transform、opacity）连 Paint 都免了，只在 Composition 阶段处理，因此最省。

这就是关键：left/top 每帧都要重新布局与绘制，而 transform/opacity 交给合成器，几乎不占主线程。

优化清单：

  1. 位移用 transform:translate()、透明度用 opacity，避免对 left/top/width/height/margin 做动画。
  2. 用 will-change:transform（或 translateZ(0)）提前把元素提升为独立图层，但用完即撤，滥用会导致图层与显存暴涨。
  3. 用 requestAnimationFrame 驱动 JS 动画，与浏览器帧节奏对齐；避免在滚动/动画回调里读写布局属性，造成强制同步布局。
  4. 用 IntersectionObserver 替代 scroll 事件做「进入视口才播动画」，避免高频回调。
  5. 用 Performance 面板录制，区分瓶颈是「脚本（主线程长任务）」还是「合成/光栅化」，并关注掉帧与 Long Task。

结论：动画只碰合成器友好的 transform/opacity，把昂贵属性留在静止状态。
