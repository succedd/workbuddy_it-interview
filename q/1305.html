故障排查：SPA 长期打开后标签页内存持续上涨、最终卡死。请说明 JS 的垃圾回收原理，并给出定位内存泄漏的步骤与常见泄漏源。

高级故障排查题前端开发工程师前端架构师浏览器原理垃圾回收内存泄漏WeakMapDevTools

题目

考察点：垃圾回收算法演进与内存泄漏的实战排查方法。

参考答案

回收原理：JavaScript 在创建对象时自动分配内存、不再使用时自动释放（垃圾回收）。早期「引用计数」只需看有没有引用，但无法处理循环引用——两个对象互相引用，函数返回后本应回收却因各自仍有引用而泄漏；现代引擎统一采用标记清除（mark-and-sweep）：从根（全局对象）出发标记所有可达对象，回收不可达者，因此循环引用不再是问题。近年的「分代 / 增量 / 并发 / 并行」都是该算法的实现优化，并非换算法，且 JS 无法编程式触发 GC。

排查步骤：

  1. 先确认是不是真泄漏：在 DevTools 的 Memory 面板反复执行「操作 → 手动 GC → 拍堆快照」，比较多次快照的 retained size 是否阶梯式上涨；Performance 面板的 Memory 曲线是否「只涨不落」。
  2. 对比快照定位增长对象：取 Snapshot A/B，用 Comparison 视图看新增且未释放的对象类型，沿 Retainers（引用链） 向上找出「谁还在引用它」。
  3. 搜 detached：检查是否持有已从页面移除的 DOM 节点（Detached DOM）。
  4. 结合 Allocation instrumentation on timeline 定位到具体分配点与调用栈。

常见泄漏源：

  • 事件监听器未解绑，尤其绑在 window / document / 全局元素上的，组件销毁后仍持有回调及其闭包；
  • 全局变量或缓存无上限：数据一直 push 进模块级数组、Map 而不清理；
  • 定时器与长连接：setInterval、requestAnimationFrame、WebSocket 未在卸载时清除/关闭；
  • 闭包内部引用大对象或 DOM；
  • Detached DOM：JS 变量持有已移除节点；
  • 订阅未取消：长请求未 abort（缺 AbortController）。

缓解工具：长生命周期映射用 WeakMap / WeakSet（键为弱引用，键不可达即可回收；注意它们不可迭代，也无法观察存活性）；缓存系统可用 WeakRef + FinalizationRegistry 做非关键清理，但 MDN 明确不能依赖其回调时机。框架里则要在卸载钩子中移除监听、清定时器、abort 请求。
