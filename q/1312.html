题目

TCP Keepalive 是如何工作的？「半打开连接」是怎么产生的，如何清理？RST 报文一般出现在哪些场景？

参考答案

TCP Keepalive 解决的问题是：连接长时间没有数据往来时，怎么判断对端还在不在，要不要回收资源。注意它与 HTTP 的 Keep-Alive 完全不是一回事——后者是应用层机制，管的是「一个 TCP 连接能不能被多个 HTTP 请求复用」。

工作流程与三参数：连接空闲超过 tcp_keepalive_time（Linux 默认 7200 秒）后，内核自动发探测报文；对端在线则回 ACK，计时器重置；对端无响应则每隔 tcp_keepalive_intvl（默认 75 秒）重发一次，最多 tcp_keepalive_probes（默认 9）次；仍无响应就判定连接已死，关闭并释放资源。按默认值，从空闲到判死最长约 7200 + 75×9 ≈ 7875 秒。特别要注意：Keepalive 默认是关闭的，应用必须通过 SO_KEEPALIVE 显式开启。

半打开连接如何产生：客户端突然断电、网线被拔、进程崩溃，服务端毫不知情——TCP 没有「忙音」，这条连接在服务端看来还是 ESTABLISHED，实际对端已经没了，这就是半打开（Half-Open）连接。它白白占用内存中的 TCB 资源，堆积多了会耗尽连接资源。

如何清理：

  1. 对端曾经崩溃但已重启：收到数据或探测包时，因内核已没有这条连接的上下文，直接回 RST，本端立即关闭；
  2. 对端不可达（崩溃未恢复或网络中断）：Keepalive 探测连续 probes 次无响应后，内核判死并释放；
  3. NAT 网关的会话超时会清掉空闲连接的映射表项，效果等同于对端不可达，所以 keepalive 间隔要小于中间设备的空闲超时。

RST 的典型场景还包括：访问未监听的端口（连接直接被拒绝）、应用异常终止连接（缓冲区还有数据就 close）、全连接队列溢出且 tcp_abort_on_overflow=1 时服务端直接回 RST。

Keepalive 的局限与应用层心跳：默认 2 小时才开始探测太慢；探测包由内核处理，只能证明对端 TCP 栈活着，不能证明应用线程池、事件循环、数据库依赖正常。所以生产环境通常以应用层心跳为主（WebSocket 的 Ping/Pong、gRPC keepalive ping、业务自定义心跳），Keepalive 只作兜底清理死连接。心跳间隔要结合连接规模、NAT/LB 空闲超时和可接受的故障发现时间综合设置，不是越频繁越好。
