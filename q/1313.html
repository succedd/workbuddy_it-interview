题目

BIO、NIO、AIO 三种 IO 模型有什么区别？NIO 的 Channel、Buffer、Selector 是如何协作的？

参考答案

三种模型的演进主线是：把「等待数据就绪」的时间从业务线程中逐步剥离。应用程序发起 IO 调用后都要经历两个阶段——内核等待数据准备好、内核把数据从内核空间拷贝到用户空间，三者的区别就在于这两个阶段线程处于什么状态。

BIO（同步阻塞 IO）：发起 read 后线程一直阻塞，直到内核把数据拷贝到用户空间才返回。实现上通常「每个连接一个线程」，连接数少时简单可靠；面对十万级连接时，线程的创建与切换开销不可承受，这是它的天花板。

NIO（同步非阻塞/多路复用）：Java 1.4 引入 java.nio 包，提供 Channel、Buffer、Selector 三大组件。注意概念辨析：单纯把 Channel 设为非阻塞模式对应「同步非阻塞 IO」，线程要不断轮询 read，空转消耗 CPU；而基于 SelectableChannel + Selector 的网络编程方式对应「IO 多路复用模型」，线程先发起 select 调用询问内核哪些连接就绪，就绪后再 read，read 的拷贝阶段仍然阻塞——它通过减少无效系统调用降低了 CPU 消耗。

三大组件如何协作：

  1. Channel（通道）：数据的传输通道，双向可读写，对应文件、Socket 等实体；
  2. Buffer（缓冲区）：NIO 面向缓冲区读写，读操作把 Channel 中的数据填入 Buffer，写操作把 Buffer 的数据写入 Channel。Buffer 内部有 capacity、limit、position、mark 四个指针，创建后默认写模式，flip() 切换到读模式，clear()/compact() 切回写模式；
  3. Selector（选择器/多路复用器）：一个线程监控多个 Channel 的就绪事件（连接、可读、可写），事件就绪才分配处理。Selector 负责报告事件是否就绪，不负责分配处理线程。

协作流程：每个客户端连接对应一个 Channel，全部注册到 Selector 上；单线程调用 select() 阻塞等待，返回就绪事件集合后，遍历事件从关联的 Channel 读入 Buffer 处理。这样少量线程即可服务大量连接，这正是 Netty、Tomcat NIO 连接器的底层模型。

AIO（异步 IO）：Java 7 的 NIO.2 引入异步通道 API。发起 read 后立即返回，等待与拷贝两个阶段全部由内核完成，完成后通过 CompletionHandler 回调或 Future 取结果，全程无阻塞点。但 Linux 上的实现并不成熟，性能提升有限，Netty 尝试过 AIO 后又放弃，目前应用远不如 NIO 广泛。

回答要点小结：按「阻塞点在哪里」对比三者——BIO 全程阻塞、NIO 阻塞在 select 与拷贝、AIO 无阻塞点；再讲三大组件分工与协作流程。可补一句：NIO 不一定比 BIO 快，它的优势体现在高并发、高延迟网络环境，连接数少时 NIO 的复杂性反而不划算。
