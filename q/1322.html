InnoDB 的 Change Buffer 是如何优化二级索引写入的？merge 在什么时机触发？为什么唯一索引用不了它？

初级简答题后端开发工程师DBA数据库管理员数据库架构师MySQLInnoDBChange Buffer二级索引随机IO

题目

考察点：对 InnoDB 写路径优化的理解，能否说清 Change Buffer 的适用条件、merge 时机与唯一索引限制的原因。

参考答案

是什么

Change Buffer 是 InnoDB 的一种特殊数据结构，用于缓存目标二级索引页不在 Buffer Pool 中的那部分变更（INSERT、UPDATE、DELETE 产生的 DML）。它在内存中占用 Buffer Pool 的一部分，持久化后属于系统表空间，受 innodb_change_buffering 参数控制。

为什么能优化写

  • 二级索引通常非唯一，插入位置由索引列值决定，往往是随机顺序；删除和更新也可能命中索引树上不相邻的页。没有 Change Buffer 时，每次变更都要把索引页从磁盘读进来再改，是典型的随机读 IO。
  • 有了 Change Buffer，变更先记下来，把「每次随机读一个页」变成「之后按页批量合并」，对写密集、IO 瓶颈型负载（如批量插入）收益明显。

merge 的触发时机

  • 目标索引页因其他读操作被加载进 Buffer Pool 时，把缓冲的变更合并到该页，之后随脏页机制刷盘；
  • InnoDB 主线程在系统较空闲时以及慢关闭（slow shutdown）过程中执行 merge 并把更新后的索引页写入磁盘；
  • 影响行数多、二级索引多时，merge 可能持续数小时，期间磁盘 IO 升高，甚至可能延续到事务提交之后、服务器重启之后。

为什么唯一索引用不了

唯一索引插入前必须检查唯一性冲突，这个检查要求先把目标页读到内存才能和已有记录比较，变更没法「先记账后见面」，Change Buffer 省掉的那次随机读就省不掉了，所以只对非唯一二级索引生效。另外含降序索引列的二级索引也不支持。

代价与权衡：Change Buffer 占用 Buffer Pool 内存，会挤占数据页缓存；如果工作集几乎全部装得进内存，页基本常驻、变更直接改内存即可，此时收益有限甚至可以关闭。
