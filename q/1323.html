应用日志大量出现「Connection is not available, request timed out after 30000ms」，结合 HikariCP 的工作原理与关键参数，说说你的排查思路？

中级场景排查题后端开发工程师Java后端工程师DBA数据库管理员连接池HikariCP连接泄漏数据库调优

题目

考察点：对连接池借还模型、核心参数与常见故障（池耗尽、连接泄漏、慢 SQL 占用）的综合排查能力。

参考答案

先讲清楚连接池的工作原理

连接池在应用与数据库之间维护一批长连接：应用线程通过 getConnection() 从池中借出连接，用完调用 close() 并不是真关闭，而是归还回池。池内部维护三部分：空闲连接队列（可立即借出）、借出连接集合（正在使用）、等待队列（拿不到连接的线程排队，最多等 connectionTimeout，HikariCP 默认 30000ms）。报错里的 30000ms 正是排队超时——说明池里的连接全部被占用了。

排查步骤

  1. 确认是否连接泄漏：把 leakDetectionThreshold 设为 2000（最低 2 秒，默认 0 表示关闭），借出超过阈值未归还的连接会打印「apparent connection leak」并带获取时的调用栈，据此定位到「借了不还」的代码，常见于忘记在 finally 中 close、异常路径漏归还。
  2. 检查慢 SQL 与长事务：连接被占住不一定是泄漏，也可能是慢查询、大批量导出、未提交的事务把借出时间拉长。去数据库侧查 information_schema.innodb_trx 与慢日志，对齐超时时间点。
  3. 评估池容量与流量：maximumPoolSize 默认只有 10，突发并发下可能确实不够；但也不要盲目调大——官方给出参考公式「连接数 ≈ CPU 核数 × 2 + 有效磁盘数」，池过大会加剧上下文切换和数据库端争用，实测反而更慢。
  4. 核对池形态：HikariCP 建议保持固定大小池（不设 minimumIdle，默认等于 maximumPoolSize），频繁扩缩会带来建连开销；同时检查 maxLifetime（默认 30 分钟）要短于数据库侧连接上限，避免用到被服务端掐断的连接。

答题要点：先解释报错对应的机制（等待队列 + connectionTimeout 超时），再按泄漏 → 慢 SQL → 容量 → 配置的顺序排查，最后点出「池不是越大越好」。
