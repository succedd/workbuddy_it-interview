Redis Cluster 节点间如何通过 gossip 协议交换状态？主观下线（PFail）到客观下线（Fail）、再到从节点选举的完整流程是怎样的？

高级简答题后端开发工程师DBA数据库管理员数据库架构师RedisRedis Clustergossip故障转移高可用

题目

考察点：对 Redis Cluster 去中心化通信机制与故障转移流程的完整掌握，注意与哨兵机制区分。

参考答案

gossip：去中心化的状态传播

Cluster 节点间通过专门的集群总线通信（端口 = 业务端口 + 10000，如 6379 对应 16379），消息主要有四种：

  • PING/PONG：每个节点每秒向随机选出的节点发 PING，消息里携带自己已知的集群状态（哪些节点存活、槽的归属），对方以 PONG 回应并同样携带自己的状态。经过多轮交换，全集群视图收敛一致。
  • MEET：新节点入群时，由已有节点向它发 MEET 打招呼，新节点再顺着 gossip 网络认识其他节点。
  • FAIL：节点被判定彻底下线后，向全集群广播 FAIL，统一更新状态。

代价是消息量随节点数平方级增长，官方建议主节点不超过 1000 个。

故障转移：两阶段下线 + 类 Raft 选举

  1. 主观下线（PFail）：节点 A 在 cluster-node-timeout（默认 15 秒）内没收到节点 B 的 PONG 回复，只是 A 单方面的怀疑——可能只是 A、B 之间网络抖动。这个判断随 gossip 消息扩散。
  2. 客观下线（Fail）：当半数以上持有槽的主节点都把 B 标记为 PFail 时，B 升级为客观下线，由节点广播 FAIL 消息。两阶段设计防止单点误判把健康节点拉下马。
  3. 从节点选举：若下线的是主节点，其从节点先做资格检查（失联过久、数据陈旧的没有资格，由 cluster-replica-validity-factor 控制），然后按与主节点的复制进度排序——数据越新等待时间越短、越先发起选举，向所有持有槽的主节点拉票。只有持有槽的主节点有投票权，每个主节点一轮只能投一票。拿到半数以上选票的从节点晋升为新主，通过 gossip 广播接管槽，客户端后续经 MOVED 重定向到新主。

注意：这套下线检测和选举都在数据节点内部完成，与哨兵的独立进程方案是两条路线；且主从复制是异步的，故障转移可能丢失主节点刚写入、尚未同步的数据。
