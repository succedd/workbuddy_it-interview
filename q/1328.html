WebSocket 的「HTTP 握手升级」是怎么完成的？和 SSE 有什么区别？实时推送方案该怎么选？

初级简答题前端开发工程师Web全栈工程师全栈开发工程师网络WebSocketSSE实时通信HTTP

题目

考察点：对 WebSocket 101 Switching Protocols 升级握手原理的理解，以及与 SSE 的工程化选型能力。

参考答案

握手升级原理：WebSocket 借用一次 HTTP 请求完成协议升级。客户端发送 GET 请求（必须 HTTP/1.1+），带 Upgrade: websocket、Connection: Upgrade，浏览器自动附上随机 Sec-WebSocket-Key 与 Sec-WebSocket-Version: 13。服务端同意升级则返回 101 Switching Protocols，其中 Sec-WebSocket-Accept 必须由 Key 推导：Key + 固定魔串 258EAFA5-E914-47DA-95CA-C5AB0DC85B11 → SHA-1 → base64。MDN 解释这个看似繁琐的步骤是为了让客户端明确确认「服务端真的懂 WebSocket」，避免把帧数据当 HTTP 解析的安全问题。握手成功后这条 TCP 连接不再是 HTTP，切换为 WebSocket 帧协议，进入全双工通信。另外浏览器请求必带 Origin 头，服务端应校验以防跨站 WebSocket 劫持（CSWH）。

SSE（Server-Sent Events）：基于普通 HTTP 长连接，EventSource 只能服务器→客户端单向推送文本事件流。优点：零协议改造、普通网关/代理直接可用、浏览器自动重连并携带 Last-Event-ID 续传。

对比选型：

| 维度 | WebSocket | SSE |

|---|---|---|

| 通信方向 | 双向全双工 | 单向推送 |

| 数据格式 | 文本 + 二进制 | 仅文本 |

| 断线重连 | 需自行实现心跳/重连 | 浏览器内置 |

| 基础设施 | 网关需支持 Upgrade | 普通 HTTP 即可 |

怎么选：只需服务器推送（站内通知、行情、日志流、AI 流式输出）→ SSE 更轻；需要双向实时（聊天、协同编辑、联机游戏）→ WebSocket；更复杂的需求（不可靠传输、乱序、多条流）可关注 WebTransport——MDN 将其定位为 WebSocket 的演进方向。两个实践细节：WebSocket 不支持背压，消费不过来会堆内存；页面有未关闭的 WebSocket 连接时可能不进入 bfcache，用完应 close()。
