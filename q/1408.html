GitHub Actions 的核心概念（Workflow/Job/Step/Runner/Matrix）是什么？如何设计一条高质量 CI 流水线？

中级简答题DevOps工程师CI/CD工程师前端开发工程师后端开发工程师CI/CDGitHub ActionsMatrix缓存

题目

考察 Actions 概念模型与 CI 工程实践。

参考答案

结论

GitHub Actions 是内置 CI/CD：Workflow（.github/workflows/*.yml，由 on: 触发：push/PR/schedule/workflow_dispatch）→ 包含一个或多个 Job（默认并行，needs 声明依赖串行）→ Job 由 Step 组成（复用 action 或 run shell）→ 执行环境是 Runner（GitHub 托管 ubuntu/windows/macos 或 self-hosted）。

高质量流水线设计

  1. 分层：PR 只跑 lint + 单测 + 类型检查（分钟级反馈）；合入 main 再跑构建/集成/部署——重活不塞进每次 push；
  2. Matrix：strategy.matrix 一份 yml 跑 node 18/20/22 × 多 OS 组合，避免复制粘贴多个 job；fail-fast 控制是否一挂全停；
  3. 缓存：actions/cache 或 setup-node 的 cache: npm，key 绑 lockfile 哈希——依赖安装常占 CI 时间大头；
  4. 安全：Job 级 permissions: 最小化（默认给只读）；第三方 action 用 commit SHA 锁版本防投毒；secrets 不进日志、pull_request_target 对 fork PR 慎用；
  5. 制品与环境：Job 间传文件用 actions/upload-artifact + download-artifact；部署用 environments + 必需审批人做人工门禁。

常见坑

  • schedule 的 cron 用 UTC，且 workflow 必须存在于默认分支才生效；
  • 同一 Job 内 step 共享工作区，跨 Job 不共享——传数据必须 artifacts；
  • runner 磁盘/超时：大构建注意 timeout-minutes 与清理，否则排队与白跑。
对比记忆：GitLab CI 是 stage/job + .gitlab-ci.yml，Jenkins 是 pipeline/agent + Jenkinsfile；面试常问三者差异与 self-hosted runner 的适用场景（内网资源、GPU、缓存复用）。
