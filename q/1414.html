MongoDB 文档建模时，「内嵌（Embedded）」和「引用（Reference）」该如何取舍？请以 1:1、1:N、N:N 三种关系举例说明。

中级场景题后端开发工程师Java后端工程师文档建模内嵌引用反范式化MongoDB

题目

考察点：MongoDB 反范式化建模的核心决策——内嵌还是引用，能否结合具体关系给出合理方案，是区分「会用」和「用得好」的关键场景题。

参考答案

要点：

  • 内嵌（Embedded）：把关联数据作为子文档/数组直接放进父文档。优点是不需要 JOIN、一次查询即可拿到完整数据、可原子更新；适合「强关联、一起读写、规模可控」的关系。例：1:1 的用户与用户资料、1:N 的订单与订单项（订单项数组内嵌在订单里）。
  • 引用（Reference）：在文档里只存对方文档的 _id（必要时加 dbref），靠应用层或 $lookup 再去取。适合「会被独立访问」「规模会无限增长」「多对多」的场景。例：N:N 的用户与课程，用单独的中间集合或双方维护 id 数组；1:N 中「N 会无限膨胀」的评论列表（内嵌会导致文档超 16MB 上限）应改为引用+单独集合。
  • 1:1：几乎总是内嵌（除非子文档极大或需单独权限）。
  • 1:N：N 较小且整体读取用内嵌；N 巨大或需独立查询/分页用引用。
  • N:N：用引用 + 中间集合（或双方 id 数组），避免双重海量内嵌。
  • 反范式化代价：内嵌带来冗余，更新时要同步多份（如作者名内嵌到文章后改名需批量更新），需在「读性能」与「写一致性成本」间权衡。
