什么情况下 MongoDB 需要引入分片（Sharding）？shard key 的选择有哪些核心原则？如果 shard key 选错（如自增 _id 或低基数字段），会造成什么后果？

题目

考察点：分片架构的触发条件、shard key 设计方法论与选错后果，是 MongoDB 高阶段位的系统设计题。

参考答案

要点（何时分片）：

  • 数据量超过单机磁盘/内存上限；② 写吞吐达到单节点瓶颈（单 primary 写入受限）；③ 出现无法靠加索引/优化查询解决的热点；④ 需要把数据就近部署到不同区域。分片前应先穷尽索引优化、读写分离、升级硬件等手段。

要点（shard key 原则）：

  • 高基数：key 的取值空间要大（如 userId），否则分片数受限、产生超大 chunk；
  • 写分布均匀：避免单调递增的 key（如默认自增 _id/时间戳）把所有新写入压到同一个「热分片」，应改用哈希分片打散；
  • 查询局部性：常用查询能带上 shard key，使其定向到单个/少数分片（targeted query），而非广播到全部分片（scatter-gather）；
  • 取舍：范围分片利于范围查询但易热点，哈希分片利于均衡但范围查询会广播，可结合 zone sharding 按业务区域切分。

要点（选错后果）：

  • 单调递增 key → 所有写入集中到当前最大 chunk 所在分片，形成「热点分片」，无法均衡；
  • 低基数字段（如 status 只有几个值）→ chunk 数量极少、单 chunk 超大（jumbo chunk），迁移卡死、数据倾斜；
  • 查询不带 shard key → 被迫广播查询所有分片再聚合，延迟与负载翻倍。
  • 结论：shard key 一旦选定难以更改（需分片集合重建），设计时要同时兼顾「均衡写」与「定向读」。
