PHP-FPM 的进程模型是怎样的？master 和 worker 各负责什么？pm = static / dynamic / ondemand 三种模式如何选型？

题目

考察 PHP-FPM 进程模型、master/worker 职责划分与三种进程管理模式的选型依据，是 PHP 后端面试的性能调优高频题。

参考答案

结论

PHP-FPM（FastCGI Process Manager）是一个常驻的进程池管理器，负责把 Nginx 等前端转发来的 FastCGI 请求分发给 PHP worker 进程执行。它解决了 PHP「一次请求一次进程」的 CGI 模式性能问题。

进程模型

  • master 进程：以 root 启动，不处理业务请求。职责：绑定 socket（TCP 或 Unix domain socket）、创建并监控 worker 池、根据 pm 配置 fork/回收 worker、处理 SIGUSR2（重载配置）/SIGUSR1（重开日志）等信号、健康检查（pm.max_children 打满时告警）。
  • worker 进程：以普通用户运行，真正执行 PHP 脚本。一次只处理一个请求，处理完不退出，而是回到池中等待下一个请求（复用 opcache、数据库长连接要小心残留状态）。超过 pm.max_requests 后 worker 自杀重建，防内存泄漏累积。

三种 pm 模式选型

| 模式 | 行为 | 适用场景 |

|---|---|---|

| static | 启动即固定 pm.max_children 个 worker | 大流量生产环境首选：内存可控、无 fork 抖动，但需按 内存 ÷ 单进程峰值内存 精确计算 |

| dynamic | 起步 pm.start_servers，在 min_spare_servers 与 max_spare_servers 间浮动 | 流量波动明显的中小站点，兼顾资源与弹性 |

| ondemand | 无请求不 fork，来请求才拉起 | 多租户/低流量虚拟主机，省内存但首请求延迟高 |

调优要点

  1. pm.max_children 溢出的症状：日志出现 server reached pm.max_children，请求排队 → 502/超时；
  2. 单 worker 内存用 ps --no-headers -o rss -C php-fpm | awk '{s+=$1} END {print s/NR/1024"MB"}' 估算；
  3. 常见 502 排查链：worker 全忙 → listen.backlog 溢出 → 与 Nginx 的 socket 权限/路径不一致。
追问常见：为什么 PHP「天然」抗内存泄漏？——请求级生命周期，变量随请求结束释放；但 FPM 常驻化后 pm.max_requests 仍是兜底手段。
