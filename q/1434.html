Oracle 里一条 SQL 变慢了，你会怎么排查？请说清执行计划的获取方式与基线（SQL Plan Baseline）的作用。

高级简答题DBA数据库管理员数据库开发工程师Java后端工程师OracleSQL调优执行计划SQL Plan Baseline

题目

考察 Oracle SQL 调优方法论：执行计划获取、统计信息、绑定变量窥探与 SQL Plan Baseline 固化。

参考答案

排查路径（自上而下）

  1. 定位 SQL：AWR（DBA_HIST_SNAPSHOT / dba_hist_sqlstat）按 elapsed time / CPU / logical reads 排 Top SQL；实时问题直接查 v$session + v$sql；
  2. 拿执行计划：EXPLAIN PLAN FOR + dbms_xplan.display（注意它不绑定真实值，可能有窥探偏差）；生产更可信的是 dbms_xplan.display_cursor(sql_id, null, 'ALLSTATS LAST')——看 A-Rows 与 E-Rows 的偏差，偏差大 = 统计信息过期或优化器估算失真；
  3. 常见病因：统计信息过期（重新 dbms_stats.gather_table_stats）、索引被禁用/失效（分区表全局索引 truncate 后 unusable）、隐式类型转换（varchar 列用数字比较使索引失效）、绑定变量窥探（一执行计划吃所有值分布，直方图缺失时更糟）。

SQL Plan Baseline 的作用

把验证过的好计划固化下来：优化器生成的新计划必须先与 baseline 中已接受的计划比对，不在其中的进 history 观察区，不会自动启用。适合「统计信息变化导致计划突变、执行走全表扫」的生产止血场景：

-- 从共享池/AWR加载好计划到基线
dbms_spm.load_plans_from_cursor_cache(sql_id => 'bad_sql_id');

配合 SQL Profile（给优化器注入更准的估算修正）可治本。

易混淆点

  • 执行计划走索引但仍然慢：多半是回表（TABLE ACCESS BY ROWID）的随机 IO，聚簇因子（clustering_factor）过高时，索引扫 ≈ 全表扫的成本；
  • Hint 只是建议，失效场景多（视图合并、优化器版本变化），基线才是「承诺」。
