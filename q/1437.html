题目

考察 Flink 时间语义、Watermark 乱序容忍机制与两阶段提交 Sink 的 Exactly-Once 端到端保证，是实时计算面试的核心题。

参考答案

Watermark 机制

  • 问题：数据乱序到达，窗口不知道「什么时候才算所有 event time ≤ T 的数据都到齐了」；
  • Watermark(w) 是一个单调递增的时间戳断言：「event time ≤ w 的数据应该都到齐了」。窗口在其 maxEventTime - 允许乱序度 达到窗口右边界时触发计算；
  • 特性：单调不减；迟到超限的数据走侧输出流（side output）补偿；watermark 在算子间取最小值传播（木桶效应，某个空闲分区会拖住全局——可用 idle source 标记解决）。

两种时间语义取舍

| | Event Time | Processing Time |

|---|---|---|

| 正确性 | 结果与到达顺序无关，可重放/可回溯 | 受延迟、乱序影响，结果不稳定 |

| 延迟 | 需等 watermark，可能有窗口延迟 | 最低 |

| 适用 | 计费/统计/审计等要求数字可对账的场景 | 监控告警等「快比准重要」的场景 |

Exactly-Once 端到端（TwoPhaseCommitSink）

以 Kafka Sink 为例：

  1. 预提交（pre-commit）：checkpoint 触发时，把本阶段数据写入 Kafka 事务中（此时对外不可见），并把事务句柄存入 checkpoint state；
  2. 提交（commit）：checkpoint 完成后，事务正式 commit，数据对消费者可见；
  3. 故障恢复：从 checkpoint 恢复时，未提交的事务abort 重放，已提交的不重复；
  • 前提条件：source 可重放（Kafka offset 存 checkpoint）、下游支持事务或幂等、execution.checkpointing.interval 合理（事务未提交窗口 = 数据可见延迟）。
常见追问：watermark 一直不涨怎么办？——优先查某个空闲/落后的 partition（用 withIdleness），其次检查是否某条数据时间戳异常巨大。
