I IT 面试题库

AWS 上给应用做权限，为什么要「IAM Role 而不是把 AccessKey 写进配置文件」？IAM Policy 里 Allow 与 Explicit Deny 同时命中时以谁为准？

中级简答题云计算工程师云解决方案架构师SRE站点可靠性工程师AWSIAMRole最小权限

题目

考察 AWS IAM 权限模型：Role 临时凭证机制、Policy 评估顺序（显式拒绝优先）、最小权限原则落地。

参考答案

为什么用 Role 而不是 AK/SK

  1. 临时凭证自动轮换：Role 颁发的是 STS 临时凭证（默认 15 分钟～12 小时，自动过期自动换），AK/SK 是长期凭证——泄露窗口是「永久」的；
  2. 无需分发密钥：EC2/ECS/Lambda 上挂 Role 后，SDK 通过实例元数据（169.254.169.254）自动取凭证，代码和配置里完全没有密钥；
  3. 可审计可撤销：CloudTrail 里能看到 AssumeRole 事件，出事直接摘 Role 即止损；长期 AK 只能换密钥一轮；
  4. 跨账号/跨服务授权的标准解法。

Policy 评估顺序（面试必答）

默认全拒 → 有显式 Allow 才放行 → 但任一显式 Deny 命中 → 最终拒绝

即 Explicit Deny > Allow，且「默认拒绝」是起点。所以排查「有 Allow 却 403」时，要沿信任链逐层查：SCP（组织层）→ 权限边界（permissions boundary）→ 身体策略（identity policy）→ 资源策略（resource policy，如 S3 bucket policy）——任何一层 Deny 或缺 Allow 都会失败。

最小权限落地

  • 从 Access Analyzer 的未使用权限报告开始收敛；
  • 用条件键（aws:SourceIp、aws:PrincipalArn）收紧上下文；
  • 生产环境禁止 Action: "*"，用 IAM Access Advisor 按实际调用裁剪。
追问：Role 能否跨账号？——能，信任策略（trust policy）里写对方账号 ARN，对方用 STS AssumeRole 换取临时凭证。
