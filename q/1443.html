Playwright 的「自动等待」和 Trace Viewer 分别解决了什么问题？相比 Selenium 它为什么更快更稳？

中级简答题自动化测试工程师测试开发工程师Playwright自动等待Trace ViewerE2E测试

题目

考察 Playwright 核心机制：actionability 自动等待、trace 调试回放、与 Selenium 架构差异（WebSocket 直连 vs HTTP 轮询）。

参考答案

自动等待（Actionability Check）

Playwright 在每次点击/输入前自动做一系列检查，全部通过才执行动作：元素可见（有非空包围盒且非 visibility:hidden）、稳定（连续两帧位置不变，等动画结束）、可交互（不在遮挡层下、不在 disabled 状态）、可接收事件（命中测试目标是元素本身或其子元素）。

开发者因此几乎不需要手写等待——Selenium 需要显式 WebDriverWait 表达的「等按钮可点」，Playwright 的 click() 内置了。等待上限由 actionTimeout 控制，超时抛错并给出失败在哪一步检查。

Trace Viewer

npx playwright test --trace on（或 CI 里失败重试时记录）后，每条用例可打开 trace 回放：每一步的前后截图 + DOM 快照 + 网络请求 + console 日志 + 耗时时间线，还能在快照里像 DevTools 一样检查元素。它把「CI 上跑挂了但本地复现不了」的经典难题变成「打开 trace 看当时页面长什么样」。

为什么比 Selenium 更快更稳

  1. 通信协议：Selenium 走 W3C WebDriver 协议（HTTP 请求轮询式），每个动作一个 HTTP 往返；Playwright 用 WebSocket 长连接直连浏览器（CDP/Juggler），指令延迟低且能接收事件推送；
  2. 浏览器级 API：直接在浏览器进程里注入脚本做命中测试，而不是跨进程反复查询；
  3. 多上下文并行：BrowserContext 是轻量的「无痕浏览器实例」，毫秒级创建，天然支持 worker 并行；
  4. 自动等待消除 sleep：不稳定用例的最大来源被机制性消除。
追问：Playwright 能否测多标签页/iframe？——能，page.context().newPage()、frameLocator() 都是一等公民，这正是它相对旧工具的优势场景。
