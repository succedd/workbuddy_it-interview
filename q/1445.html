什么是重入（Reentrancy）攻击？Checks-Effects-Interactions 模式如何防它？重入锁（mutex）又是什么？

中级简答题智能合约开发工程师区块链工程师Web3开发工程师Solidity重入攻击CEI智能合约安全

题目

考察 Solidity 智能合约安全：重入攻击原理、CEI 模式、互斥锁与 receive/payable 机制，是智能合约面试的第一高频题。

参考答案

攻击原理

Solidity 给外部地址转账（call{value: x}("")）时会移交控制权——对方若是合约，其 receive()/fallback() 会被执行。重入攻击：恶意合约在 receive() 里再次调用原合约的提款函数，而此时原合约的余额还没扣减，于是「一边转一边取」直到榨干。

经典案例即 2016 年 The DAO 被盗 360 万 ETH（最终导致 ETH 硬分叉）。

// ❌ 脆弱写法：先转账，后清零
(bool ok, ) = msg.sender.call{value: amount}("");
balances[msg.sender] = 0; // 控制权已丢失，永远走不到

防御一：Checks-Effects-Interactions（CEI）

先校验、再改状态、最后才与外部交互：

// ✅ 先扣余额，再转账
balances[msg.sender] = 0;                    // Effects
(bool ok, ) = msg.sender.call{value: amount}(""); // Interactions
require(ok);

重入时余额已是 0，require(amount <= balances[msg.sender]) 直接 revert——账本先落地，攻击者拿不到「还没扣的钱」。

防御二：重入锁（mutex）

bool private locked;
modifier noReentrant() {
    require(!locked, "reentrant");
    locked = true;
    _;
    locked = false;
}

OpenZeppelin 的 ReentrancyGuard.nonReentrant 即此实现。CEI 是根本解，mutex 是多函数交叉调用（跨函数重入）时的保险。

补充

  • 0.8+ 的内置溢出检查防不了重入，别混淆；
  • transfer/send 有 2300 gas 限制曾被视为「天然防重入」，但 EIP-1884 后 gas 成本变化使其不可靠，正确姿势是 call + CEI + mutex；
  • 审计必查清单：所有 call/delegatecall 外呼点是否在状态更新之后。
