题目

考察 Unity 协程的执行模型：yield return 各类型的恢复时机、协程与主循环的关系、适用边界。

参考答案

执行模型

Unity 协程不是多线程：它跑在主线程，本质是 C# 迭代器（IEnumerator）。StartCoroutine 后协程体执行到第一个 yield 就挂起并把控制权还给 Unity，之后由引擎在主循环的固定阶段逐帧调用 MoveNext() 恢复执行——所以协程是「引擎代管的分帧状态机」。

yield 各类型恢复时机（高频考点）

| yield 返回 | 恢复时机 |

|---|---|

| null | 下一帧 Update 之后（当帧剩余逻辑不中断） |

| WaitForSeconds(t) | 渲染后计时 t 秒的下一帧渲染后（受 Time.timeScale 影响） |

| WaitForSecondsRealtime(t) | 同上但用真实时间（不受暂停影响） |

| WaitForEndOfFrame | 当帧所有相机与 UI 渲染完成后（截图常用） |

| WaitForFixedUpdate | 物理步骤之后 |

| StartCoroutine(other) | 等待子协程跑完（协程编排） |

注意 yield return 0 与 null 等价；WaitForSeconds 必须缓存复用（每次 new 会产生 GC）。

与 Invoke / async-await 取舍

  • 协程：与 Unity 帧循环天然同步，适合动画序列、延迟逻辑、分帧加载；缺点是依赖 GameObject 存活——Destroy(obj) 或 obj.SetActive(false) 会静默终止协程（隐藏不销毁时协程其实还在跑，是经典坑）；
  • Invoke/InvokeRepeating：只适合简单延迟调用，字符串反射、无法传参，新代码基本被协程与 async 取代；
  • async/await：真正的异步（可回线程池做重计算），但要自己处理回主线程（UnityWebRequest 后 await 默认不回主线程，需 SyncContext 或 UniTask）；场景切换时 async 续延不会自动取消，需要 CancellationToken，协程反而由引擎自动管理。

面试加分点

  • 协程在 MonoBehaviour.OnDisable 不自动停，OnDestroy 才停——「面板禁用后协程还在改 UI」的 bug 根因多在这；
  • 大量协程每帧轮询有开销，定时器密集场景用集中管理的调度器替代。
