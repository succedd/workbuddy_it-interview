题目

故障排查题（高级）：结合 Dart const 与状态管理，定位 Flutter 重建类问题。

参考答案

要点：

  • setState 不刷新：先确认是否在 build 之外错误地直接改了字段却没包在 setState(() {}) 里；其次检查是否是 const 子 Widget——const 实例 identical 相等，框架会跳过其 rebuild，若你期望它随状态变，就不该标 const；再看状态是否真的变了（对象引用没变、只是内部字段变，且用了 Equatable/== 比较时会认为「没变」）。
  • 重建风暴（build 被狂调）：常见原因——① 在 build 里做耗时计算或新建大对象，导致每次都重算；② 把 setState 放在了高频回调（滚动/动画）里；③ 状态提升过高，父 Widget 一变、整棵子树全 rebuild。
  • 定位手段：用 Flutter DevTools 的 Widget Rebuild 面板看哪些 Widget 重建次数异常；在 build 加 debugPrint 或断点统计调用频次。
  • 优化套路：① 用 const 固化不变的子树；② 把状态下沉到最小必要范围的 Widget，或改用状态管理（Provider/Riverpod/Bloc）做精准 Selector 订阅，避免整树重建；③ 耗时计算移到 initState/compute(Isolate)，不在 build 里算；④ 列表用 ListView.builder + itemExtent/key，避免一次性构建全部。

核心：Flutter 是「声明式 + 增量 rebuild」，问题是「重建范围过大」或「状态没真正触发」。用 DevTools 量化重建、用 const/状态隔离把重建限制在最小范围，必要时把重计算搬出主线程。
