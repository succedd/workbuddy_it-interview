百舸 CLI 提交训练任务，创建人为何显示 root 而不是子用户

中级故障排查题公有云售后技术支持云资源运维工程师安全运营工程师SOC百度智能云百舸IAMAK/SK子用户主账号

题目

场景：客户用百舸 CLI 提交训练任务，任务列表「创建人」显示为 root。客户说 AK/SK 是用自己的子账号创建的，应该显示自己的用户名。该子用户有「系统管理员」策略，IAM 子用户详情页的 AccessKey 列表为空；内部日志显示这组 AK 换出的临时凭证 userId 等于 domainId。请说明你如何定位原因、给出解决方案，并说明长期的密钥治理建议。

参考答案

先给结论

  • 任务「创建人」记录的是调用 OpenAPI 时签名所用 AK/SK 代表的身份，不是谁登录控制台、谁敲的 CLI。
  • 本案例中，客户用的那组 AK/SK 换出来的临时凭证 userId 等于 domainId，说明它代表的是主账号（root）身份，所以创建人显示 root 是「如实记录」，不是百舸显示错了。
  • 这组 AK/SK 是拥有「系统管理员」权限的子用户从「安全认证」页面创建的，而该子用户在 IAM 详情页的 AccessKey 列表是空的。内部排查结论是：这种方式创建出来的密钥等同于主账号密钥。
  • 解决：在 IAM 子用户详情页的 AccessKey 区域，为该子用户单独创建一组 AK/SK，用它重新配置百舸 CLI 再提交，创建人即可显示为子用户名。
  • 一句话记住：登录身份不等于签名身份，看创建人先看 AK 挂在谁名下。

题目背景（读给候选人）

  • 客户通过百舸 CLI 提交分布式训练任务，任务列表「创建人」一列显示的是 root。
  • 客户反馈：AK/SK 是用自己的子账号创建的，按理应该显示自己的用户名。
  • 该子用户被授予了「系统管理员」策略，另外还有 AccessKey 管理、AIHC（百舸）和订单相关策略，部分来自所属用户组。
  • 在 IAM 用户管理里打开这个子用户的详情页，AccessKey 列表显示「暂无数据」。
  • 第一问：你会怎么判断「创建人显示 root」到底是展示 Bug，还是身份本身就是 root？要查哪些证据？

考察目标

  • 是否理解云上「主账号 / 子用户 / AK/SK / 临时凭证」的身份模型。
  • 能否区分「谁在操作」和「请求以谁的身份签名」。
  • 排查时是否先拿身份证据，而不是先怀疑产品展示或直接让客户换密钥。
  • 能否给出最小权限、密钥治理方面的建议。
  • 能否把技术结论翻译成客户听得懂的话术。

排查思路：先拿身份证据

  • 第一步，看任务记录：创建人字段来自 OpenAPI 请求的鉴权结果。控制台提交和 CLI / SDK 提交走的是同一套鉴权逻辑，差别只在用的凭证。
  • 第二步，查这组 AK 的归属：在 IAM 子用户详情页看 AccessKey 列表里有没有这个 AK。本例列表为空，说明这组 AK 不在子用户名下。
  • 第三步，查凭证签发日志（需内部协助）：OpenAPI 网关会用 AK 换取临时凭证，日志里能看到签发结果的 userId 与 domainId。
  • 判定规则：userId == domainId 代表主账号身份；userId != domainId 代表某个子用户。本例是前者。
  • 第四步，确认 AK 创建入口：问清客户是从哪个页面创建的。本例是子用户登录后在「头像 → 安全认证」页面创建。
  • 到这里证据链闭合：创建人显示 root 是因为签名身份就是 root，展示没有错。

根因分析

  • 直接原因：CLI 配置的 AK/SK 代表主账号身份，请求以 root 签名，百舸据此记录创建人为 root。
  • 为什么子用户能拿到「主账号身份」的密钥：该子用户拥有「系统管理员」这类高权限策略，从「安全认证」页面创建的 AccessKey，在本案例里实际签发出来的身份是主账号，与在 IAM 子用户详情页为该子用户创建的 AccessKey 不是一回事。
  • 注意口径：官方文档写的是子用户和主账号都可以在「安全认证」页面创建 AccessKey，且子用户需要具备系统管理员、IAMFullControlAccessPolicy、IAMManageAccessKeyPolicy 或包含 CreateAccessKey 的自定义策略之一。「安全认证页创建的密钥等同主账号」是本案例的内部排查结论，回答时要以签发日志和 AK 归属为证据，不要当成文档规则背诵。
  • 已验证的正确组合：子用户 + 系统管理员权限 + 子用户自己的 AK/SK + OpenAPI 提交，创建人能正确显示子用户名。也就是说，问题不在权限，而在密钥归属。

解决方案

  1. 主账号或有 IAM 管理权限的人进入 IAM 控制台，打开「用户管理」，点进对应子用户详情页。
  2. 在 AccessKey 区域为该子用户创建一组新的 AK/SK，立即保存 SK（只显示一次）。
  3. 用这组 AK/SK 重新配置百舸 CLI，再提交一次测试任务。
  4. 在任务列表确认创建人显示为子用户名；同时在子用户详情页确认 AK 已出现在列表里。
  5. 确认无误后，评估停用并删除原来那组等同主账号身份的 AK/SK，先排查还有哪些脚本、流水线在用它，避免误停业务。

给客户的回复口径

  • 您好！关于「百舸 CLI 提交训练任务、创建人显示为 root 而非子账号」的问题，排查结论如下。
  • 原因：您当前用于提交任务的 AK/SK 实际代表的是主账号（root）身份。这组密钥虽然是在子用户下操作创建的，但该子用户拥有「系统管理员」权限，并且是从「安全认证」页面创建的 AccessKey，这种情况下签发的身份指向主账号，因此通过 OpenAPI / CLI 提交任务时创建人显示为 root。
  • 解决：请在 IAM 子用户的 AccessKey 管理页面为对应子用户单独创建一组 AK/SK（参考官方文档「子用户创建 AccessKey」），用这组子用户专属的 AK/SK 重新配置百舸 CLI 并提交任务，创建人即可正确显示为对应子账号。

追问 1：控制台提交显示子用户名，CLI 提交显示 root，是不是 CLI 有 Bug？

  • 不是。控制台用的是登录会话的身份，CLI 用的是配置文件里的 AK/SK。两边凭证不同，签名身份自然不同。
  • 正确做法是比对两次请求的签名身份，而不是比对「是不是同一个人操作的」。

追问 2：既然子用户有系统管理员权限，用 root 身份的密钥又能跑，为什么要换？

  • 审计失真：所有操作都记在 root 名下，出了问题无法追溯到具体人。
  • 权限过大：主账号身份不受子用户策略约束，密钥一旦泄露，影响的是整个账号。
  • 管理困难：员工离职或权限调整时，禁用子用户无法让这组密钥失效。
  • 官方文档也明确不建议使用主账号 AccessKey，建议按最小权限给子用户授权。

追问 3：怎么快速自查一组 AK 代表谁？

  • 看归属：在 IAM 各子用户详情页的 AccessKey 列表里找这个 AK，找得到就是该子用户的，哪里都找不到要警惕是主账号级密钥。
  • 看效果：用这组 AK 调一个会记录操作人的接口（如提交测试任务），看记录的创建人或操作人。
  • 看日志：需要内部确认时，查临时凭证签发记录里的 userId 是否等于 domainId。

追问 4：有没有比「换一组 AK」更好的长期做法？

  • 按人或按用途拆子用户，每个子用户只授予 AIHC 所需策略，不默认给「系统管理员」。
  • 自动化流水线使用专用子用户或角色，密钥定期轮转，旧密钥先禁用观察再删除。
  • 统一规定 AK 的创建入口和登记方式，避免同一账号下出现来源不明的高权限密钥。

常见误区

  • 把「子用户在页面上点了创建」等同于「密钥属于子用户」。
  • 一看到 root 就判定为产品展示 Bug。
  • 为了显示正确去收回子用户的系统管理员权限。本例已验证，权限不是关键，密钥归属才是。
  • 换完新密钥就结束，忘了清理旧的高权限密钥。
