百舸GPU任务调度失败：节点有空闲卡，任务却一直 Pending，怎么定位？

题目

场景：某客户在百舸某队列上有 4 张空闲 GPU 卡，提交训练任务后一直 Pending，控制台显示节点 running 且有空闲量。节点规格 176 核 / 960 GiB / 8 卡，系统预留后最大可分配 170 核 / 898 GiB。请说明 Pending 的根因、百舸的调度判断公式、排查步骤和解决方法，并结合资源池、队列、节点、容器、任务、开发机的层级关系，回答客户的常见疑问。

现象

  • 某客户在百舸某队列上有 4 张空闲 GPU 卡，提交训练任务后一直 Pending。
  • 控制台显示节点状态为 running，节点列表里也能看到「空闲量」。
  • 客户的疑问：卡明明空着，任务为什么调度不上去？

节点资源情况

节点规格：176 核 CPU / 960 GiB 内存 / 8 张 GPU 卡。

系统预留：6 核 + 62 GiB 留给管控组件，最大可分配 = 170 核 / 898 GiB / 8 卡。

节点GPU 空闲CPU 已分配CPU 剩余内存已分配内存剩余
节点A2 张144 核26 核656 GiB242 GiB
节点B2 张164 核6 核720 GiB178 GiB
节点C0 张160 核10 核400 GiB498 GiB
节点D0 张144 核26 核656 GiB242 GiB
  • 空闲的 4 张卡分散在节点A、节点B，每台各 2 张；另外 2 台节点 GPU 已占满。
  • 有空闲卡的两台节点合计剩余：4 张卡 + 32 核 CPU + 420 GiB 内存。
说明：原文写作「剩余 2 核」，对照控制台截图，「2」是该节点的 GPU 空闲量，CPU 剩余按「最大可用量 − 分配量」计算为 26 核和 6 核，上表已按截图校正。

因果链

环节发生了什么
1. 请求值偏高任务的 CPU / 内存 requests 设置过高
2. 资源被占已运行任务大量占用 CPU / 内存
3. 单节点不足2 台节点 GPU 已满；另 2 台各剩 2 张卡，但 CPU 只剩 26 核和 6 核
4. 界面误导控制台显示「有空闲量」，看起来资源够用
5. 无法落点新任务的申请量在任何一台节点上都无法同时满足
6. 结果GPU 物理空闲，但容器创建不了，任务一直 Pending

百舸是整机调度逻辑：任务申请的 GPU、CPU、内存必须在同一台节点上同时满足，不能跨节点拼凑。

  • 空闲卡分散在 2 台节点，每台的 CPU 剩余都不够任务申请量。GPU 物理空闲，但 CPU 不足导致容器无法创建。
  • 界面「空闲量」是累加值，不等于「单节点可用量」。

核心调度公式

单节点（最大可分配量 − 当前分配量）≥ 任务申请量  →  才能调度

以本次节点B为例：

项目数值
节点最大可分配170 核 CPU
节点当前分配164 核 CPU
节点剩余170 − 164 = 6 核
任务申请（假设）80 核
判断6 < 80，无法调度

界面显示的「空闲量」是所有节点的累加值，不等于单节点可用量，必须用上面公式逐节点计算。

解决方法

  • 调小任务配置中的 resources.requests.cpu 和 resources.requests.memory，让单任务需求能在一台节点的剩余量内满足。
  • 修改后重新提交，任务成功调度。

排查步骤

  1. 看「最大可用量 − 分配量」，不看「空闲量」。
  2. 查 Job 配置里 CPU / 内存的 requests 数值。
  3. 逐节点对比：任务申请量 vs 单节点剩余量（CPU、内存、GPU 三项都要比）。
  4. 查调度事件：kubectl describe pod <pod名>，看 Events 里的 Pending 原因（如 Insufficient cpu / Insufficient memory）。

注意

  • 排查优先级：先查 CPU / 内存，再查 GPU 硬件 / 驱动。
  • 建议：资源使用率超过 80% 时设置告警，提前发现单节点资源紧张。

附：百舸 AIHC 架构全解（背景知识）

一、百舸是什么

百舸（AIHC）是百度智能云专为 AI 训练 / 推理设计的 GPU 算力托管平台。客户不用管机器、不用装驱动、不用运维集群，只需提交任务，平台负责调度运行。

二、层级结构
百舸平台
└── 资源池（Resource Pool）
    └── 队列（Queue）
        └── 节点（Node）= 物理服务器
            └── GPU 卡
                └── 容器（Container）= 任务运行单元
                    └── 任务（Job）代码在此运行
三、各层详解（结合本案例数据）

1. 资源池

一批物理服务器的集合，是最顶层的资源边界。

资源池名称资源池 ID节点数量

2. 队列

资源池内部的资源分区。每个队列管理一批固定节点，任务提交到哪个队列就只能用那批节点，队列之间资源完全隔离。

3. 节点

一台物理 GPU 服务器。

项目CPU内存GPU
总量176 核960 GiB8 张
系统预留（管控组件）6 核62 GiB0
最大可分配170 核898 GiB8 张

4. 容器（Container）

在节点上动态创建的隔离运行环境，任务的代码就跑在容器里。

  • 每个容器占用一定量的 CPU / 内存 / GPU。
  • 容器之间完全隔离，互不干扰。
  • 任务结束后自动销毁，资源立即释放。
  • 通俗理解：节点是战车，容器是战车上隔出来的独立驾驶舱，代码在驾驶舱里运行，跑完拆掉。

5. 任务（Job）

用户提交的一个计算请求，描述「我要运行什么代码、需要多少资源」。

  • 关键调度规则：百舸是整机调度，任务所需资源必须在同一台节点上同时满足，不能跨节点拼凑。
  • 调度判断公式：单节点（最大可分配量 − 当前分配量）≥ 任务申请量 → 才能在该节点调度。

调度流程：

提交任务（申请 CPU + 内存 + GPU）
        ↓
调度器逐个扫描队列内节点
        ↓
找到满足条件的节点 → 在该节点创建容器 → 任务启动
找不到             → 任务 Pending

6. 开发机

一种长期运行的交互式任务，可 SSH 登录操作，类似云服务器。

对比项普通训练任务开发机
生命周期跑完自动销毁长期运行，手动停止
交互方式提交代码等结果SSH 登录
资源占用按需申请持续占用，不用也耗资源

注意：开发机不用时必须停止，否则会持续占用节点资源，挤压训练任务。
