Vite 的依赖预构建（Dependency Pre-Bundling）到底解决了什么问题？为什么开发环境下必须先做这一步？

中级简答题前端开发工程师前端架构师Vite依赖预构建ESM

题目

第一次启动 Vite 时会先「预构建」依赖再打开页面，控制台会打印 optimizing dependencies。请说明这一步存在的原因、它带来的收益，以及缓存失效与强制重建的机制。

参考答案

一、背景：dev 阶段直接提供原生 ESM

Vite 在开发环境下把源码当作原生 ESM 提供给浏览器，浏览器只请求当前页面真正用到的模块，因此冷启动时间几乎与项目规模无关。但这条路线有两个绕不开的障碍，正是依赖预构建要解决的。

二、它解决的两个问题

1. CommonJS / UMD 兼容性。 浏览器原生 ESM 不认识 require/module.exports，而 npm 上大量包仍以 CJS 或 UMD 发布。Vite 必须先把它们转成 ESM；转换时还会做智能导入分析，让对 CJS 模块的具名导入也能正常工作，例如 import React, { useState } from 'react' 在 React 这种导出是动态赋值的包上依然符合预期。

2. 性能：消灭请求风暴。 有些包的 ESM 产物内部被拆成成百上千个互相 import 的小文件，lodash-es 就有 600 多个内部模块。手写一句 import { debounce } from 'lodash-es'，浏览器会同时发出 600+ 个 HTTP 请求，服务端扛得住，浏览器侧却会因连接拥塞导致页面明显变慢。预构建把它打成一个模块，请求数从 600 降到 1。

三、执行与缓存机制

  • 首次启动 vite 时自动、透明地完成；用 esbuild（新版工具链为 Rolldown）这类原生工具执行，速度远快于传统打包器。
  • 入口来自对源码的自动扫描（识别裸模块导入）；运行中若发现缓存里没有的新依赖，会重新预构建并在必要时刷新页面。
  • 文件系统缓存放在 node_modules/.vite，是否重跑取决于：包管理器 lockfile 内容、patches 目录修改时间、vite.config.js 相关字段、NODE_ENV。想强制重跑可用 --force 或直接删除该目录。
  • 浏览器缓存用 max-age=31536000,immutable 强缓存，靠追加的版本 query 失效；调试依赖源码时需临时禁用缓存或加 --force 重启。

四、两个易错点

  • 预构建只在开发模式生效；生产环境仍然要打包，因为嵌套 ESM 的大量网络往返在生产并不划算。
  • monorepo 里被 link 的同仓依赖会被当作源码处理而不打包，若它不是 ESM 产物，需要显式加进 optimizeDeps.include。
