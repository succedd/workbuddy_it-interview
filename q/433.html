@babel/preset-env 是如何「按需」决定转译哪些语法的？modules 与 useBuiltIns 该怎么配？

中级简答题前端开发工程师Web全栈工程师Babelpreset-env浏览器兼容

题目

项目需要兼容一批老浏览器，但又不希望把每一行现代语法都降级、导致产物膨胀。请说明 preset-env 的工作机制与关键选项的取舍。

参考答案

一、它是什么

@babel/preset-env 是一个「智能预设」：根据你声明的目标环境，自动推导出需要的语法转换插件（以及可选的浏览器 polyfill），不再需要手工维护一长串插件列表，产物也因此更小。

二、工作原理

它依托 browserslist、compat-table、electron-to-chromium 等数据源，维护着「语法/特性 → 各目标环境支持版本 → Babel 转换插件与 core-js polyfill」的映射关系。拿到 targets 后查出一份插件清单，交给 Babel 执行。

  • 默认读取 .browserslistrc 或 package.json 里的 browserslist 字段作为目标，除非你显式设置了 targets 或 ignoreBrowserslistConfig。
  • 不收录 Stage 3 以下的提案：那个阶段浏览器基本都没实现，需要你手动引入；shippedProposals 选项可打开已经落地的提案。
  • 把 debug 设为 true 可以打印出实际启用了哪些插件与 polyfill、以及是由哪个 target 导致的，排查产物膨胀时非常有用。

三、modules 选项

默认值是 auto：Babel 依据 caller 数据（由 babel-loader、@rollup/plugin-babel 等提供）判断是否需要转换模块格式。设为 false 表示保留 ESM，仅在打算直接向浏览器交付原生 ESM 时使用；使用打包器时文档推荐保持 auto——打包器会告知 Babel 自己支持 ESM，从而不做转换。

实践要点：如果发现构建产物里 ESM 被转成了 CommonJS，Tree Shaking 会跟着失效（webpack 无法做静态分析），此时才需要显式干预，确保 ESM 结构保留到打包器手里。

四、useBuiltIns 与 corejs

  • entry：把源码里整包的 core-js 导入替换成按目标环境需要的具体条目，整个应用只写一次，多处引入可能造成难以排查的全局冲突。
  • usage：按每个文件中实际用到的 API 自动注入，重复引入由打包器去重。
  • false：完全不自动注入。

两者都要配合 corejs 指定版本（例如 3.33）才会注入与该版本匹配的 polyfill。注意 Babel 8 已移除 useBuiltIns，改为直接使用 babel-plugin-polyfill-corejs3。

五、补充

forceAllTransforms 会强制跑完全部转换，仅在产物还要过 UglifyJS 这类只支持 ES5 的工具时才开；include 与 exclude 用于强制加入或排除某个插件（例如用 fast-async 替代 regenerator）。
