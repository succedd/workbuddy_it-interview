什么是关键渲染路径（Critical Rendering Path）？围绕它可以做哪些首屏优化？

中级场景题前端开发工程师HTML/CSS/JS工程师首屏优化关键渲染路径性能指标

题目

用户反馈页面白屏时间长、首屏出来得很慢。请从浏览器把 HTML/CSS/JS 变成像素的过程出发，说明瓶颈通常在哪、以及对应的优化手段。

参考答案

一、关键渲染路径是什么

它是浏览器把 HTML、CSS、JavaScript 转换成屏幕像素所经历的步骤序列，包含 DOM、CSSOM、渲染树（Render Tree）和布局（Layout）四个阶段，最后是绘制（Paint）。优化它就能改善首次渲染时间，也能保证后续交互达到 60fps、避免卡顿。

二、各阶段要点

  • DOM 增量构建：HTML 字节 → 令牌 → 节点 → DOM 树。节点越多，后续阶段越慢。
  • CSSOM 不是增量的，CSS 是渲染阻塞的：后面的规则可能覆盖前面的，因此必须等 CSS 全部解析完才能构建渲染树。
  • 渲染树只含可见内容：display: none 的元素及其后代不会进入渲染树。
  • 布局依赖视口尺寸与节点数量：viewport meta 决定布局视口宽度；渲染树一旦被改动（加节点、改内容、改盒模型属性）就会触发布局。要减少布局的频率与耗时，就批量更新、避免动画修改盒模型属性。
  • 绘制：首屏会绘制整个屏幕，之后浏览器只重绘受影响的最小区域。

三、优化的三条主线

  1. 减少关键资源数量：把非关键资源延迟下载、标记为 async 或直接删掉；对图片、路由组件做懒加载。
  2. 减少关键资源体积与请求数：压缩/最小化 JS、CSS；用响应式图片与现代图片格式控制媒体体积。
  3. 缩短关键路径长度：用 preload / preconnect / dns-prefetch 提前取得关键资源，内联关键 CSS，配合 CDN 降低延迟。

四、实践中容易踩的坑

  • 不要过度优化选择器：.bar .foo 比 .foo 慢，但差距在微秒级，几乎从不值得投入；先测量再优化。
  • 把 JS 从解析阻塞中解放：默认脚本会阻塞 HTML 解析，合理使用 defer / async 能显著改善首屏。
  • 建立性能预算并持续监测：结合真实用户监控（RUM，看长期趋势）与合成监控（回归测试）两类手段，为关键指标设定预算上限，防止版本迭代中悄悄劣化。
