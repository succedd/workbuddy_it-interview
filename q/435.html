TypeScript 中 interface 和 type 有什么区别？项目里该如何选择？

初级简答题前端开发工程师Web全栈工程师TypeScript类型系统接口

题目

团队代码里两种写法混用，有人建议统一。请从扩展方式、同名声明冲突处理、可表达的类型范围几个角度说明差异，并给出选型建议。

参考答案

一、先说共同点

两者都能用来命名对象类型，也都支持泛型——例如描述一个盒子既可以用 interface Box<Type>，也可以用 type Box<Type> 来写。所以选型不能停留在「能不能写」这个层面。

二、核心差异一：扩展方式不同

  • interface 用 extends：从其它命名类型复制成员并追加新成员，还能一次继承多个类型。
  • type 用交叉类型 &：把已有对象类型组合起来，再用类型别名给结果命名。

官方文档明确指出：二者的主要区别在于如何处理冲突，而这也通常是你在 interface 与交叉类型别名之间做选择的首要理由。

三、核心差异二：冲突处理与声明合并

  • 同名 interface：TypeScript 会尝试合并；属性兼容则合并成功，属性同名但类型不兼容则直接报错。这一特性常用于给第三方库的类型做扩展补充。
  • 交叉类型：属性类型冲突时会被自动合并、编译通过，但那个属性会变成 never——要求同时满足 string 和 number，结果往往出人意料，且错误不在声明处暴露。

这是选型时最值得权衡的一点：前者让冲突尽早暴露，后者可能把问题推迟到使用处。

四、核心差异三：可表达的范围不同

文档原话是「type aliases, unlike interfaces, can describe more than just object types」。因此：

  • 联合类型、带 null 的辅助类型、数组/元组的简写形式（如 [string, number]、可选元素 [number, number, number?]、剩余元素、只读元组）习惯上由 type 承载；
  • 想用 interface 表达等价的元组结构，得手工声明数字索引与字面量 length，非常别扭；
  • 映射类型、条件类型这类类型运算更是 type 的主场。

五、选型建议

对外的对象形状、需要被他人扩展或合并声明的（如库的公开 API、DTO 结构）优先用 interface；联合、元组、函数别名、以及一切类型运算用 type。团队内统一约定比争论本身更重要——两种写法在项目里各司其职、保持风格一致即可。
