Next.js App Router 里 Server Components 与 Client Components 该怎么划分？'use client' 的边界是如何生效的？

高级简答题前端开发工程师Web全栈工程师Next.jsRSC服务端组件

题目

团队刚迁移到 App Router，经常遇到「在服务端组件里用了 useState 报错」或「把整个页面标成客户端组件导致 bundle 变大」。请说明划分依据与边界规则。

参考答案

一、默认与划分依据

App Router 中 layout 和 page 默认是 Server Component。判断标准不是「页面在哪渲染」，而是这段逻辑需要哪种环境的能力：

  • 用 Client Component 当你需要：状态与事件处理器（onClick、onChange）、生命周期逻辑（useEffect）、浏览器专有 API（localStorage、window、navigator.geolocation）、自定义 hooks。
  • 用 Server Component 当你需要：贴近数据源取数（数据库、API）、安全地使用 API key 等密钥、减少发往浏览器的 JavaScript、改善 FCP 并向客户端流式传输内容。

典型组合：页面作为 Server Component 取数，把结果作为 props 传给一个只负责点赞交互的 Client Component。

二、'use client' 是「边界」而不是「这个组件在客户端渲染」

把它写在文件顶部（import 之上）就声明了 Server 与 Client 模块图之间的边界：一旦某个文件被标记，它 import 的模块以及它直接渲染的组件都会进入客户端 bundle，所以不必给每个组件都加指令。

关键例外：作为 props 或 children 传入的 Server Component 不在 Client Component 的模块图里。它们仍在服务端渲染，以已渲染结果的形式传进来。这就是 <Modal>（客户端管开关）包裹 <Cart>（服务端取数）这种模式成立的原因。

因此优化 bundle 的正确做法是把 'use client' 下沉到最小的交互单元，而不是给整个 layout 打标记。

三、渲染与加载流程

服务端：Server Components 被渲染成一种紧凑的序列化格式 RSC Payload，其中包含 Server Components 的渲染结果、Client Components 的占位及其 JS 文件引用、以及从 Server 传给 Client 的 props；再用 Client Components + RSC Payload 预渲染出 HTML。

客户端首次加载：HTML 先给出快速的非交互预览 → RSC Payload 用于协调两棵组件树 → JavaScript hydrate（把事件处理器挂到 DOM 上）后页面可交互。

后续导航：RSC Payload 被预取并缓存，实现近乎瞬时的导航；Client Components 完全在客户端渲染，不再需要服务端产出的 HTML。

四、三个必踩的坑

  • props 必须可序列化：传给 Client Component 的函数、Symbol 等无法序列化。
  • Context 不支持 Server Component：React context 需要包一层接收 children 的 Client Provider，且 provider 应尽量放在树的最深处，以便 Next.js 优化其余静态部分。
  • 环境污染：只有 NEXT_PUBLIC_ 前缀的环境变量会进客户端 bundle，其余会被替换成空字符串——看似能跑实则失效。用 server-only / client-only 包可以让误用在构建期报错。
