有人手工在控制台改了资源、也有人本地跑 terraform apply，导致 state 冲突和计划里出现大量意外变更，怎么处理？

高级场景题DevOps工程师云平台开发工程师Terraform状态管理IaC漂移

题目

团队刚开始用 Terraform，state 文件放在本地甚至提交进 Git。请说明 state 的作用、冲突与漂移的根因，以及已存在的存量资源该如何纳入管理。

参考答案

一、先讲清 state 是什么

Terraform 用 state 保存远程对象与配置中 resource instance 的绑定关系（识别哪个云资源对应哪段代码），并记录元数据、提升大规模基础设施的性能。任何操作前都会先 refresh，用真实基础设施状态更新 state，再据此计算变更。

二、冲突的根因与治理

默认 state 存在本地 terraform.tfstate（外加一份 .backup），这既无法协作，一旦文件丢失就等于丢失整个工作区的状态。

正确做法是存入 HCP Terraform 或远程 backend：

  • 远程 state 提供状态锁，并发 apply 会被阻塞而非互相覆盖。
  • 不要放在不支持 state locking 和访问控制的存储（包括直接提交到版本控制系统），既可能丢数据，也会泄露 state 中的敏感信息（state 里通常含明文属性值）。
  • 在 CI 中串行化执行，plan 产物作为评审对象后再 apply 该产物，避免「本地随手 apply」。

三、漂移（drift）怎么处理

控制台手工改动后，refresh 会让 plan 出现预期外的 diff，两条路二选一：

  1. 保留改动：把控制台上的变更回写进代码，直到 plan 干净；
  2. 回滚改动：让真实资源回到代码声明的状态（可用 -refresh-only 单独刷新查看漂移，用 ignore_changes 忽略由外部系统管理的字段）。

同时应配套制度：生产环境禁止控制台改资源，或改动必须补提 PR。

四、存量资源如何纳管

Terraform 要求「配置中的 resource instance」与「远程对象」一对一。打破这一保证的只有两种方式，且后果需要你自己负责：

  • terraform import：把外部已创建的对象绑定到某个 resource instance，纳管后要补齐配置直到 plan 无变更。
  • terraform state rm：让 Terraform「忘记」某个对象（不再管理，需自行决定是否真的删除该资源，或重新 import 到别的 instance）。

五、红线与建议

绝不直接编辑 state 文件（它是 JSON 快照，格式会随版本演进），改用 terraform state 系列子命令；terraform show -json / terraform output -json 才是给外部系统消费的接口。此外建议：按环境/业务拆分多个 state 降低爆炸半径、开启后端版本控制与备份、对 state 加密并最小化访问权限。
