Spring Cloud Gateway 处理一个请求的完整流程是怎样的？断言（Predicate）和过滤器（Filter）分别在哪个阶段生效？

中级简答题Java后端工程师后端开发工程师Spring Cloud GatewayAPI网关过滤器链

题目

考察点：Handler Mapping → Web Handler → 过滤器链的三段流程，pre/post 过滤器以代理请求为分界线。属简答题（中级）。

参考答案

完整处理流程

  1. 客户端向 Spring Cloud Gateway 发起请求。
  2. Gateway Handler Mapping 用路由断言判断请求是否匹配某条 Route；没有匹配的路由就直接返回 404。
  3. 匹配成功后交给 Gateway Web Handler，请求进入这条路由专属的过滤器链。
  4. 过滤器链以「代理请求」这个动作分成两段（官方文档示意图里的那条虚线）：先执行所有 pre 过滤器逻辑，然后发出代理请求，最后执行 post 过滤器逻辑。

断言（Predicate）与过滤器（Filter）的分工

  • Predicate 决定「这个请求走不走这条路由」，在 Handler Mapping 阶段生效，命中即止。内置的有 Path、Method、Header、Cookie、After/Before/Between（时间）等。
  • Filter 决定「走这条路由时请求被怎么加工」，在 Web Handler 阶段生效，且分两个时间点：

- pre（代理请求发出前）：鉴权、限流、灰度路由、路径重写（如 StripPrefix）、请求头改写；

- post（代理请求返回后）：响应头处理、访问日志、熔断统计、响应内容改写。

工程注意点

  • 路由 URI 中未指定端口时，HTTP 默认 80、HTTPS 默认 443。
  • Gateway 构建在响应式栈（WebFlux + Netty）之上，过滤器里不能写阻塞代码，否则会占住 Event Loop 拖垮整个网关；必须做阻塞调用时要放到独立线程池隔离。
  • 网关适合承载横切关注点（鉴权、限流、灰度、链路追踪），业务编排逻辑不要下沉到网关，否则会让它变成新的单体。
