线上 PostgreSQL 磁盘占用只增不减，日志出现 "database must be vacuumed within N transactions" 警告，根因是什么？如何排查与处理？

高级故障排查题DBA数据库管理员后端开发工程师PostgreSQLVACUUMMVCC

题目

一个 PostgreSQL 实例上线半年后表文件持续膨胀、磁盘告警，同时日志出现 must be vacuumed within ... transactions 的 WARNING。请说明 MVCC 下的根因、排查步骤与处置方案。

参考答案

根因：MVCC 下 UPDATE/DELETE 不立即删除旧行版本

  • PostgreSQL 的 MVCC 要求旧行版本在仍可能被其他事务看到时不能被删除，所以 UPDATE/DELETE 只是让旧版本变成 dead tuple（死元组），空间不会立刻释放。
  • 标准 VACUUM 只移除死元组并把空间标记为空闲供后续复用，通常不把空间返还给操作系统（除非表尾恰好有整页空闲且能拿到排他锁）。因此频繁更新的表会长期处于「膨胀」状态，磁盘只增不减。
  • 若表经历大批量 UPDATE/DELETE，单纯 VACUUM 不够，需要 VACUUM FULL / CLUSTER / 表重写：它们重建整表、把空间还给 OS，但要 ACCESS EXCLUSIVE 锁、期间不能读写，且需额外约一个表大小的磁盘。生产上更常用 pg_repack 这类在线重建工具。

为什么会出现 XID 警告

  • 事务 ID 是 32 位循环空间，必须在 20 亿个事务内对每张表做一次 vacuum，否则旧事务「看起来变成未来」，即灾难性的事务 ID 回绕数据丢失。
  • VACUUM 通过把足够老的行标记为 frozen（插入 XID 当作 FrozenTransactionId，永远比任何普通 XID 更老）来推进 relfrozenxid，从而避免回绕。
  • 距离回绕点 4000 万事务时开始告警；少于 300 万时系统拒绝分配新 XID，只能起只读事务，写入全部报错。

排查步骤

  1. 看死元组与 autovacuum 是否跟上：SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_vacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;
  2. 看冻结年龄：SELECT c.oid::regclass, age(c.relfrozenxid) FROM pg_class c WHERE c.relkind IN ('r','m') ORDER BY age DESC; 以及 SELECT datname, age(datfrozenxid) FROM pg_database;
  3. 找阻碍 vacuum 的元凶：pg_stat_activity 里 age(backend_xmin) 大的长事务、pg_prepared_xacts 里的悬挂预备事务、pg_replication_slots 里失效的复制槽（它们都会钉住最老 xmin，让死元组永远清不掉）。
  4. 检查 autovacuum 是否太温和：autovacuum_vacuum_scale_factor（大表常需调小或改表级 autovacuum_vacuum_threshold）、autovacuum_max_workers、autovacuum_naptime，以及是否有表级存储参数覆盖了全局配置。

处置要点

  • 常规：调参让 autovacuum 跑得更勤（大表按表设 autovacuum_vacuum_scale_factor=0.01 之类），清理长事务与失效复制槽，需要时用 VACUUM (ANALYZE) 手动补一次。
  • 紧急回绕：必须由超级用户执行库级 VACUUM（否则无法处理系统目录，datfrozenxid 推不动）。不要用 VACUUM FULL（它需要 XID，会失败甚至加剧回绕风险），也不要用 VACUUM FREEZE（做了超出必要的额外工作）。
  • 需要真正回收磁盘：在低峰期用 pg_repack 在线重建，或短暂停写后用 VACUUM FULL；批量清空场景优先 TRUNCATE。
