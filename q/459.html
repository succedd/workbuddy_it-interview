拿到一条慢 SQL，如何用 EXPLAIN ANALYZE 读懂执行计划并定位瓶颈？

中级简答题数据库开发工程师Java后端工程师执行计划EXPLAINSQL调优

题目

EXPLAIN 和 EXPLAIN ANALYZE 输出什么、二者有什么区别？计划树该怎么读？哪些指标是最有价值的性能信号？

参考答案

先分清 EXPLAIN 与 EXPLAIN ANALYZE

  • EXPLAIN 不真正执行查询，只展示优化器的计划与估算成本；EXPLAIN ANALYZE 会真正执行语句，并额外输出真实行数和真实耗时，用来检验估算是否准确。
  • 因为 ANALYZE 真的执行，副作用照常发生（UPDATE 会真的改数据）。分析写语句时应包在事务里回滚：BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;。
  • 注意 ANALYZE 的时间不含结果传输给客户端的成本，且计时本身有开销。

计划树怎么读

  • 计划是一棵计划节点树，最底层是扫描节点，其上是连接、聚合、排序等节点，执行与阅读顺序都是自下而上；缩进表示父子关系，第一行是顶层节点，其总成本就是全计划的估算成本。
  • 估算部分：cost=启动成本..总成本（任意单位，以 seq_page_cost 等参数为基准，上层成本包含子节点）、rows（该节点输出的估算行数）、width（估算平均行宽，字节）。
  • 真实部分：actual time=启动..总耗时，单位是毫秒，且是每次执行的平均值；loops 是执行次数。actual time × loops 才是该节点真实总耗时——嵌套循环的内层节点单次很快但 loops 很大时，总时间往往才是瓶颈。

常见节点含义

  • Seq Scan：全表扫，表很小时正常；Index Scan：按索引顺序取行，适合取少量行或 ORDER BY 恰好匹配索引顺序；Index Only Scan：所需列全在索引里、无需回表，Heap Fetches 就是回表次数，为 0 才是理想；Bitmap Index Scan + Bitmap Heap Scan：先在索引里收集行位置再按物理顺序回表，比随机回表便宜，还可用 BitmapAnd/BitmapOr 组合多个索引。
  • 连接：Nested Loop 适合外层小、内层有索引；Hash Join 适合大表相连（小侧建哈希表）；Merge Join 要求两侧按连接键有序。

最有价值的几个性能信号

  1. 估算行数与真实行数偏差巨大：通常说明统计信息过期或采样不准，先 ANALYZE 刷新，再判断是否需要提高 default_statistics_target；估算不准会直接导致选错计划。
  2. 大表 Seq Scan + Rows Removed by Filter 很大：扫描了大量无用行，多半是缺索引或过滤条件选择性差。
  3. Sort 节点显示 Sort Method: external merge Disk：排序放不下内存、溢写到磁盘，考虑调大 work_mem、减少排序数据量或用索引避免排序。
  4. Index Only Scan 的 Heap Fetches > 0：说明发生了回表，考虑建覆盖索引（或用 INCLUDE 列）。
  5. 顶层 cost 只是估算，不要拿它和 actual time 直接比较，也不要把小表上的结论外推到大表。
