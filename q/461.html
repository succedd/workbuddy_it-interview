前端要系统性地防御 XSS，OWASP 的 Rule #0 到 #7 分别讲了什么？

高级简答题安全开发工程师信息安全工程师XSS输出编码CSP

题目

XSS 至今仍是 Web 端最高频的漏洞之一，而很多团队的防护只停留在「过滤特殊字符」。请从输出编码、HTML 净化、安全接收器、CSP 与 Trusted Types 等角度，说明一套纵深防御方案。

参考答案

一、总原则

OWASP《XSS Prevention Cheat Sheet》的核心结论是：没有任何单一技术能彻底解决 XSS，必须组合使用框架自动转义、按上下文的输出编码、HTML 净化，再叠加 CSP / Trusted Types 等纵深防御控制。

二、Rule #0：不要把不可信数据放进危险上下文

以下位置即使做了输出编码也不安全，应直接避免：<script> 标签内部、HTML 注释、<style> 内部、自定义标签与自定义属性、所有 on* 事件处理器（onclick、onerror、onmouseover），以及 eval()、setTimeout()、setInterval()。

三、按上下文做输出编码（Rule #1 - #5）

关键点是上下文决定编码方式，用错编码等于没防：

| 上下文 | 规则 | 编码方式 |

| --- | --- | --- |

| HTML 正文 | Rule #1 | HTML 实体编码，< → &lt;、& → &amp; |

| HTML 属性 | Rule #2 | &#xHH; 形式编码，且属性值必须用引号包起来 |

| JavaScript | Rule #3 | \uXXXX 编码，且只能放进带引号的数据值里 |

| CSS | Rule #4 | \XX / \XXXXXX 十六进制编码，且只能放进属性值 |

| URL 参数 | Rule #5 | 百分号编码 %HH，只编码参数值，不编码整个 URL |

一个高频错误：URL 要放进 href / src 时，需先做 URL 编码，再做 HTML 属性编码，顺序不能反。

四、需要渲染用户 HTML 时用净化（Rule #6）

输出编码会把富文本样式一并破坏，此时应改用 HTML Sanitization，OWASP 推荐使用 DOMPurify。注意三点：先净化再改动、确认下游库不会二次修改字符串、以及必须定期升级——浏览器新特性会不断带来新的绕过方式。

五、DOM 型 XSS 专项（Rule #7）

原则是换掉危险 sink：用 textContent、setAttribute、document.createTextNode 替代 innerHTML。更进一步可开启 Trusted Types，让 innerHTML、outerHTML、document.write、script.src 等 sink 拒绝接收普通字符串，强制数据流经审查过的策略——这是少数能消除整类 DOM XSS 而不只是缓解的手段。遗留代码可配置 default policy 委托给 DOMPurify。

六、两个常见错误做法

  • 只依赖 CSP：官方明确 CSP 只能作为纵深防御的一层，不能当主要防线；且必须按应用定制，企业级「一刀切」下发 CSP 头常会打挂遗留系统，最后只能开安全例外，反而削弱整体防护。
  • 在 Spring 拦截器 / Servlet Filter 里统一转义：上下文无关的统一编码会造成双重编码（O'Hara 渲染成 O\'Hara），且对纯客户端的 DOM XSS 完全无效。

七、框架是起点不是终点

优先使用框架自带的自动转义，但要避开框架的「逃逸口」：React 的 dangerouslySetInnerHTML、Vue 的 v-html、Angular 的 bypassSecurityTrustAs*、Lit 的 unsafeHTML。此外 React 无法处理 javascript: / data: URL，需要单独校验。
