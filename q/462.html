用户密码在数据库里应该怎么存？为什么不能直接用 MD5 或 SHA-256？

中级简答题信息安全工程师安全开发工程师密码存储哈希算法加盐

题目

仍有不少老系统在使用 MD5 或加盐 SHA-256 存储密码。请说明这种做法的风险，以及现代应用应该采用的口令哈希算法、参数与升级策略。

参考答案

一、为什么不能用 MD5 / SHA-256

这类算法的设计目标是快，而口令哈希恰恰需要慢。攻击者拿到库后会用候选密码、撞库字典、规则化词表或暴力枚举去撞哈希，配合 GPU 和云算力，快速哈希意味着单位时间能尝试的密码数量极大，破解成本极低。它们还缺少工作因子与内存硬度，无法通过调参跟上硬件演进；不加盐时还会直接被彩虹表命中。

二、正确做法：慢哈希 + 每用户唯一 salt

OWASP 的推荐优先级：

| 场景 | 算法与最低参数 |

| --- | --- |

| 首选 | Argon2id，m=19 MiB、t=2、p=1 |

| Argon2id 不可用 | scrypt，N=2^17、r=8、p=1 |

| 遗留系统 | bcrypt，工作因子 ≥ 10，注意 72 字节上限 |

| 需 FIPS-140 合规 | PBKDF2-HMAC-SHA256，迭代 ≥ 600,000 |

salt 的三个作用：① 每个密码唯一，逼迫攻击者逐个破解而不能一次算完比对全库；② 抵御彩虹表等预计算攻击；③ 相同密码产生不同哈希，不泄露「谁和谁用了同一个密码」。主流库通常自动管理 salt，开发者按推荐方式调用即可。

pepper 是可选的深度防御：所有密码共用一个密钥，必须存在 secrets vault 或 HSM 中，绝不能与哈希同库存。它防止攻击者仅拿到数据库就能开工，但单独使用不增加安全强度；一旦泄露需全员重置密码（因为不知道明文就无法重算）。

工作因子调优：经验法则是单次哈希耗时控制在 1 秒以内；设得过高反而会被利用发起 CPU 型 DoS。

三、不要用加密代替哈希

哈希是单向函数，加密是双向函数。密码用加密存储意味着存在被还原成明文的风险。唯一例外是系统必须拿明文去认证另一个不支持 OIDC 等现代协议的老系统，此时也应尽量改架构绕开。

四、算法要能平滑升级

把算法与工作因子以标准格式（如 modular PHC string format）与哈希一起存储，过渡期允许新旧算法共存。最常见做法是 rehash on login：用户登录时系统拿到明文，用新算法/新工作因子重算并覆盖旧记录。对长期不活跃的用户，可删除旧哈希强制重置。若旧哈希已经泄露，仅 rehash 不够——必须让旧密码失效并要求设置新密码，否则旧哈希对攻击者仍然有效。

五、两个易踩的坑

  • bcrypt 输入上限 72 字节，需要限制密码最大长度。
  • 直接 bcrypt(sha256(password)) 是有害的：哈希输出中的 NULL 字节会造成截断，且存在 password shucking 风险。必须预哈希时应使用 bcrypt(base64(hmac-sha384(password, pepper)), salt, cost)，且 pepper 不入库。
