业务需要支持用户上传头像和简历附件，请从设计上说明如何保证文件上传功能的安全？

高级场景题安全开发工程师安全架构师文件上传纵深防御安全设计

题目

文件上传是 Web 应用中最容易被低估的风险入口：只校验扩展名几乎必被绕过。请给出一套完整的防护设计，涵盖类型校验、文件命名、存储位置、权限控制与内容校验。

参考答案

OWASP 的核心立场是：文件上传没有银弹，必须纵深防御，任何单一校验都能被绕过。可按以下层次设计。

一、扩展名：只做白名单，且在解码之后校验

  • 只允许业务真正需要的扩展名：头像只用一种图片格式，简历只放 pdf 和 docx，其余一律不开。
  • 校验必须在文件名解码之后进行，才能挡住双扩展名（.jpg.php 绕过只看 .jpg 的正则）和空字节截断（.php%00.jpg）。
  • 单纯维护危险扩展名黑名单是很弱的保护，官方明确不建议作为唯一手段。

二、Content-Type 与文件签名都只能当辅助

  • Content-Type 由客户端提供，可被随意伪造，不能作为安全依据，只能用来拦住用户误传错误类型。
  • 文件签名（magic bytes）校验比 Content-Type 可靠，但绕过同样常见且容易，也不能单独使用。

三、文件名必须由应用重新生成

最稳妥的做法是用 UUID/GUID 之类的随机字符串重命名，一次性消除特殊字符、系统保留名、前导点（隐藏文件）、连续点（目录穿越）等所有隐患。若业务必须保留原文件名，则：限制最大长度、把字符集收敛到字母数字 + 连字符 + 空格 + 点、禁止前导点与连续点、禁止前导连字符与空格（方便脚本安全处理）。

四、大小与解压限制

必须限制单文件大小。若服务端会解压文件，限制要在解压后计算，并使用安全的方式估算压缩包实际大小，避免 zip bomb 打满存储。下载侧也要做请求限流。

五、存储位置与文件系统权限

优先级从高到低：独立主机存储（上传与应用完全隔离）> 存在 webroot 之外 > 存在 webroot 内但只给写权限（需要读时必须叠加内部 IP、授权用户等控制）。文件系统权限遵循最小权限原则，绝不给上传目录执行权限——确实需要执行的文件必须先扫描，确认无宏或隐藏脚本。

对外提供访问时，不要直接暴露真实路径与真实文件名，应通过应用层 handler 做 id 到文件的映射。

六、内容侧的深度校验

  • 图片：做二次重编码/重写（re-render），可以顺带破坏掉注入在图片元数据或像素中的恶意内容。
  • Office 文档：用 Apache POI 等库解析校验，或走 CDR（Content Disarm & Reconstruct）。
  • 杀毒与沙箱：有条件则过杀毒引擎；重要场景可在沙箱中人工审核后再对外发布。
  • 不建议允许 ZIP：压缩包内可夹带任意类型文件，攻击面过多。

七、别忘了接口本身

上传接口必须做身份认证 + 授权双重校验（用户需可识别、且具备相应权限），并接入 CSRF 防护。若文件可公开访问，还要考虑：防止遍历泄露其他文件、防止「小请求大响应」型 DoS、以及提供违规内容与侵权举报入口。

八、工程建议

优先参考成熟开源实现（如 Java 的 document-upload-protection），不要自造正则；所有用到的解析库都要安全配置并及时升级。

补充：把文件存进数据库是一种可选方案，便于统一备份与权限管理，但会带来性能、存储与 SQL 注入风险，只有在有 DBA 支持且确实更优时才采用。
