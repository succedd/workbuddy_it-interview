用 JMeter 压测时并发一加上去 TPS 就卡住不动、响应时间却持续变长，如何排查？

高级故障排查题性能测试工程师测试开发工程师JMeterTPS瓶颈压测排查

题目

这是性能测试中最典型的「压不上去」场景。很多人第一反应是被测系统到了容量上限，实际未必。请给出一套分层排查思路，先分清瓶颈在压力机、网络还是被测系统。

参考答案

排查的核心原则是先证伪压力机，再谈被测系统。相当比例的「性能瓶颈」其实是压测端自己先顶不住了。

第一步：确认 JMeter 自身有没有成为瓶颈

  • 必须用 CLI（非 GUI）模式执行：jmeter -n -t test.jmx -l test.jtl。GUI 模式只用于调试脚本，绝不能用来跑正式压测。
  • 压测时禁用或删除所有 Listener，尤其是 View Results Tree 和 View Results in Table——它们会在内存中累积每一个样本，直接拖垮压测机；用了 -l 落盘后监听器可以全部删掉。
  • 降低资源占用：输出用 CSV 而不是 XML、只保存需要的字段、关闭 functional mode、尽量少用断言、脚本语言选性能最好的（见 JSR223 章节）。
  • 检查压力机自身的 CPU、内存、网络与文件句柄；可用 JavaTest Sampler（不产生网络访问）测出该平台大致的吞吐上限作为基线。

第二步：确认线程数是否合理（警惕协调遗漏）

线程数取决于硬件能力与测试计划设计，也受服务端响应速度影响（服务端越快，JMeter 反而越忙）。线程数没有正确测算会遇到 Coordinated Omission 问题，得到错误或失真的结果。正确做法是逐步加压找拐点，而不是一上来就堆几千线程。

第三步：分层判断瓶颈在哪

在 TPS 停滞的同时，观察下面几组信号的组合：

  • 压力机资源打满、服务端还很闲 → 压测端瓶颈，加机器
  • 服务端 CPU 打满 → 应用计算或 GC 瓶颈
  • CPU 不高但响应时间持续上涨 → 锁竞争、线程池排队、慢 SQL、外部依赖等待
  • 网络带宽或连接池打满 → 基础设施瓶颈
  • 错误率随并发上升 → 多半是连接池、超时或限流配置

第四步：单机顶不住就横向扩展

需要大规模负载时，用分布式模式在多个节点跑 CLI 实例，由 Controller 汇总结果；也可以跑多个自治实例，最后合并 JTL 统一分析。注意此时 Controller 的结果汇总与网络传输本身也可能成为新的瓶颈。

脚本设计层面也常是元凶

  • 需要大量随机数据时应提前生成到文件，用 CSV Data Set 读取，避免运行时现算。
  • 少用大量相似 sampler，改用同一 sampler 循环 + 变量参数化。

一个常见误区

看到「TPS 不涨、响应时间变长」就下结论说系统到达容量上限。其实先确认三件事——压测机有没有顶满、是不是 GUI 模式、有没有开监听器——往往就能解决一半的问题。
