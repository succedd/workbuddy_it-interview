故障排查题：用户反馈页面点击无响应、动画卡死，Performance 面板显示一条持续数秒的 Long Task，函数调用栈指向一个 Promise.then 里反复 `queueMicrotask`/`then` 的轮询逻辑。请分析成因并给出排查与修复方案。

高级故障排查题前端开发工程师微任务饥饿Long Task性能排查事件循环

题目

考察点：把事件循环知识用于真实性能事故——微任务饥饿（microtask starvation）。追问：把这段轮询改成 setTimeout(loop, 0) 为什么就能让页面恢复响应？代价是什么？

参考答案

要点：成因是微任务饥饿——微任务在入列新微任务时会被事件循环在同一轮内持续处理到队列为空，永不把控制权交还给渲染和输入处理。

  • 机制：事件循环的规则是「排空整个微任务队列后才考虑渲染与下一个宏任务」。若每个微任务又入列新的微任务（无限 Promise 链式轮询、递归 queueMicrotask），队列永远不清空，浏览器无法更新渲染、无法响应点击——这正是 Performance 里那条长达数秒的 Long Task。
  • 排查路径：

- Performance 录制确认 Long Task 边界，看火焰图定位是哪段 Promise 链在自旋；

- 代码审查：是否存在 .then() 内部又返回 pending Promise 的轮询、或 while+queueMicrotask 的「异步死循环」；

- 注意 await 一个永不 resolve 的 Promise 不算此类（它会让出控制权），但 async function 里循环 queueMicrotask 就会。

  • 修复：把自旋逻辑改为宏任务级调度——setTimeout(loop, 0) 或 MessageChannel，每轮之间事件循环有机会处理渲染与输入；理想方案是用 requestAnimationFrame/requestIdleCallback 或 MutationObserver/事件驱动替代轮询本身。
  • 代价：宏任务调度每轮间隙更「贵」，轮询频率上限变低；但对交互型页面这正是想要的取舍——响应性优先于吞吐。
