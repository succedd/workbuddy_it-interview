场景题：你加入一个 20 人团队，主仓库同时存在 Git Flow（feature/release/hotfix 多长命分支）和 trunk-based（主干开发 + 短命分支）两种提案。请对比两种分支策略的适用场景，并给出你的选型建议。

题目

考察点：分支策略是团队协作与 CI/CD 效率的核心权衡。追问：如果团队要求「随时可发布」，两种策略分别靠什么机制保证？

参考答案

要点：分支策略的本质权衡是「发布节奏的隔离需求」与「集成成本」，没有绝对最优，取决于发布频率与团队规模。

  • Git Flow：master + develop 双主干，feature/release/hotfix 支撑「多版本并行维护」。适合发布周期长、多版本并存的产品（App 发版、SDK、私有化部署），隔离清晰但分支多、合并成本高、集成晚，容易攒出大冲突。
  • Trunk-based：所有人向主干提交，分支存活通常 < 2 天，靠 feature flag 控制未完成功能。适合持续部署的互联网服务：集成早、冲突小、主干始终可发布；代价是必须配套自动化测试、CI 门禁和 feature flag 基础设施。
  • 选型建议：20 人团队若做 SaaS/在线服务，选 trunk-based + GitHub Flow 简化版（PR 短命分支 + 必须过 CI + squash 合并），配合每日主干构建；若交付的是需要给客户维护 1.x/2.x 的产品，用 Git Flow 的 release/hotfix 分支承载版本维护，feature 开发仍走短命分支，两者并不互斥。
  • 「随时可发布」的保证机制：trunk-based 靠 CI 门禁 + feature flag（未完成功能关闭开关也可上线）；Git Flow 靠 release 分支上的验收与 cherry-pick 修缺陷。前者把成本花在自动化，后者花在人工流程。
