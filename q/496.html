场景题：同事执行了 git reset --hard HEAD~2 丢掉了两个未推送的本地提交，随后又在另一个分支上 force push 重写了已共享的分支。请分别说明：如何用 reflog 找回「丢失」的提交？为什么被 reset 的提交并不会立刻消失？

题目

考察点：把「Git 几乎不会真正丢失数据」的原理（引用可达性 + reflog + GC）用于真实事故，是追问链的收口。追问：git gc 什么时候才会真正删掉这些提交？

参考答案

要点：reset 只移动分支指针，提交对象仍留在对象库中，只要 reflog 里还有记录就完全可恢复。

  • 找回流程：

1. git reflog 查看本仓库 HEAD 的移动历史，找到 reset 之前的那个动作行（如 HEAD@{1}: commit: 完成支付回调），记下其 SHA；

2. git reset --hard <SHA> 或 git branch recover <SHA> 把分支/新分支指向它，两个提交完整回来了；

3. 若记不清，git fsck --lost-found 可列出没有任何引用指向的悬空提交辅助排查。

  • 为什么不会立刻消失：Git 的 GC 判断标准是可达性——从任何引用（分支、标签、reflog）出发遍历不到的对象才算垃圾。reset/rebase/amend 产生的「旧提交」在 reflog 过期前都可达，默认 reflog 条目保留 90 天（不可达提交 30 天），到期后 gc 才真正清理。所以「git reset 丢代码」九成是虚惊。
  • force push 重写公共分支的善后：受影响的同事不要直接 pull 合并，先 fetch，再 git rebase origin/<branch> 或 git pull --rebase，Git 会按 patch-id 跳过已被重写吸收的提交；事后团队应开启分支保护禁止强推主干。
  • 预防措施：重要分支开 protected branch；养成 git branch backup-<date> 打临时书签再做危险操作的习惯——成本为一个指针文件，换一条完整退路。
