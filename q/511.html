为什么分布式系统需要分布式事务？CAP 与 BASE 理论如何解释「强一致 vs 最终一致」的取舍？

初级简答题Java后端工程师分布式事务CAPBASE最终一致

题目

考察点：是否理解单机 ACID 在分布式下失效的根因，以及 CAP/BASE 给出的工程权衡。追问：为什么大多数互联网系统选择最终一致而不是强一致？

参考答案

要点：

  1. 为什么需要：单体库里一个本地事务就能保证 ACID；但下单、扣库存、扣余额分散在多个服务/库后，一次操作跨多个资源，本地事务管不到全局，必须用分布式事务保证跨服务的业务正确性。
  2. CAP 定理：一致性（C）、可用性（A）、分区容错（P）三者最多取二；分布式系统必然有网络分区（P 必选），所以实际是在 CP（强一致、牺牲可用） 与 AP（高可用、牺牲强一致） 之间选。
  3. BASE 理论：在 AP 基础上放宽——Basically Available（基本可用）、Soft state（软状态，允许中间态）、Eventual consistency（最终一致）。即不要求每刻都一致，只要经过一段时间后达成一致。
  4. 取舍：金融核心账务等强一致场景走 CP（如 2PC/XA）；电商、社交等高频场景走 AP + 最终一致（消息表/事务消息），用牺牲短暂不一致换吞吐与可用性。

结论：分布式事务不是「把本地事务搬过来」，而是按业务一致性要求，在「强一致（慢但准）」和「最终一致（快但短暂不一致、需补偿）」之间做架构取舍。
