列举常见的「索引失效」场景，并说明如何用 `EXPLAIN` 执行计划判断一条 SQL 是否走了索引。

高级场景题数据库工程师数据库开发工程师后端开发工程师索引失效EXPLAIN执行计划SQL优化

题目

说明函数/隐式转换/前导模糊/OR/!=/NULL 等导致失效的情况，并解释 EXPLAIN 的 type/key/rows/Extra 关键字段。

参考答案

  • 常见索引失效场景：

1. 对索引列使用函数或运算：WHERE YEAR(created_at)=2024、WHERE amount+1=10 → 无法用索引。

2. 隐式类型转换：列是字符串却用数字比较 WHERE phone=13800000000（MySQL 会转字符串，致失效）。

3. 前导模糊/左右模糊：%abc 无法用 B+ 树定位（abc% 可走前缀）。

4. 不等于/范围过度：!=、<> 多数情况放弃索引；NOT IN、OR 连接非索引列也会失效。

5. 违背最左前缀（见上题）。

6. 字符集/排序规则不一致 的 join 关联列导致无法用索引。

  • 用 EXPLAIN 判断：

- type：访问类型，从好到差 system > const > eq_ref > ref > range > index > ALL；ALL 即全表扫描（未走索引）。

- key：实际使用的索引；为 NULL 表示没用到。

- rows：预估扫描行数，越大越慢。

- Extra：Using index（覆盖索引，好）、Using where（回表过滤）、Using filesort/Using temporary（需优化，排序/临时表）。

  • 优化思路：建覆盖索引、避免 SELECT *、改写函数条件为范围、调整联合索引顺序。
