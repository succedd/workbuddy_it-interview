如何保证缓存与数据库的数据一致性？先删缓存还是先更新数据库？延迟双删是什么？

高级故障排查题数据库工程师后端开发工程师后端架构师缓存一致性延迟双删Cache-Aside最终一致

题目

用了 Redis 缓存 + MySQL。更新数据时，缓存和 DB 怎么操作才能保证最终一致？请分析“先更新 DB 再删缓存”“先删缓存再更新 DB”的并发问题，并说明延迟双删与消息队列重试的思路。

参考答案

核心结论：缓存与 DB 无法在分布式下做到强一致，目标是最终一致。业界主流用Cache-Aside（旁路缓存）+ 先更新 DB、再删除缓存。

先更新 DB，再删缓存（推荐）：

  • 流程：写 DB → 删缓存（或下次读时回填）。
  • 并发风险低：极端情况下“读请求在 DB 写前读到旧值且缓存恰失效”才不一致，概率低；且靠缓存 TTL 兜底最终一致。

先删缓存，再更新 DB 的问题：删缓存后、DB 提交前，若有读请求会把旧值重新填回缓存 → 不一致窗口更大，故一般不选。

延迟双删：删缓存 → 更新 DB → 延迟一段时间再删一次缓存，抵消并发读回填的旧值。延迟时间取“读业务耗时”之上。

删除失败兜底：

  • 消息队列重试：删缓存失败则发 MQ，消费端重试直到成功；
  • 给缓存加 TTL，作为最终兜底，保证旧数据不会永远留存。

注意：更新缓存（写穿）vs 删缓存——只读缓存场景优先“删缓存 + 读时回填”，避免无效写与并发写覆盖。强一致需求应直接读 DB，不依赖缓存。
