分布式锁的过期时间设短了会误删自己、设长了阻塞久，如何做“锁续期（watchdog）”？

高级场景题锁续期watchdogRedisson分布式锁

题目

业务执行时间不确定，锁 TTL 难以预估。请说明看门狗（watchdog）续期机制的思想，以及使用 Redisson 等客户端时续期与释放的注意点。

参考答案

问题背景：TTL 太短 → 业务没跑完锁就过期，别人抢锁（自己变“无锁执行”）；TTL 太长 → 客户端崩溃后临界区长时间无法进入。

看门狗（watchdog）续期：

  • 客户端加锁成功后，启动一个后台定时任务（看门狗）；
  • 只要客户端仍持有锁且业务未结束，就周期性地把锁的过期时间重置/延长（如每 1/3 TTL 续一次）；
  • 客户端正常释放锁时，取消看门狗并删除 key；
  • 客户端崩溃 → 看门狗随之停止 → 锁在 TTL 到期后自动释放，避免死锁。

Redisson 实践：lock() 默认带 watchdog（每 10s 续期到 30s），lock(leaseTime) 显式指定后不自动续期；释放用 unlock()（内部校验+删除）。

注意点：

  1. 续期本身须原子（用 Lua 或 PEXPIRE）；
  2. 续期间隔应小于 TTL，且留网络余量；
  3. 必须配合唯一 value + 安全释放（Lua/DELEX），否则续期/释放会动到他人锁；
  4. 看门狗不能解决“GC/STW 长停顿导致续期失败”的极端场景，超高安全要求仍需 fencing token（etcd/ZK）。
