【场景题】如何优雅地停止一个正在运行的 Java 线程？为什么 volatile 状态标志位能可靠工作？

初级场景题Java后端工程师后端架构师JVMG1GC

题目

追问链起点：从一个最常用的 volatile 实战场景切入。考察点：Thread.stop() 被废弃的原因；volatile 状态标志位的可见性依据（happens-before 传递性）；与 interrupt() 机制的配合与选型。

参考答案

要点一：stop() 为什么被废弃

  • Thread.stop() 会立即终止线程并释放其持有的所有锁，被终止线程正在保护的共享数据可能处于"改了一半"的不一致状态，且调用方无从感知，问题难以排查，因此 JDK 早已将其标记为废弃。
  • 正确思路是"协作式终止"：由目标线程自己在安全检查点检测停止信号并主动退出。

要点二：volatile 状态标志位方案及其原理

  • 典型写法：private volatile boolean running = true; 工作线程在循环中轮询该标志，发现 false 即退出；外部线程只做一次 volatile 写。
  • 可靠性依据是 JMM 的 happens-before：volatile 写 happens-before 后续的 volatile 读；结合程序顺序规则与传递性，写线程在置 flag 前对普通变量的所有修改，读线程在看到 flag 变化后全部可见——这使标志位不仅能传递"要停了"的信号，还能安全发布停止前的状态。

要点三：与 interrupt() 的配合与选型

  • 线程卡在 sleep/wait/IO 等阻塞点时轮询标志位是无效的（收不到信号），此时应使用 interrupt()：阻塞方法会抛出 InterruptedException 或设置中断标志位，线程捕获后在 catch 中收尾退出。
  • 实践选型：纯计算/轮询循环用 volatile 标志；存在阻塞调用的任务用 interrupt 为主、标志位为辅，两者常结合使用。注意 catch InterruptedException 后应恢复中断状态（Thread.currentThread().interrupt()），避免中断信号被吞。
