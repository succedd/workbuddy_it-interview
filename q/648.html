InnoDB 的行级锁有哪三种？next-key lock 是如何防止当前读幻读的？间隙锁之间为什么互相兼容？

中级简答题后端开发工程师全栈开发工程师GraphQLRESTAPI

题目

追问链第四环：从"幻读靠锁解决"深入到锁的具体形态。考察点：Record Lock / Gap Lock / Next-Key Lock 的定义与锁对象差异；间隙锁只防插入不防读的设计意图；间隙锁兼容性反而容易引发死锁的细节。

参考答案

要点一：三种行级锁

  • Record Lock（记录锁）：仅锁住一条记录本身，分 S 型与 X 型，遵循 S-S 兼容、S-X/X-X 互斥。
  • Gap Lock（间隙锁）：锁定一个开区间范围但不包含记录本身，只在 RR 与串行化级别下存在，目的是防止其他事务向间隙插入"幻影记录"。
  • Next-Key Lock（临键锁）：Record Lock + Gap Lock 的组合，锁住一个左开右闭区间如 (3, 5]，既保护记录本身，又阻止新纪录插入到记录前面的间隙。

要点二：next-key lock 防当前读幻读的原理

  • 当前读语句（select ... for update 等）对扫描到的索引范围加 next-key lock 后，其他事务既不能修改范围内已有记录（记录锁互斥），也不能把新行插入到被保护的间隙（插入时发现位置被间隙锁覆盖而阻塞，并生成插入意向锁等待）。
  • 插入被"卡住"直到持锁事务提交释放间隙锁，幻影行根本无法出现，当前读因此可重复。

要点三：间隙锁的兼容性与死锁隐患

  • 间隙锁之间是兼容的：两个事务可以同时持有包含共同间隙的间隙锁，互不阻塞——因为它的目的是"防插入"而非"互斥读"，没有 S/X 之分。
  • 但这也埋着死锁隐患：事务 A、B 同时持有同一间隙的间隙锁后，A 尝试向该间隙插入（等 B 释放）、B 尝试向该间隙插入（等 A 释放），互相等待形成死锁。这是高频线上死锁模式之一，缩短事务、降低隔离级别或用 RC（无间隙锁）是常见缓解手段。
