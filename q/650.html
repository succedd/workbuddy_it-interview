【系统设计题】为账户表设计高并发余额扣减方案：如何在保证不超扣的前提下尽量减小锁的开销？请对比 SELECT ... FOR UPDATE、乐观锁版本号与原子 UPDATE 三种路线并说明锁的具体行为

高级系统设计题Java后端工程师后端架构师SpringCloudAlibabaNacosSeataSentinel

题目

追问链第六环：把锁知识落到并发写设计。考察点：当前读加锁的具体范围（等值查询唯一索引的加锁形态）；三种扣减路线的锁开销与适用场景；热点行问题与合并扣减/队列化等优化方向。

参考答案

要点一：路线对比

  • SELECT ... FOR UPDATE（悲观锁/当前读）：事务内对目标行加 X 型记录锁（等值查询命中唯一索引时只锁该记录本身），后续 UPDATE 同事务执行，全程持锁到 commit。强一致、逻辑直白，但并发下锁竞争激烈、持有时间越长吞吐越低；注意必须在事务中且 where 条件必须走索引，否则锁范围会扩大甚至升级为对扫描范围的锁，殃及无关行。
  • 乐观锁版本号：update account set balance = balance - ? , version = version + 1 where id = ? and version = ?；不加行锁，靠 affected rows 判断成败，失败重试。读多写少/冲突率低时性能最好，冲突率高时重试风暴反而劣化。
  • 原子 UPDATE：update account set balance = balance - ? where id = ? and balance >= ?；单条语句利用 InnoDB 行锁天然原子完成"判断+扣减"，无需先查后改，代码最简，冲突退化为短促的行锁排队，是余额扣减的默认首选。

要点二：锁开销与热点行优化

  • 三种路线最终都会落到同一行的行锁上，热点账户（如平台总账）的并发扣减会形成行锁排队，QPS 上限受单行锁吞吐约束。
  • 优化方向：热点行拆分（余额分桶）、把扣减请求在应用层合并后批量提交、用 MQ 把同步扣减削峰为串行消费、Redis 预扣 + 异步落库对账。核心思想都是"把单行锁的串行瓶颈摊开"。

要点三：一致性配套设计

  • 余额字段用 UNSIGNED 约束兜底防负数；扣减与流水写入同事务保证账实一致；对账任务兜底；乐观锁重试需设上限并监控失败率。
  • 选型建议：一般账户扣减用原子 UPDATE + 条件判断；冲突极低且逻辑复杂的业务用乐观锁；需要先读后写跨多资源协调时才用 FOR UPDATE，且务必控制事务长度。
