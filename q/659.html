什么是双亲委派模型？它解决了什么问题？如何打破双亲委派？

高级简答题深度学习工程师算法工程师PyTorchTensorautograd

题目

追问链第二问。考察点：三层类加载器与委派顺序；委派带来的「类的唯一性/安全性」收益；打破双亲委派的三种典型方式（重写 loadClass、线程上下文类加载器、OSGi/模块化）。

参考答案

要点一：模型定义与委派顺序

  • 类加载器之间存在父子关系（一般是组合关系而非继承）：启动类加载器（Bootstrap，C++ 实现，加载 JAVA_HOME/lib）→ 扩展类加载器（Extension / JDK9 后为 Platform）→ 应用程序类加载器（AppClassLoader，加载 classpath）→ 自定义类加载器。
  • 工作过程：一个类加载器收到加载请求时，先不自己加载，而是把请求逐级委派给父加载器；只有父加载器反馈「自己无法完成」（搜索范围内找不到该类）时，子加载器才尝试自己加载。

要点二：解决了什么问题

  • 避免类重复加载：父加载器已经加载过的类，子加载器不会再加载一次，保证同一个类在 JVM 中只有一份 Class 对象。
  • 保证核心类库安全（沙箱隔离）：比如用户自己写了一个 java.lang.Object，由于委派机制，最终会由 Bootstrap 加载 JDK 原生的 Object，用户写的同名类不会被加载，防止核心 API 被篡改。
  • 类的唯一性判定：JVM 判断两个类是否「相等」，前提是由同一个类加载器加载；不同类加载器加载的同名类互不相等，这也是双亲委派保证类型体系一致的基础。

要点三：如何打破双亲委派

  • 1) 重写 loadClass()：双亲委派的逻辑就写在 ClassLoader.loadClass() 里，重写它改变委派顺序即可（JDK 建议只重写 findClass()，重写 loadClass() 即为打破）。
  • 2) 线程上下文类加载器（TCCL）：父加载器请求子加载器去完成加载，属于「反向委派」。典型场景是 JNDI / JDBC SPI——DriverManager 由 Bootstrap 加载，但各家数据库驱动在 classpath 上，只能借 Thread.currentThread().getContextClassLoader() 加载。
  • 3) 模块化与热部署：OSGi、JDK 9 模块系统、Tomcat 的 WebAppClassLoader 都自定义了委派规则（如 Tomcat 先自己加载 Web 应用类，再委派给父加载器），以实现应用间类隔离与热替换。

要点四：为什么要打破

  • 基础类需要回调用户代码（SPI）、多应用需要类隔离、需要热部署/热加载——这些场景下严格的单向委派就成了束缚。
