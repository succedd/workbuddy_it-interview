哪些对象可以作为 GC Roots？为什么说对象被判定不可达后还有一段「缓刑」期？

高级简答题AI Agent开发工程师LLM应用开发工程师AI应用开发工程师AI Agent工具调用ReAct

题目

追问链第二问。考察点：GC Roots 的具体组成；两次标记与 finalize() 的缓刑机制；方法区（类、常量）的回收条件。

参考答案

要点一：GC Roots 的常见组成

  • 虚拟机栈（栈帧局部变量表）中引用的对象：如方法里 User u = new User() 的 u，正在执行的方法里的参数、局部变量、临时变量。
  • 本地方法栈中 JNI（native 方法）引用的对象。
  • 方法区中类静态属性引用的对象：如 static User u;。
  • 方法区中常量引用的对象：如字符串常量池里的引用、static final 常量。
  • 所有被同步锁 synchronized 持有的对象。
  • JVM 内部引用：基本数据类型对应的 Class 对象、常驻异常对象（NullPointerException 等）、系统类加载器。
  • 此外，垃圾收集还会根据所选收集器与回收区域临时加入一些对象（如跨代引用时的 Remembered Set 相关对象），因此枚举根节点时必须暂停用户线程（Stop The World）以保证一致性快照。

要点二：为什么不可达不是「立即死亡」

  • 可达性分析判定不可达后，对象进入「缓刑」阶段，真正回收要经过两次标记：

1. 第一次标记：对象不可达，被首次标记并筛选——判断是否有必要执行 finalize()（未重写过，或已被 JVM 调用过一次，都视为「没必要执行」）。

2. 第二次标记：若需要执行 finalize()，对象被放进 F-Queue，由低优先级的 Finalizer 线程去执行。只要对象在 finalize() 中重新与引用链上的任一对象建立关联（例如把 this 赋给某个静态变量），第二次标记时它就会被移出「即将回收」集合，成功自救。

  • 一个对象的 finalize() 最多只会被 JVM 自动调用一次，因此自救机会只有一次；没有自救的，第二次标记后即被回收。

要点三：实践结论

  • finalize() 运行代价高昂、不确定性大且无法保证调用顺序，官方已明确不推荐使用（JDK 9 起被标记为 deprecated）；释放资源应改用 try-with-resources 或 Cleaner。
  • 方法区的回收条件苛刻：常量需无任何引用；类需同时满足「实例全部回收、加载它的 ClassLoader 已回收、Class 对象无任何引用（含反射）」三个条件才「允许」回收，这也是元空间泄漏难排查的原因。
