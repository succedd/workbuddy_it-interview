MySQL 的 undo log、redo log、binlog 分别解决什么问题？各自保证了 ACID 的哪一性？

中级简答题LLM应用开发工程师AI应用开发工程师RAG工程师LLMRAG微调Agent

题目

追问链起点。考察点：三种日志所属层次（InnoDB 层 vs Server 层）；undo 保证原子性、redo 保证持久性、binlog 用于归档与主从复制；一条 UPDATE 语句的完整日志链路。

参考答案

要点一：三种日志的定位与层次

  • undo log（回滚日志）：由 InnoDB 存储引擎层生成，保证事务的原子性（Atomicity），用于事务回滚和 MVCC。
  • redo log（重做日志）：同样由 InnoDB 层生成，保证事务的持久性（Durability），用于掉电等故障后的崩溃恢复。
  • binlog（归档日志）：由 Server 层生成，所有存储引擎通用，主要用于数据备份、主从复制，本身不保证 crash-safe。

要点二：为什么需要 undo log

  • 事务执行中途崩溃或主动 ROLLBACK，需要把数据恢复到事务开始前的样子。
  • 做法：每次对记录做「增删改」前，先把回滚所需的信息记进 undo log（如插入记主键、更新记被修改列的旧值、删除记整行）。回滚时执行相反的操作即可：insert 对应 delete，delete 对应 insert，update 对应反向 update。
  • 同一条记录的 undo log 会形成版本链，配合 ReadView 就实现了 MVCC 快照读，这也是 RC/RR 隔离级别下「读不加锁」的基础。

要点三：为什么需要 redo log（WAL）

  • 修改数据时，InnoDB 先在内存的 Buffer Pool 中改脏页，并不立即刷盘（随机写极慢）。
  • 但如果此时宕机，内存中的脏页会丢失，事务却已经返回成功，就破坏了持久性。
  • 于是引入 WAL（Write-Ahead Logging）：修改前先顺序写 redo log（顺序写远快于随机写），并保证日志先落盘。宕机重启后，InnoDB 用 redo log 把没来得及刷盘的修改重做一遍，从而保证「已提交事务不丢失」。
  • redo log 是物理日志（记录「在某个数据页的某个偏移量做了什么修改」），大小固定、循环写，写满会覆盖前面的空间（因此必须先推进 checkpoint 把脏页刷盘）。

要点四：为什么还需要 binlog

  • redo log 是 InnoDB 私有的，且循环写会覆盖，无法用于数据备份和主从复制；binlog 是追加写（写满切新文件，不覆盖），记录了完整的逻辑变更历史。
  • binlog 有三种格式：

- STATEMENT：记原始 SQL 语句，日志量小，但含 now()、uuid() 等不确定函数时会导致主从不一致。

- ROW：记每行数据的变化前后镜像，日志量大但绝对安全，MySQL 8.0 起默认 ROW。

- MIXED：混合模式，一般情况用 STATEMENT，可能引发不一致时自动切 ROW。

要点五：一条 UPDATE 的日志顺序

  • 取数据页进 Buffer Pool → 写 undo log → 改内存数据页 → 写 redo log（prepare）→ 写 binlog → 写 redo log（commit），即两阶段提交。
