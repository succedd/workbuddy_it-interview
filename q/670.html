MySQL 主从复制是怎么实现的？它依赖哪种日志？主库宕机后从库数据一定完整吗？

高级简答题后端开发工程师数据库工程师DBA数据库管理员MySQL主从复制binlogrelay log

题目

追问链第三问。考察点：binlog + 三个线程（dump / I/O / SQL）的协作；异步复制默认不保证零丢失；半同步与 GTID 的作用。

参考答案

要点一：复制依赖 binlog

  • 主库把数据变更写进 binlog；从库把主库的 binlog 拉过来重放（replay），从而保持一致。
  • 因为 binlog 是 Server 层日志且追加写不覆盖，天然适合作为复制的传输介质；而 redo log 循环写会覆盖，无法用于复制。

要点二：三个线程的协作过程

  • 1) 主库的 log dump 线程：从库连上来后，主库为其创建一个 dump 线程，负责读取 binlog 并推送给从库。
  • 2) 从库的 I/O 线程：连接主库，请求 binlog，把收到的日志写入本地的 relay log（中继日志）。
  • 3) 从库的 SQL 线程：读取 relay log，解析出日志内容并在从库上重放，使数据与主库一致。
  • 所以整条链路是：主库 binlog → 从库 relay log → 从库数据。

要点三：复制格式与一致性

  • STATEMENT 格式在主从上执行同一条 SQL，遇到 now()、uuid()、limit 无 order by 等场景可能结果不同，存在主从不一致风险。
  • ROW 格式记录行的实际变化，最安全（MySQL 8.0 默认），但日志体积大、网络与磁盘开销更高。
  • 生产上通常选 ROW（或 MIXED），并把从库设为 read_only 防止误写破坏一致性。

要点四：主库宕机后从库不一定完整

  • MySQL 默认的复制是异步的：主库写完 binlog 就返回给客户端，不等待从库接收。若主库此时宕机且 binlog 尚未传给从库，这部分数据会永久丢失，切换后从库就少了数据。
  • 改进方案：

- 半同步复制（semi-sync）：主库提交后至少等待一个从库确认收到 binlog 才返回，降低丢失概率（不保证完全不丢，且超时会退化为异步）。

- 全同步 / 强一致方案（如 MySQL Group Replication、MGR）：多数派确认后才提交，牺牲延迟换一致性。

- GTID 复制：用全局事务 ID 代替「文件名 + 偏移量」定位同步位点，故障切换时能自动找到正确位置，避免重复或漏执行。

要点五：复制的典型用途

  • 读写分离（写走主、读走从）、数据备份（在从库备份不影响主库）、高可用切换、灰度/分析查询隔离。
