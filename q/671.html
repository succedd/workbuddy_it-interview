MySQL 主从延迟是怎么产生的？如何监控并缓解？

高级简答题后端开发工程师数据库工程师DBA数据库管理员MySQL主从延迟并行复制高可用

题目

追问链第四问。考察点：从库单线程重放、大事务、锁等待、硬件差异等成因；Seconds_Behind_Master 的局限；并行复制（MTS）与拆大事务等缓解手段；延迟时应如何路由读请求。

参考答案

要点一：延迟的本质

  • 主从延迟 = 主库执行完事务的时刻，与从库重放完该事务的时刻之差。
  • 链路是串行的：主库写 binlog → 网络传输 → 从库写 relay log → 从库 SQL 线程重放，任何一环变慢都会累积成延迟。

要点二：常见成因

  • 从库重放是瓶颈（最常见）：早期 MySQL 从库只有一个 SQL 线程串行重放，主库可以并发写，从库却要排队执行，自然追不上。
  • 大事务：主库一个事务删了 100 万行，从库也要一个事务删 100 万行，期间从库无法并行，延迟瞬间拉大。
  • 从库承担大量读压力：从库既要重放又要扛查询，CPU/IO 被打满。
  • 从库上的长查询或表锁：分析型 SQL 锁住正在重放的表，SQL 线程被阻塞。
  • 硬件/参数差异：从库机器配置低于主库、磁盘 IO 差、sync_binlog/刷盘策略不一致。
  • 网络抖动：跨机房、跨地域复制时延高或丢包。

要点三：如何监控

  • SHOW SLAVE STATUS\G 中的 Seconds_Behind_Master：从库落后主库的秒数。
  • 注意它的局限：该值基于 binlog 中事件的时间戳计算，复制线程卡死或网络断开时可能显示 0 或不准；更可靠的做法是在主库定期写入心跳表（含时间戳），在从库读取并计算差值，或基于 GTID 差值判断。
  • 生产上应把延迟做成监控指标 + 告警，并对「延迟超过阈值」的从库自动摘除读流量。

要点四：如何缓解

  • 开启并行复制（MTS）：MySQL 5.6 起支持按库并行，5.7 起 slave_parallel_type=LOGICAL_CLOCK 支持基于组提交的按事务并行，能数倍提升重放速度（MySQL 8.0 进一步优化为基于 WRITESET 的并行）。
  • 拆小大事务：批量更新/删除拆成分批执行，避免单个事务锁定过久。
  • 提升从库规格、使用 SSD、让从库专机专用（备份库与读库分离）。
  • 减少从库读压力：加从库分流，或把分析型查询迁到数据仓库。
  • 半同步复制降低极端情况下的数据丢失风险（但会略微增加主库提交延迟）。

要点五：业务侧的应对

  • 写后立即读的请求强制走主库（见读写分离场景）；
  • 对实时性要求极高且无法忍受延迟的查询，直接走主库或走缓存；
  • 在应用层设置「延迟阈值」，超过阈值把该从库摘掉，避免读到严重过期的数据。
