InnoDB 已经有了 Buffer Pool，为什么还需要 redo log？直接把脏页刷盘不行吗？

高级简答题Android开发工程师移动端开发工程师Android四大组件Activity

题目

追问链终点。考察点：随机写 vs 顺序写的性能差异；WAL 思想；Buffer Pool 解决「读慢」、redo log 解决「写了丢」；redo log 循环写与 checkpoint 的关系。

参考答案

要点一：两者解决的是不同问题

  • Buffer Pool 解决「读写慢」：它是内存中的页缓存，让读写尽可能命中内存，避免每次都访问磁盘。
  • redo log 解决「写了会丢」：内存是易失的，宕机后 Buffer Pool 里的脏页全部消失。redo log 把变更先顺序落盘，重启后据此重做，保证已提交事务不丢失。
  • 一句话：Buffer Pool 提升性能，redo log 保证持久性，二者不是替代关系而是配合关系。

要点二：为什么不能直接刷脏页

  • 随机写太慢：一个事务可能只改了几个字节，但对应的数据页散落在磁盘各处。刷脏页是随机 I/O，机械盘磁头要反复寻道，即使 SSD 也有写放大。若每个事务都同步刷脏页，TPS 会低到无法接受。
  • 写放大严重：一个 16KB 的页里改 8 字节，却要整页写回，浪费了 2000 倍的 I/O。
  • redo log 是顺序写：追加到日志文件尾部，顺序 I/O 比随机 I/O 快 1~2 个数量级，且只记录「哪里改了什么」，体积极小。这就是 WAL（Write-Ahead Logging） 的核心收益：用顺序写换取随机写。
  • 因此正确做法是：改内存页 + 顺序写 redo log，脏页由后台线程择机批量刷盘，把随机写摊平。

要点三：redo log 的落盘策略

  • 由 innodb_flush_log_at_trx_commit 控制：

- 1（默认）：每次事务提交都把 redo log 刷到磁盘，最安全，宕机不丢已提交事务。

- 2：每次提交只写到操作系统的 page cache，由 OS 决定何时刷盘；MySQL 宕机不丢，但机器断电会丢最后约 1 秒的事务。

- 0：每秒写盘一次；MySQL 宕机会丢约 1 秒的事务。

  • 金融、交易场景必须设为 1；日志类、可重放的业务可放宽到 2 换取吞吐。

要点四：redo log 写满了怎么办

  • redo log 是固定大小、循环写的结构。写满时，MySQL 必须停下来先把部分脏页刷盘，推进 checkpoint，擦除掉已不再需要的日志腾出空间，此期间业务写入会明显卡顿。
  • 这也是生产调优的重点：redo log 太小会导致频繁 checkpoint 与卡顿；太大则崩溃恢复时间变长。通常把 innodb_log_file_size 设为能容纳约 1 小时的写入量。

要点五：完整链路回顾

  • 读：先查 Buffer Pool，未命中再从磁盘载入并缓存。
  • 写：改 Buffer Pool 中的页（变脏页）→ 写 redo log（顺序）→ 后台线程择机把脏页刷盘（随机）→ 刷完推进 checkpoint，对应 redo log 空间可回收。
