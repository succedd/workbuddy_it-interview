为什么 MySQL 主键推荐使用自增 ID 而不是 UUID？

中级简答题Android开发工程师移动端开发工程师Compose声明式重组

题目

追问链第二问。考察点：聚簇索引按主键顺序存储；UUID 无序导致页分裂与碎片；二级索引叶子节点存主键值，主键越长索引越占空间；自增 ID 的局限与替代方案。

参考答案

要点一：InnoDB 是索引组织表（聚簇索引）

  • InnoDB 的数据按主键顺序存储在聚簇索引的 B+ 树叶子节点上。主键值决定了行的物理排列顺序。
  • 因此主键的插入顺序直接决定了 B+ 树是「顺序追加」还是「随机插入」。

要点二：自增 ID 的优势

  • 顺序写入，无页分裂：新行的主键总是比已有的都大，直接追加到 B+ 树最右边的页；页写满就新开一页，不会产生页分裂、不移动已有数据、不产生碎片。
  • 写入速度快：顺序 I/O，且能充分利用 Buffer Pool 的预读与缓存（热点集中在最新的几页）。
  • 占用空间小：BIGINT 只有 8 字节；而 UUID 是 36 字节字符串（或用 BINARY(16) 也需 16 字节）。

要点三：UUID 作为主键的三大问题

  • 随机写入导致页分裂：UUID 无序，新行可能被插入到 B+ 树的中间位置。目标页已满时触发页分裂——把一页拆成两页并移动数据，产生大量随机 I/O 与内存碎片，写入吞吐显著下降，表也会膨胀。
  • 二级索引被撑大：InnoDB 的二级索引叶子节点存的是主键值。主键从 8 字节变成 36 字节，每一条二级索引记录都要跟着变大，所有索引的体积成倍增长，缓存命中率下降。
  • 缓存局部性差：随机主键让热数据分散在大量页面里，Buffer Pool 命中率降低。

要点四：自增 ID 的局限

  • 不安全：ID 连续递增，容易暴露业务量（爬一遍就知道订单总数），且可被遍历。
  • 分布式场景不友好：分库分表下多库各自自增会冲突，需要额外设置步长（如 auto_increment_increment）或引入发号器。
  • 无法提前生成：必须先落库才能拿到 ID，某些需要「先生成 ID 再落库」的场景受限。

要点五：折中方案

  • 对内部分库分表：用雪花算法（Snowflake）等趋势递增的分布式 ID——高位是时间戳，整体递增，避免了 UUID 的随机写入问题，同时保证全局唯一。
  • 对对外暴露的字段：额外加一个 UUID / 短码字段做业务标识，主键仍用自增或 Snowflake，兼顾性能与安全。
  • 如果必须用 UUID：使用 MySQL 8.0 的 UUID_TO_BIN(uuid(), 1)（第 2 个参数为 1 会交换时间低位到高位，使其趋势递增）并存入 BINARY(16)，可大幅缓解随机写入问题。
