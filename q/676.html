为什么建议把索引列设置为 NOT NULL？允许 NULL 会带来哪些代价？

中级简答题后端开发工程师数据库工程师MySQLNULL索引设计建表规范

题目

追问链第三问。考察点：NULL 值的额外存储与标志位；NULL 对索引统计与优化器的影响；col = NULL 与 IS NULL 的语义陷阱；对聚合函数与 join 的影响。

参考答案

要点一：额外的存储与判断开销

  • 可为 NULL 的列，每行需要额外的标志位记录「该列是否为 NULL」（在行格式的 NULL 值列表中），即使该列存的是 NULL 也要占 1 bit（按字节对齐）。
  • 索引中同样要维护这个信息，索引结构更复杂，扫描时需要额外判断，性能略差。

要点二：语义与写法上的陷阱

  • col = NULL 永远不成立：SQL 中 NULL 代表「未知」，与任何值（包括 NULL 自身）比较的结果都是 UNKNOWN。判断是否为空必须写 IS NULL / IS NOT NULL。
  • 这是最常见的线上 bug 之一：WHERE name != 'Tom' 不会返回 name 为 NULL 的行，导致数据「莫名丢失」。
  • NOT IN 子查询中一旦包含 NULL 值，整个表达式结果恒为 UNKNOWN，查询返回空集；应改用 NOT EXISTS 或先过滤掉 NULL。

要点三：对聚合与去重的影响

  • count(列名) 忽略 NULL 行，而 count(*) 不忽略——用错会算错总数（见本链第一问）。
  • sum()、avg() 同样忽略 NULL：avg(列名) 的分母是非 NULL 行数，而非总行数。
  • group by 与 distinct 会把所有 NULL 视为同一组，join 时 NULL 与 NULL 不会被判为相等。

要点四：对优化器的影响

  • 索引列的 NULL 值会参与索引统计（基数、直方图），NULL 占比高时优化器对选择性的估算更容易失准，可能选错索引或放弃使用索引。
  • 部分情况下 IS NULL 仍可以走索引，但涉及 NULL 的复合条件往往让优化器更难优化。

要点五：实践建议

  • 建表时给列显式设置 NOT NULL 并配默认值（字符串默认 ''、数值默认 0、时间默认当前时间），能消除绝大多数 NULL 相关的坑。
  • 确实需要表达「无值」语义时，用明确的哨兵值（如 -1、''）或单独的状态字段，比 NULL 更可控。
  • 对已存在的可空列，改用默认值前要先回填存量 NULL，并确认业务代码没有依赖 IS NULL 的判断。
