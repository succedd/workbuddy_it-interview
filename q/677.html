什么是前缀索引？使用前缀索引有什么代价，什么时候该用？

高级简答题区块链工程师区块链后端工程师区块链哈希默克尔树

题目

追问链终点。考察点：对长字符串列只索引前 N 个字符以减小索引体积；如何确定合适的前缀长度（区分度计算）；前缀索引导致无法覆盖索引、无法用于 order by/group by 的代价。

参考答案

要点一：什么是前缀索引

  • 对 CHAR、VARCHAR、TEXT、BLOB 这类长字符串列建索引时，可以只把字符串前 N 个字符纳入索引：ALTER TABLE t ADD INDEX idx_name(name(10));
  • 目的：大幅减小索引体积——索引项变短后，单个索引页能放下更多记录，B+ 树层级更浅，缓存命中率更高，检索更快。

要点二：如何确定前缀长度（关键实操）

  • 核心指标是区分度（选择性）：前缀的区分度越接近完整列的区分度越好。
  • 计算方法：

1. 先算完整列的区分度：SELECT COUNT(DISTINCT name) / COUNT(*) FROM t;

2. 再逐个尝试前缀长度：SELECT COUNT(DISTINCT LEFT(name, N)) / COUNT(*) FROM t;（N 取 5、10、15…）

3. 选区分度接近完整列且 N 最小的那个长度（如达到 95% 以上即可），在「索引体积」和「区分度」之间取平衡。

要点三：代价与限制（面试必答）

  • 无法利用覆盖索引：前缀索引只存了字符串的前 N 个字符，不是完整值。即使查询只 select 该列，也必须回表取完整值，失去了覆盖索引「不回表」的优化。
  • 无法用于 ORDER BY / GROUP BY：索引中的值不完整，无法保证排序结果的正确性，MySQL 只能使用临时表或 filesort 完成排序。
  • 仍需回表二次比较：前缀相同但完整值不同的记录，索引只能把范围缩小到若干候选行，回表后再精确比对完整字符串过滤。
  • 区分度低时失效：若前缀区分度太差（如大量记录前 N 个字符相同），过滤效果差，优化器可能直接放弃使用该索引。

要点四：什么时候该用

  • 适合：长字符串列（邮箱、URL、地址、标题）且前缀区分度足够高；只用于等值查询或前缀匹配（LIKE 'abc%'）而不做排序分组的场景。
  • 不适合：需要对该列排序、分组；或查询依赖覆盖索引；或字符串本身很短（加了前缀收益不大）。
  • 不支持后缀匹配：LIKE '%abc' 走不了前缀索引，需要改用全文索引、倒排索引（ES）或存储反转字符串 + 前缀索引。

要点五：替代方案

  • 哈希列：新增一列存完整字符串的 CRC32 / MD5（或 BINARY(16) 的 UUID），对该定长列建索引，查询时同时带上原值精确比对。优点是索引极小、区分度极高；缺点是不支持范围查询与前缀匹配。
  • 全文索引 / 搜索引擎：对模糊搜索、分词检索场景，应使用 FULLTEXT 或 Elasticsearch，而不是在 B+ 树索引上硬凑。
